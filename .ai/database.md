# Database contract

Use `PHPThis\Database\Connection`. It is an instrumented PDO boundary, not a query builder.

Read `docs/decisions/012-pdo-transport-application-owned-dialects.md` before changing connection behavior or driver certification, ADR 057 before changing distinct-placeholder enforcement, ADR 038 before changing application database-authority guidance, and ADR 039 before changing migration ownership or placement guidance. Preserve native PDO DSNs and application-owned SQL; do not add a driver enum, connection registry, dialect interface, SQL rewriting, portability helper, role registry, permission helper, or runtime authority introspection.

Read ADR 022 before changing the protected document-list proof. That application path deliberately keeps complete raw SQLite SQL and explicit named parameter arrays together at direct `Connection` calls. Do not replace them with an ORM, query builder, repository, generic paginator, SQL/binding/placeholder helper, generated or dynamic SQL, transaction callback, or dialect abstraction.

Rules:

- Follow `.ai/configuration.md` for deployment-input reading, parsing, process-specific final types, credential separation, and failure. For a selected database connection, reference that non-secret typed configuration record and inject only the runtime type into visible HTTP `Connection::connect` construction; configuration-only scope records connection composition as deferred. Do not pass a configuration reader into behavior or let one database process obtain another process's identity.
- Treat the database and object definition source, database/catalog/schema/attachment namespace selection and qualification as supported, namespace and object control-or-ownership model, and active authority as separate application facts. Record the control-or-ownership model as not applicable when the engine has no such ownership concept. PHPThis chooses no namespace, qualification or search-path policy, identity topology, default privilege, or authority set. A recorded engine-default namespace and a recorded application-specific namespace are both valid application decisions.
- Configuration and source presence do not activate database authority. Connectivity, a trivial query, object existence, and migration completion do not prove that a runtime identity can execute an application's exact statements.
- Record every named operation's exact required objects and actions, code-owned statement source, prohibited actions, and the selected engine's effective-authority resolution. Direct, role or inherited, public or default, database or global, ownership-chain, IAM, and filesystem or process authority are examples, not universal categories. Zero runtime object access is valid before an operation exists.
- Give each adopted authority activation or deactivation one explicit application-owned owner and non-HTTP path: checksum-covered engine-specific `GRANT` or `REVOKE` migration SQL when supported and selected, a separately authorized application operation, or a named external provisioning source. Record elevated required and prohibited capabilities only when that path is adopted.
- Activate and verify authority against the exact engine and version before dependent code receives traffic. A failed migration, authority transition, or verification stops its dependent stage; remove or drain dependent code before deactivating authority or removing a namespace it needs. `.ai/operations.md` owns the application-specific release order.
- Execute SQL only through direct calls to `Connection`; do not add a second database execution boundary.
- Pass SQL that PHPStan resolves natively to a finite set of non-blank compile-time constant strings.
- Map an external structural choice such as ordering, selected columns, operators, or a bounded list shape to finite reviewed code-owned statements or fragments. Prefer complete statements, keep the final SQL finite and constant, and reject an unknown choice before database work.
- Keep every statement visibly specific to the application's recorded engine and version.
- Name every selected column; never use `SELECT *`.
- Give every selected expression a unique name or alias.
- Bind every SQL data value. PHT008 requires one distinct exact case-sensitive named parameter such as `:first_user_id` for each occurrence in every PHT006-finite alternative; bind repeated values separately, never interpolate values, repeat a placeholder name, generate or rewrite SQL, or pass both `user_id` and `:user_id` as input keys.
- Do not create an SQL sanitizer. Escaping, filtering dangerous characters, or validating an identifier does not replace bound data and compile-time-constant structure.
- Call `selectOneRow` only when zero or one row is valid.
- Call `selectAllRows` only with an explicit bound in the SQL or a documented bounded result.
- Call `executeStatement` for writes and inspect the affected-row count when it matters.
- Parse every returned row immediately with a concrete `fromDatabaseRow` projection factory.
- Start transactions explicitly, commit inside `try`, and roll back in `finally` when still active.
- Never call any connection method from a loop.
- Give each request a deliberately chosen `QueryBudget` in the composition root.
- Give each request a bounded `QueryTrace` and pass it explicitly to `Connection::connect` after the query budget.
- Give each separately named connection and terminal-summary source an explicit distinct budget and trace; do not share observation state across sources or engines or claim cross-connection atomicity.
- Test the same handler with small and large fixtures and assert equal query counts.
- Test adversarial strings as ordinary bound data and prove unsupported structural selectors and oversized list shapes fail before a statement is attempted.
- Inspect `QueryTrace::snapshot()` directly in tests; do not create broad query-log files.
- Register at most eight application-owned terminal-summary database sources through a finite code-owned list. Give each a bounded lower-ASCII label, its own budget, and a distinct trace; do not move event emission into `Connection` or add SQL/binding helpers.
- For ADR 024 jobs, keep the producer insert on the same connection and transaction as its business write, use one finite SQLite `UPDATE ... RETURNING` claim, fence every later transition with job identity, leased state, opaque token, and unexpired deadline, and commit the idempotent database effect with successful completion on that same connection.
- For ADR 027 migrations, use a fresh separately authorized SQLite migration connection only from the application console, validate one bounded inspectable ledger before pending work, and keep each concrete migration step's complete constant SQL and ledger insert in its own explicit transaction. The final coordinator's ordered manifest and private step calls are finite and unrolled; no database call occurs in a loop.
- Treat migrations as specialized database evolution, not a sibling business feature or a framework subsystem. Recommend `src/Database/Migrations/` and a matching application namespace for new adoption, while accepting the coherent path and namespace recorded by the application. Placement never creates a generic query, repository, or persistence layer: request-time SQL remains at its handler or one justified concrete operation.
- If multiple named database connections adopt separately tracked migrations, keep each connection's migration source, namespace, command, manifest, ledger, transition implementation, per-history constraints, and evidence boundary explicit in `.ai/migrations.md`; reference exact configuration and process identity from `.ai/configuration.md`, effective database-authority facts and accountable transition ownership from `.ai/data.md`, and application-wide sequencing and operational runbooks from `.ai/operations.md`. Permit an application-owned subdivision only for an adopted separately tracked history; do not prescribe speculative connection directories for a single-database application. Call histories independent only after their managed objects, data, authority transitions, and coordination domains are proved disjoint.

For each connection, the application context must record the code authority for structural SQL choices, bounded-list policy, database and object definition source, supported namespace selection and qualification, namespace and object control-or-ownership model or explicit non-applicability, runtime identity, each named operation's exact required objects and actions, explicitly prohibited runtime capabilities, engine-specific effective-authority resolution, authority activation/deactivation owner, and exact-engine verification source and date. Record separate migration or administrative required and prohibited capabilities, activation path, and isolation mechanism only when that elevated path is adopted. SQLite records applicable file ownership, permissions, attachment boundaries, and process isolation rather than invented roles or grants. Other engines record only the direct, role/inherited, public/default, database/global, ownership-chain, IAM, filesystem/process, or other sources they actually use. Least privilege limits damage after a defect; it does not make unsafe SQL safe.

Raw `array<string, mixed>` rows must not reach a response or business operation. A query budget is a backstop, not proof of good query shape. The trace hashes exact SQL and never retains SQL or parameters. Budget-rejected calls are not traced because PDO was not attempted. Trace duration covers prepare, bind, and execute, not fetching. Review joins, indexes, result bounds, and execution plans for production queries.

For a response that embeds child data, the handler or its one justified concrete operation owns the complete data-access plan. Its database-statement, cache-operation, and external-call counts stay fixed and bounded as the parent page grows. Complete those operations first, parse every row through concrete projections, and only then map the already-loaded values and encode JSON. Per-resource mapping, serialization, callbacks, and recursive traversal perform no database, cache, or external-service I/O. `PHT003` catches a direct lexical database call inside a loop; it does not inspect an indirectly called mapper or prove the absence of cache or integration work, so query budgets and scale evidence remain required.

For an ordinary to-one `parent.child` relationship, prefer one explicit bounded join with named parent and child columns, a uniqueness-preserving join condition, and every operation-owned scope or authorization predicate that applies to either side. A finite batch plan may instead use a fixed number of reviewed statements when one join is inappropriate, but it never executes one child lookup per parent. A fixed statement count is necessary, not sufficient: bound and review rows scanned, indexes, join fan-out, projection width, child cardinality, and response bytes against representative data.

Parent pagination remains authoritative. A join must not change the maximum parent count, stable parent ordering, continuation, or duplicate-parent behavior. A to-many relationship commonly needs a bounded parent-page read followed by one finite child batch rather than applying the parent limit to fanned-out joined rows. Every nested collection separately records its maximum cardinality, deterministic ordering, truncation, continuation, and contribution to the response-size limit. Missing optional to-one data has one exact object, `null`, or absence policy. Select only fields required by the operation, and when both a relationship identifier and the nested object's identifier are emitted, assert their explicit equality invariant.

The base transport harness defaults to SQLite. A requested driver must be installed and configured or the harness fails; dedicated CI runs the exact SQLite, MySQL, and PostgreSQL versions in the maintained [PDO transport certification matrix](../docs/database.md#pdo-transport-certification-matrix). The harness reports each observed version, and CI rejects a mismatch before fixture DDL. Changes to `Connection` must pass `composer test:database-drivers` locally and the complete three-engine CI job. A local run without an expected version does not expand the matrix, and engine-specific application behavior still needs tests against the exact deployed version.

`#[\SensitiveParameter]` on the `Connection::connect` password reduces accidental wrapper stack-trace disclosure only. It does not encrypt, redact explicit output, detect secrets, or replace the application's configuration and logging tests.

The sample user read uses one bounded aggregate statement for user event counts. Its small and large fixtures must keep the same query count and output contract. The account-scoped sample write performs exactly four named statements inside one explicit transaction: user, `account_users` relation, event, and commit-visible job. Actor authorization reads `account_memberships`; never infer that a principal ID and user ID identify the same entity. A one-statement budget rejects the account-user write, a three-statement budget rejects job publication, and each failure leaves every affected table unchanged. Do not replace either path with per-row queries or a transaction callback.

The protected document list is SQLite-only application evidence. It maps `order=rank_asc` and `order=rank_desc`, cursor presence, and omitted or one-to-three-category filters to eight complete statements; a direct empty list or parsed `['']` shape returns an empty page with zero protected SQL, and native PHP inputs such as `?categories[]=` produce that parsed shape. Every non-empty page binds requested account, resolved tenant, principal membership, cursor presence and values, category values, and the 51-row lookahead limit explicitly and uses one statement. Its exact `v1:<order>:<sort_rank>:<document_key>` cursor orders numeric `sort_rank` then `document_key COLLATE BINARY`; traversal is not a snapshot. MySQL and PostgreSQL remain base PDO transport claims only.

ADR 043 owns the universal application-migration invariants. Each history records its exact initial baseline, checksum-covered DDL/data/authority effects, finite exact-engine ledger metadata and rejection of unrecorded ledger-related objects, exact transaction and DDL atomicity limits, separately typed no-fallback configuration and identity, stable collision-safe coordination namespace and permissions, reachable-topology exclusion, lost-owner safety, and its disjoint or explicitly shared boundary with other histories. ADR 027 is SQLite-only application evidence: its `database:migrate` command owns one final `SqliteApplicationMigrations` coordinator with a finite ordered manifest and unrolled private migration-step calls, SHA-256 checksums over permanent identifiers and exact statement sequences, a bounded `application_migrations` ledger, one transaction per pending migration, and one application-private nonblocking same-host `flock`. It neither runs during HTTP startup nor adds a framework schema or migration abstraction. ADR 038 requires an adopting application to state whether any runtime-authority transition is checksum-covered migration work or a separately authorized ordered stage; migration success alone does not prove runtime authority is active. MySQL, PostgreSQL, and every other adoption require their own exact-engine consistency, coordination, authority, recovery, and integration evidence.
