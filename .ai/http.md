# HTTP contract

`Request` and `Response` are immutable values. A handler returns a response; it does not emit output or terminate the process.

Rules:

- Normalize the method and path once in `RequestReader`; do not normalize again in handlers.
- Pass parsed input explicitly. Do not read superglobals in handlers.
- For multipart `POST`, use only the bounded typed `Request::$uploads` map. Require one exact field in an application boundary; never pass raw `$_FILES` or trust client filename, path, media type, or reported size.
- Store normalized request header names as lowercase keys and use explicit array access; do not add a header helper.
- Parse a JSON body once with a concrete `Command::fromJson` factory; reject missing, unknown, and wrongly typed fields.
- Construct the complete final readonly command before downstream operation behavior. When a separate typed operation seam is justified, call it only with that command. Invalid input causes zero seam calls and no operation-owned downstream I/O or mutation; record any protected-request policy work deliberately ordered before parsing.
- Keep validation, deliberate field normalization, output encoding or escaping, and authorization as separate visible decisions; none is a generic input helper.
- Set the outer body limit in the composition root, enforce endpoint-specific limits before decoding, and use `JSON_THROW_ON_ERROR` with an explicit depth.
- Enforce route-specific media types in the handler before parsing or database work.
- For frontend integration, a frontend/API handoff, browser CORS, static assets, or application-owned HTML rendering, follow `docs/frontend-integration.md`. Prefer a separately owned frontend and API exposed through one same-origin reverse proxy when the product permits it; keep operation contracts and frontend evidence application-owned.
- Treat cross-origin browser access as one complete application or deployment policy covering preflight, success, mapped failure, routing-owned `404` and `405`, unknown failure, credentials, cache variation, and exposed response fields including `X-Request-ID`. An explicit `OPTIONS` route or route-local request-handler decorator proves only the paths it can reach; do not add generic CORS middleware or claim partial headers establish complete support.
- Keep optional HTML and static assets application-owned. Encode untrusted output for its exact sink, use only finite code-owned template and asset selection, and install a mature template package only as an explicit pinned application dependency. Add no framework renderer, templating engine, static-file server, OpenAPI or JSON Schema generator, or client generator.
- For every resource identifier, declare the narrowest fixed route type: `positive-int`, `uuid`, or `ulid` for that canonical representation, and `token` only for a genuinely opaque identifier. Read it through the matching `PathParameters::positiveInteger()`, `uuid()`, `ulid()`, or `token()` accessor.
- Immediately wrap the unchanged route value in an application-owned route-specific identifier and enforce any narrower domain rule before database work. Routing performs no normalization, domain binding, record lookup, or type fallback.
- Keep an optional application-owned request-handler decorator inside explicit route-handler composition. It is one final application class implementing only `RequestHandler` around one downstream `RequestHandler`, delegates zero or one time with the exact same immutable `Request` instance, propagates its own and downstream exceptions unchanged, and returns the downstream `Response` unchanged or creates an explicit immutable replacement that preserves every unchanged field. Keep its one narrowly named route concern and bounded side effects visible and tested; do not use it to wrap `Application`, `RequestBoundary`, the terminal coordinator, or `ResponseEmitter`.
- Set status, body, and headers explicitly.
- Keep generic redacted `400 invalid_request` and `422 unprocessable_content` responses as the default. A recorded operation may adopt `docs/errors.md#optional-application-owned-field-issues`; construct that exact bounded response in the operation's explicit pre-I/O branch and keep client decoding and compatibility application-owned. Do not add a generic response wrapper, validation renderer, middleware, or generated schema or client.
- For a new application's successful structured JSON resource representations, follow the advisory application-owned convention in `docs/frontend-integration.md` and `docs/request-handling.md`: one resource uses a top-level `data` object, a collection uses a top-level `data` array including `[]`, and optional operation-owned pagination or other non-resource information uses a top-level `meta` object. Keep every field and continuation semantic operation-specific, keep errors and non-resource representations outside this convention, and do not add a framework or application-wide response wrapper, serializer, resource class, paginator, middleware, helper, discovery mechanism, or generator.
- Nested child objects and collections may appear inside `data` only as explicit operation-owned fields. Give each relationship an operation-specific role name and record the exact nested field set, native types, bounds, ordering, optional object-versus-`null`-versus-absence behavior, whether authorization or tenant scope applies to either role and, where applicable, the exact policy and evidence, data-minimization policy, and compatibility policy. This guidance uses `parent.child` only as neutral relationship notation; it does not prescribe either response field name.
- Write reusable relationship guidance with neutral role vocabulary such as `parent.child`. Domain-specific nouns belong only in explicitly labeled application examples or checked recipes and never become PHPThis conventions.
- Complete every database, cache, and external-service operation before per-resource mapping or JSON encoding. The complete I/O plan remains fixed and bounded independently of parent-page cardinality; mapping, serialization, callbacks, and recursive traversal perform no I/O. `PHT003` rejects direct lexical `Connection` calls inside loops, but it cannot prove that an indirectly called mapper, cache client, or integration is I/O-free, so application-owned scale evidence remains mandatory.
- For an ordinary nested to-one relationship, prefer one explicit bounded join with concrete projections, a uniqueness-preserving join condition, and every operation-owned scope or authorization predicate that applies to either side. A finite batch plan is valid only when its complete statement and other I/O counts are fixed and bounded; never perform one child lookup per parent. Keep parent pagination authoritative and follow `.ai/database.md` and `.ai/testing.md` for fan-out, query-shape, and scale evidence.
- Construct only final `200` through `599` responses. Ordinary responses reject `Transfer-Encoding`; an ordinary content-bearing response may omit `Content-Length`, but any supplied value is the canonical decimal `strlen($body)`. A `204`, `205`, or `304` has an empty ordinary body and no `Content-Length`.
- Keep `HEAD` explicit and application-owned: declare its route and return its empty body without `Content-Length` under the current safe subset. Do not fall back to `GET`, suppress a `GET` body, give the emitter a request, or infer a representation length.
- For `Cache-Control`, validators, or `Vary`, also follow `.ai/cache.md`. PHPThis uses `no-store` on framework-owned 404 and 405 responses, `private, no-store` on the unknown-failure 500, and at least `no-store` on current skeleton/example handlers; protected example outcomes use `private`. It does not automatically inject or replace policy on arbitrary handler responses.
- Represent response cookies only as validated `ResponseCookie` values in `Response::$cookies`; never encode `Set-Cookie` in the ordinary header map.
- Keep every cookie name, value, path, expiration, and security attribute explicit. A name is a non-empty HTTP token; the name and cookie-safe ASCII value together occupy at most 4,096 bytes. `Path` is an absolute 1-to-1,024-byte string using only visible ASCII except semicolon. `expiresAt` is either absent or a Unix timestamp from 1 through the smaller of `PHP_INT_MAX` and 253,402,300,799, so every supported platform serializes a four-digit UTC year; the upper bound is 253,402,300,799 on 64-bit PHP. `maximumAgeSeconds` is either absent or 0 through 34,560,000; zero means immediate deletion, and `Max-Age` is authoritative when both lifetime attributes are present. The application deliberately keeps any accompanying `Expires` fallback coherent with that duration; PHPThis does not read a clock or infer the relationship.
- Apply reserved-name requirements case-insensitively without changing the emitted case-sensitive cookie name. `__Secure-` requires `Secure`; `__Host-` requires `Secure` and `Path=/`; `__Http-` requires `Secure` and `HttpOnly`; and `__Host-Http-` requires all four host and HTTP constraints. Prefer the canonical prefix casing. `SameSite=None` also requires `Secure`.
- Every current `ResponseCookie` is host-only because it cannot express `Domain`. `Domain`, `Partitioned`/CHIPS, and `Priority` are unsupported; a cross-subdomain or embedded third-party requirement needs a separate accepted problem statement and decision.
- A `Response` accepts at most 50 cookies, rejects a repeated case-sensitive cookie name regardless of path, and accepts at most 8,192 aggregate bytes across the exact `ResponseCookie::headerValue()` strings. Cookie names that differ by case remain distinct. Keep deployment-specific total response-header limits separate because field names, framing, ordinary headers, servers, proxies, and clients add their own bytes and limits.
- Encode JSON with `JSON_THROW_ON_ERROR` and set its content type.
- Emit the response only after `RequestBoundary::handle` returns.
- At emitter entry, reject ordinary and local-file responses as `ResponseEmissionFailed(true)` when headers are already sent or any active PHP-managed output-buffer level reports pending bytes. Allow empty active and nested buffers. Inspect every level without flushing, cleaning, rewriting, or incorporating prior bytes, and fail before status, headers, cookies, body, or file access. Treat this as one PHP-reported snapshot; custom output-handler private state, later output, and SAPI, server, proxy, compression, network, or client buffering remain deployment-owned.
- Before emission, preserve the application-owned ADR 023 coordinator's generated `X-Request-ID` and one failure-isolated terminal sink attempt. Do not add this behavior to `RequestBoundary`, `ResponseEmitter`, an application-owned request-handler decorator, generic or framework middleware, or a global logger.
- For a local file, use only `LocalFileBody` with an application-resolved absolute path and expected bytes. Keep the ordinary body empty, set exact `Content-Length` and representation headers in the handler, preserve the file body through response copies, and let the emitter verify and stream fixed chunks.
- Keep range handling deferred: emit the complete `200` representation with `Accept-Ranges: none`; do not add `206`, `Content-Range`, or range parsing.
- Handle `ResponseEmissionFailed` only at the visible front controller after terminal response selection. Only `ResponseEmissionFailed(false)` may receive one generic fallback; pending-buffer, already-sent-header, and post-header failures report `true` and cannot receive a replacement response.
- Treat redirects and non-local or callback streams as future explicit response types, not array conventions.

ADR 021's Create proof uses the application-owned `CreateUserOperation` seam and `TransactionalCreateUser` as the concrete operation directly owning that transaction's complete SQL, without adding a framework input, query object, helper, or service API. ADR 026 adds the narrow file-transfer values; ADR 053 adds no core HTTP or storage value. ADR 032 adds fixed canonical UUID and ULID route types without binding behavior or a runtime identifier dependency. ADR 033 and Consumer Contract v9 permit only the bounded application-owned request-handler decorator above and leave Strict Profile v2 unchanged. ADR 045 adds the bounded ordinary-response framing above; ADR 049 adds the bounded response-cookie profile; ADR 060 adds the pending-output preflight; current Consumer Contract v17 carries version 16 and Strict Profile v4 forward. ADR 056's raw request-target and path byte exclusion remains runtime contract behavior routed through `.ai/request-boundary.md` and `.ai/routing.md`, not part of PHT008.
