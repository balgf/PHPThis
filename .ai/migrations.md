# Migration authoring contract

Read [ADR 043](../docs/decisions/043-engine-specific-application-migration-invariants.md), [ADR 027](../docs/decisions/027-application-owned-explicit-sqlite-migrations.md) when the SQLite reference proof applies, ADR 038, ADR 039, [Explicit application migrations](../docs/migrations.md), `.ai/database.md`, `.ai/cli.md`, and `.ai/testing.md` before adding or changing a migration.

PHPThis provides no core migration API. ADR 043 defines engine-neutral application-owned invariants; ADR 027 remains one accepted SQLite-specific reference proof.

Rules:

- Treat migrations as specialized application-owned database evolution. For a new adopting application, recommend `src/Database/Migrations/` with a matching namespace such as `App\Database\Migrations`; record the actual source path and namespace in the application's `.ai/migrations.md`.
- Accept any coherent application-owned alternative. Do not reject an alternative location, enforce paths through the checker, derive executable work from placement, create an empty migration directory for a database-free skeleton, or silently relocate established source. A relocation is an application architecture change requiring explicit human approval.
- When multiple named database connections own separately tracked migration histories, keep one application console executable but require each history to record its own stable name, engine/version decision, finite explicit command, migration source, namespace, coordinator, manifest, ledger, atomicity, coordination, recovery, output, per-history compatibility and handoff constraints, typed-configuration/process-identity reference to `.ai/configuration.md`, database-authority reference to `.ai/data.md`, and evidence boundary. `.ai/operations.md` alone owns the application-wide release sequence. No policy, configuration value, credential, or fallback inherits implicitly. Never combine migration credentials or let one history obtain another's identity/configuration. Each pair of histories must prove disjoint managed objects, data, authority transitions, and coordination domains or share explicit serialization, release, and recovery ownership with cross-history partial-deployment evidence. Permit an application-selected connection-owned subdivision only for those adopted histories; do not prescribe or scaffold speculative subdivisions for a single-database application.
- Do not infer a generic `Database/Queries` directory, repository layer, or alternate SQL execution boundary from the recommended migration directory. Runtime SQL stays in its handler or the one justified narrowly named concrete operation.
- Keep the finite migration command or commands on the application's sole console executable. Give each separately tracked history one explicit command owner and never run any migration command during HTTP startup or through framework `bin/phpthis`.
- Record the exact engine and supported version plus its accepted database/catalog/schema/attachment namespace model, namespace and object control-or-ownership or non-applicability, DDL, authority, coordination, recovery, and integration decision. For each history, record one exact initial baseline. It may be empty, include pre-provisioned database, namespace, role or identity, and coordination objects, or include a separately reviewed existing schema, data state, or ledger prefix whose exact structure and assumptions are proved. Enumerate every accepted present object, data assumption, ledger row, and checksum plus every application-managed object or history entry that must be absent; never infer or manufacture a ledger prefix. Require `.ai/data.md` to own exact required and prohibited capabilities, supported isolation or applicable file/process authority overlap and residual risk, accountable transition ownership, and authority evidence; retain stable references here. Keep elevated migration configuration and its process-entry path unavailable to HTTP through `.ai/configuration.md` in every engine.
- Keep the selected authority-transition implementation source and complete non-HTTP implementation path here. Record whether complete engine-specific `GRANT` or `REVOKE` SQL, when supported and selected, is visible and checksum-covered in a migration, a separately authorized application stage owns the transition, or a named external provisioning source owns it; never leave activation implicit or run it through HTTP.
- Keep one final concrete coordinator, one finite ordered source manifest, and one bounded ledger per separately tracked history, with unrolled private migration-step methods. Do not scan files, discover classes, resolve strings, or load runtime `.sql` files.
- Give every migration one permanent bounded identifier, complete engine-specific compile-time-constant statements, direct `Connection` calls, explicit unique named bindings where data exists, and a SHA-256 checksum covering the identifier, every statement, every code-owned binding name/type/literal value or finite binding-derivation policy, and every exact ordered application effect, including DDL, data, and authority changes. Unreviewed deployment environment, command, or network input never changes a migration binding.
- Require each bounded ledger to store position, identifier, and checksum. Any selected extra metadata, including a timestamp, is engine-specific and must have an explicit source, representation, and bound; be parsed and validated as non-executable data; and never select work, define order, or grant authority. Record a finite exact-engine metadata acceptance policy for the ledger and any explicitly permitted supporting objects; reject a missing, incompatible, or additional unrecorded ledger-related object before history parsing or pending work. The applicable coordination or serialization mechanism must become effective before ledger bootstrap or creation plus authoritative definition, complete-history, and applied-checksum validation, and must remain effective through all checksum-covered migration effects and either accepted ledger completion or a finite fail-closed failure outcome. Never record a partial state as applied. Detected coordination loss stops before the next mutation. When ownership can expire or be lost, a successor must not mutate until prior in-flight database work is fenced, the prior session/work is confirmed invalidated or terminated, or another proved exact-engine exclusion boundary establishes termination; a post-statement check or exited client alone is insufficient. After loss or process termination, the next owner reacquires coordination, re-detects exact state, and only then may perform a later mutation. Reject overflow, unknown, duplicate, missing, reordered, malformed, or edited history without silent repair.
- Record the selected engine/version's transaction behavior and DDL atomicity limits. Define how each migration's effects and ledger record remain consistent across success, failure, process termination, and any non-transactional DDL boundary; do not claim atomicity the engine cannot provide.
- Never call a database method in a loop, infer a down migration, execute a stored class or SQL value, hide transaction ownership in a callback, or retry implicitly.
- For every supported topology from which a migration writer can run, record one explicit coordination or serialization mechanism: application-local, database/server-owned, deployment-owned, or a named external coordinator. Record its stable identifier and namespace, collision boundary, exact creation, acquisition, use, and release permissions or authority, owner, scope, contention and acquisition-failure behavior, expiry or loss behavior, process/session termination behavior, and exact hosts or runners covered. Concurrently reachable topologies for the same history must share one exclusion domain or be pairwise authority-gated so their migration identities/configurations cannot be active together; prove every reachable cross-topology pair. Its ownership begins before ledger bootstrap or creation plus authoritative definition/history validation and extends through every checksum-covered effect and either accepted ledger completion or a finite fail-closed failure outcome. Do not treat a same-host file lock as distributed coordination or assume one topology's proof covers another.
- Use a fresh migration connection with an explicit finite budget and bounded trace. When the engine-specific ledger selects a timestamp field, its explicit value may use an engine expression such as the SQLite example's `unixepoch()` or an application-supplied value, but never a hidden default.
- Record finite stable success names, nonzero failure names, exact exit status, and exact stdout/stderr bytes for the application. Never emit paths, DSNs, credentials, SQL, bindings, exception details, ledger contents, schema contents, or application data. The `applied` and `up_to_date` success names belong to the ADR 027 SQLite example only; another adoption does not inherit them.
- Record how every partial state is detected before later work, which states stop safely, and the application-owned forward migration or other accepted recovery for each state. Applied history remains immutable. Backup restoration or another recovery mutation requires separate explicit human authorization.
- Record only each history's engine-specific compatibility, authority-verification, failure-stop, and handoff constraints, then reference the application-wide sequence in `.ai/operations.md`; do not duplicate that sequence here. Required authority still precedes dependent traffic, and dependent code is removed or drained before its authority or required namespace is deactivated.
- If the application deliberately adopts ADR 027's SQLite reference shape, execute each pending migration and its ledger insert in one explicit transaction, commit inside `try`, roll back in `finally` only while active, preserve earlier commits after a later failure, hold one application-private nonblocking exclusive same-host `flock` around database work with release in `finally`, retain its stricter SQLite ledger-definition proof, and use its `applied` or `up_to_date` success names. These are conditional SQLite/example and host-topology mechanics, not engine-neutral requirements.
- Keep every engine outside evidence that did not exercise its exact version and topology. MySQL, PostgreSQL, and other engines require their own transaction and DDL atomicity limits, ledger-consistency design, coordination, privilege, partial-failure recovery, and integration evidence.

Evidence must cover each history's exact recorded initial baseline, deterministic order, accepted-ledger-prefix validation, every pending checksum-covered statement, code-owned binding value or finite binding-derivation policy, and DDL/data/authority effect; exact position/identifier/checksum ledger; every selected extra metadata field's source, representation, bound, validation, and non-authoritative use; no-op rerun; binding/policy and statement drift rejection before further work; finite exact-engine ledger-metadata acceptance; rejection of incompatible or additional unrecorded ledger-related objects before history parsing or pending work; malformed and overflowing ledger; exact transaction and DDL atomicity limits; ledger consistency at each failure boundary; partial-failure detection and forward recovery; exact CLI bytes and redaction; no HTTP migration or authority-transition path; and the complete project gate against that history's exact engine and version. This compatibility proof uses the selected engine's safe metadata or catalog mechanism and does not inherit SQLite byte-for-byte definition comparison. For every application-local or database/server writer topology, concurrent real-console processes prove the concrete coordination mechanism, stable identifier/namespace, collision isolation, permissions, and protected interval. Evidence covers every concurrently reachable cross-topology pair through shared exclusion or pairwise authority gating. An expiring or lost owner is fenced from later mutations or confirmed terminated with no in-flight work before successor mutation. Evidence proves no partial state is recorded as applied, detected coordination loss stops before the next mutation, and the next owner reacquires coordination and re-detects exact state before mutating. Deployment or external serialization is proven at that owning boundary, including that bypassing it cannot obtain the history's migration identity or configuration. Every separately tracked history proves its engine/version decision, finite explicit command, separate configuration factory/final readonly type/process identity without fallback or combined credentials, and disjoint managed objects, data, authority transitions, and coordination domains or shared serialization/release/recovery with cross-history partial-deployment evidence. An ADR 027 SQLite adoption additionally proves its stricter ledger definition, nonblocking same-host `flock` contention and cleanup, active-transaction rollback, earlier committed migrations preserved, and forward continuation. For every adopted transition, execute each intended statement under the runtime identity before traffic, safely verify selected prohibited namespace, DDL, identity or role, authority-management, administrative, migration-ledger, and unrelated-object actions against the exact engine and version, record the engine's actual effective-authority resolution, and prove HTTP cannot obtain elevated configuration.
