# Terminal request-summary contract

Start ordinary request-correlation or operational-summary work with `docs/logging.md` and this current guide. Read ADR 023 only when reviewing or changing its terminal request-summary decision.

Rules:

- Keep the coordinator, event construction, and sink application-owned and explicitly wired at the front-controller composition boundary. Do not move any part into an application-owned request-handler decorator. Add no core event, sink, coordinator, logger, generic or framework middleware, facade, helper, discovery mechanism, or hidden instrumentation.
- Generate 128 random bits during request-scoped composition before bounded request ingestion and encode exactly 32 lowercase hexadecimal characters. Propagate that value as `correlation_id` and the single `X-Request-ID` response header; never echo an arbitrary incoming identifier.
- Preserve ADR 023's mandatory closed version-1 `application.request_summary` schema with monotonic duration, selected response status, generic outcome, nullable class-only unknown failure, aggregate query evidence, and at most eight finite code-owned database sources. The executable Redis example alone advances to version `2`, preserving those fields and adding exactly one bounded `document_cache` snapshot from `DocumentDetailsCacheTrace`; the health-only skeleton remains version `1`.
- Give each source a bounded lower-ASCII label, explicit `QueryBudget`, and distinct bounded `QueryTrace`. Preserve raw engine-specific SQL and explicit named parameter arrays at direct `Connection` call sites; do not add an ORM or binding helper to produce observability.
- Known denials have only the generic known-failure outcome and selected status. Named unknown failures contribute only their concrete class; anonymous throwables use the nearest named parent because their runtime class name embeds source location. Omit every request, credential, domain, response-body, SQL, binding, DSN, driver, message, source-location, and stack value.
- Make exactly one sink invocation attempt after the response and event are fixed. Cache and lease operations add no separate log write. Swallow sink failure without retry, fallback, another event, or response mutation. Never claim durable delivery or successful response emission.

Tests cover success, mapped failure, known denial where applicable, unknown failure, identifier grammar and propagation, zero and multiple sources, duplicate-query aggregation, budget overrun, trace truncation, complete redaction, exactly one invocation attempt, and a throwing sink that leaves the response unchanged. The Redis proof also covers the exact version-2 `document_cache` shape and all finite cache outcomes without keys, values, identities, endpoints, credentials, or exception details.

## Optional ADR 051 operational log-record profile

ADR 051 accepts the optional application-owned operational log-record profile in `docs/observability/log-levels.md`, `docs/observability/destination-record.md`, and `docs/observability/destination-profiles.md`. While adopting or reviewing it:

- Preserve Consumer Contract version 12 and the exact accepted request-summary version-1 and Redis-proof version-2 objects. Do not add timestamp or level fields to either summary.
- Keep the exact destination envelope at `record_schema_version`, `occurred_at`, `level`, then `summary`, with UTC microseconds and a complete encoded-record bound of 65,536 bytes including LF.
- Keep the checked `RequestSummaryDestinationRecord` reference limited to final encoding of the existing concrete summary. It is not a logger, sink port, writer, clock abstraction, file or stream implementation, collector, or delivery proof.
- Keep timestamp creation, HTTP level derivation, encoding, bound enforcement, and destination I/O inside the existing one sink attempt. Preserve no retry, fallback, duplicate record, response mutation, or durable-delivery claim.
- Keep the finite levels exactly `debug`, `info`, `warning`, `error`, and `critical`. For HTTP, derive `error` first for unknown failure or status at least `500`, otherwise `warning` for observed query failure or budget rejection, otherwise `info`; HTTP uses neither `debug` nor `critical`.
- Keep the checked encoder as the sole HTTP level-map owner and emit one `info`, `warning`, or `error` record for every valid summary before the selected destination write. Add no configurable HTTP minimum level, generic threshold API, sink-owned duplicate map, or suppression path.
- Keep every other process summary, level map, and emission policy finite, code-owned, closed, and application-specific. A named `debug` event is emitted only under that process's recorded policy. Do not introduce arbitrary message/context input or a framework or generic application logger, enum, helper, facade, middleware, event bus, discovery mechanism, or runtime dependency.
- Before adoption, prove the worst-case valid record fits 65,536 bytes including LF from the exact maximum source count, each source's selected `QueryTrace` fingerprint-retention limit, every closed summary extension, JSON escaping, and encoder overhead. Keep post-encode rejection as defense, not as the sizing policy.
- Select one application destination: one recorded stdout/stderr stream or one dedicated daily-file policy. For a local file, recommend `<project-root>/var/log/application.jsonl`, generated inside the checkout but outside the public document root, never committed, and ignored by the exact project-root `.gitignore` pattern `/var/log/` (not the host `/var/log` directory). Require typed configuration to resolve the destination to an absolute path and record the exact project-root command `tail -F var/log/application.jsonl`. For a host or virtual machine, recommend `/var/log/<application>/application.jsonl` or an equivalent dedicated persistent mount, where `<application>` is one static non-sensitive deployment identifier. For a container, prefer the selected stdout or stderr profile over its ephemeral writable layer.
- For a file, keep one stable active filename and external UTC daily rotation as the preferred starting point. Deployment pre-creates the trusted parent directory and active regular non-symlink file; the application runtime and HTTP request path never create or repair the directory or call `mkdir`, `touch`, `chmod`, or `chown` for the destination. Recommend POSIX directory mode `0750` and file mode `0640` only when one writer identity and one collector group match that topology; otherwise require an explicit least-privilege ownership and access policy. `tail -F` is human inspection that follows path replacement, not evidence that a writer reopened or a collector delivered a record.
- Keep file location, UTC rollover, permissions, writer topology, append/lock and partial-write semantics, rotation/reopen, retention, delayed compression, deletion, quota, inode/read-only/disk-full behavior, tail workflow, and collector lag application and deployment facts. Do not present the shared deployment-configured PHP error log as pure JSONL.
- Keep Grafana delivery downstream: selected destination to Grafana Alloy to Loki or Grafana Cloud Logs to Grafana. Do not contact a remote log service synchronously in the request path. Keep credentials in collector configuration. Default indexed labels to stable service, environment, and static deployment dimensions; a finite static process role such as `web`, `worker`, or `scheduler` may be a measured bounded dimension, while dynamic process identifiers, PIDs, replicas, correlation, request, user, tenant, resource, path, SQL fingerprint, and other per-record identifiers are never labels. Retain level and event in JSON or bounded structured metadata until measured query/volume/cardinality evidence justifies stream splitting. Record the selected tenant/account reference, remote retention/deletion, region/data residency, access owner, and incident owner as application and deployment facts.

Absent deliberate application adoption, do not change the existing error-log sink, skeleton runtime, example runtime, source dependencies, Contract/Profile, or current proof claims to present this optional profile as implemented behavior.
