# File-transfer contract

Start ordinary multipart-upload, local-file-response, or accepted Amazon S3 profile work with `docs/file-transfers/README.md` and this current guide. Read ADR 026 or ADR 053 only when reviewing or changing the decision itself. Keep transport normalization in core and every storage decision in the application.

For optional checked media inspection, select `docs/file-transfers/inspected-png.md`, `docs/file-transfers/inspected-jpeg.md`, `docs/file-transfers/inspected-mp4.md`, or `docs/file-transfers/inspected-wav.md` and the shared catalog reference's named application policy/source/evidence. Its narrow `INSPECTED_CONTENT` recipe does not change the existing opaque example, starter non-adoption or storage profiles.

## Multipart request path

Follow `docs/file-transfers/request-ingestion.md` for the current API, limits and failures. The sole front controller passes only server/query arrays; `RequestReader` performs one explicit native parse inside `RequestBoundary`, before session begin or handler dispatch. A `null` multipart limit disables multipart input.

- Adopt immutable `MultipartLimits` explicitly; require effective automatic POST parsing off, native uploads on and no earlier body reader. Never fall back to automatically parsed arrays.
- Record all request/file/field byte ceilings. Optional `maximumFieldBytes` and `maximumTotalFieldBytes` retain 8,192/65,536 defaults; names count toward the aggregate. Follow the ingestion guide's positive finite configuration relationships and verify changed limits through the target SAPI before adoption.
- Receive immutable `MultipartForm` on `Request::$multipart`; its flat string fields and typed uploads use the exact bounded grammar. Preserve it through routing. Parse the complete permitted field/file set into one operation value and handle every upload error before operation I/O.
- Treat client filename/media type as hostile metadata; validate then discard full_path. Verify provenance and actual size separately. Unknown native upload errors remain operational failures.
- Native count/request limit exceptions reject the entire parse. PHP still collapses scalar duplicates, normalizes names and can discard malformed parts or accept a missing closing boundary. Record whether that normalized-input contract suits each operation; a stronger requirement needs separately verified upstream strict validation.

## Pre-PHP ingress policy

Record dated effective settings and first rejection owners using `docs/file-transfers/deployment.md`: server/proxy buffering, bytes, timeouts and rate/concurrency; PHP automatic parsing, uploads, explicit parser options, temporary storage, filters, encoding, upload progress and applicable execution/input limits. Verify them through the target SAPI. Normalized aggregate sizes exclude overwritten/discarded parts; raw resource bounds are separate. An application response test cannot certify a proxy or PHP rejection before the front controller.

## Application-owned local upload policy

The move, durable-root, and local-emitter rules in this section are the unchanged `LOCAL_ADR026` profile. `AMAZON_S3_ADR053` reuses the common multipart and request-policy rules but follows the exact accepted S3 route below instead of these local-storage rules.

- Require one exact field name and explicit inclusive minimum and maximum file bytes before storage, including whether zero-byte files are accepted. The example uses `document`, a 2 MiB total multipart transport limit, and accepts 0 through 1,048,576 file bytes inclusive.
- Do not infer content from the client media type or filename. If content classification is required, add an application-owned inspected-content decision and evidence.
- Record either `OPAQUE_BYTES` or `INSPECTED_CONTENT`. Opaque bytes use fixed code-owned stored and download names, are never parsed or served as active content, and download only as `application/octet-stream` attachment with `nosniff`, explicit cache policy, and the operation's recorded authentication/authorization policy. This posture does not certify content safety, absence of malware, or downstream-parser safety. Inspected content records one versioned inspection definition: exact accepted formats, byte-derived detection, parser or scanner and pinned version/configuration/signatures, isolation, timeout, memory, nesting or decompression bounds, update owner, failure and quarantine behavior, and executable fixtures; client metadata is never the classifier. Pending, scanner-error, rejected, and quarantined states are non-serving until one recorded accepted promotion. Define which tool, configuration, signature, format-allowlist, or application-policy changes create a new inspection definition. For every such change, record whether retained bytes are re-inspected or remain under their earlier definition; when reinspection is required, name the bounded selection, ordering, rate, retry, non-serving state, result transition, accepted promotion, completion evidence, and failure-recovery owner. An external inspector additionally requires exact third-party data processing, byte retention/deletion, residency, authenticated transport, least credential and rotation, timeout, ambiguous-failure, retry, and duplicate-submission decisions.
- For every protected upload, keep `authenticate -> resolve tenant when applicable -> authorize upload -> validate CSRF when applicable -> admission -> quota reservation -> storage` visible, and stop before every later step on failure. Bind retained metadata and storage identity to the applicable tenant, owner or principal, and named upload/download authorization action; record each inapplicable dimension explicitly. For cookie-authenticated state-changing uploads, `SameSite` is not a substitute for the exact CSRF mechanism. A protected download authorizes its named action before lookup when existence is confidential. Record explicit not-applicable facts for public, non-browser, stateless, tenant-free, owner-free, or CSRF-free operations rather than implying protection.
- Verify `is_uploaded_file`, read the actual size, and require it to equal the reported size before calling the one narrowly named storage operation. The PHP temporary path is request-scoped input only: never persist, enqueue, log, trace, or reuse it after that request. Durable work stores only the application-owned destination or bounded reference established after a successful move.
- Generate the storage identifier and destination server-side. Keep the root outside the public tree with explicit directory and file permissions.
- Use `move_uploaded_file` visibly. Before a successful move PHP owns temporary cleanup; after it, the application owns retention, deletion, backup, and incident handling.
- Record a dedicated effective web-SAPI `upload_tmp_dir` and separate durable-storage root. For the temporary root, name the non-root request identity, owner, group, exact ACL or explicit `NONE`, modes, no-execute/non-public mount semantics, capacity and inode bounds plus monitoring and alert ownership, request-termination cleanup, bounded stale-file policy, and container or multi-host visibility. Deployment or test setup pre-creates the durable root before HTTP handling with its exact owner, group, ACL-or-`NONE`, modes, local-versus-network/mount semantics, unrelated-writer exclusion, capacity/inode monitoring, and topology; the request identity has no authority or need to create, chmod, chown, repair, or replace that root. Neither root is an application release directory; neither becomes executable or directly web-served. After moving, recheck regular non-symlink type, exact accepted byte count, and permissions before publishing an identifier. If byte identity or integrity is claimed, record the exact digest algorithm, computation point, trusted stored representation, verification points, mismatch behavior, update/reinspection interaction, retention, deletion, backup/restore, and algorithm-transition lifecycle; size alone is not integrity.
- Record per-request and applicable principal, tenant, object, deployment, egress, byte, count, rate, and aggregate-capacity quotas; the atomic reservation/concurrency rule; the generic failure; and which ingress, application, storage, or scheduled operation owns enforcement. Record retry, idempotency and duplicate-request policy, including an ambiguous client response after a completed move. Record deterministic outcomes and recovery ownership for move failure, response/emission failure, process crash, disk full, inode exhaustion, permission failure, and partial cleanup. Record retention start, expiry, deletion, orphan and partial-write recovery, one named bounded reconciliation path, deletion propagation to replicas and backups, restore interaction, legal hold, and incident owners, including what happens when cleanup or quota accounting fails.
- Do not add a generic storage interface, facade, disk registry, binding helper, automatic persistence, or hidden cleanup.

## Local-file response path

- The application resolves one bounded absolute regular-file path and expected byte count into `LocalFileBody`; it does not pass a client filename or storage identifier to the emitter.
- The current path-only profile requires one application/deployment storage invariant from authorized selection through completed emission: the selected pathname and bytes remain immutable under exclusive-writer authority, with no replacement, mutation, unlink, relink, or symlink substitution. A digest is additional integrity evidence only and cannot replace this invariant. An identity-bound body, open-handle body, or different response primitive requires a separately accepted core/response decision.
- A file `Response` has an empty string body, exact canonical `Content-Length`, no `Transfer-Encoding` or `Content-Range`, and a status supported by the concrete full-response contract.
- Set `Content-Type`, code-owned `Content-Disposition`, cache policy, `X-Content-Type-Options`, and `Accept-Ranges: none` explicitly in the handler.
- Before file access, `ResponseEmitter` applies the common response-output guard: already-sent headers or pending bytes in any active PHP-managed output-buffer level fail as `ResponseEmissionFailed(true)`, while all-empty active and nested buffers remain valid. It inspects without cleaning, flushing, rewriting, or incorporating prior bytes. It then opens and checks the regular file before headers, verifies the expected length, emits fixed 8,192-byte chunks, and closes in `finally`.
- A pre-header `ResponseEmissionFailed(false)` may select one generic fallback at the front controller. After headers, do not attempt a replacement response; the declared length exposes truncation to the client.
- Ignore `Range` and return the complete `200` response. Do not add `206`, `Content-Range`, or range parsing without a new accepted decision.

### Exact emitter guarantee

For the opened handle, the emitter checks regular-file type and exact expected size before starting the response, then attempts one sequential pass of no more than 8,192 bytes per read. It either echoes exactly the declared byte count or throws `ResponseEmissionFailed`; it never intentionally emits beyond that count, retries the transfer, or selects a second response after headers. The emitter guarantees neither immutable content after the pre-header `fstat`, an integrity digest, client receipt, durable delivery, nor bounded buffering in PHP, the web server, proxy, TLS terminator, kernel, or client. The mandatory path-only immutability/exclusive-writer invariant above is application/deployment policy, not an emitter guarantee; a pre-emission digest cannot prevent a later same-size swap.

## Required evidence

Prove the typed runtime shape, every `RequestUploadError`, missing, nested, multiple named uploads, mixed/text-only fields, raw-scalar-duplicate and malformed-part limitations with their suitability decision, wrong-media, oversized, unsafe-metadata, provenance, actual-size, move, permission, missing-file, framing, header-control, duplicate-header, pre-header emission failure, complete-byte, full-range-request, and fixed-chunk paths that the application claims. Include a real SAPI request with output written directly to a file, the exact dated effective pre-PHP settings including `max_multipart_body_parts`, and state any uninjectable filesystem/read failures plus PHP, web-server, proxy, buffering, content inspection, quota, lifecycle, request-policy, authorization, tenant, CSRF, and topology limits that remain unproved.

For a protected operation, prove unauthenticated, forbidden, cross-tenant, permitted, unexpected-policy-failure, and applicable CSRF outcomes with no storage lookup or mutation after a denial. Prove temporary and durable root isolation, quota boundaries and concurrent reservation behavior, lifecycle and cleanup outcomes, and every claimed opaque or inspected-content path against the actual selected definition, tools, and versions. `INSPECTED_CONTENT` evidence additionally changes each recorded definition input and proves the exact retained-byte reinspection or explicit no-reinspection policy, bounded progress, availability/quarantine behavior, result transition, and recovery. Static context checks can require the application record and markers; only application-owned behavior, integration, and deployment tests prove the selected mechanisms.

Do not introduce an ORM, automatic binding, discovery, generic helper, image processing, MIME or filename trust, automatic cleanup, or a range implementation while changing this path.

## Accepted Amazon S3 profile route

Accepted ADR 053, `docs/file-transfers/amazon-s3.md`, and `docs/file-transfers/amazon-s3-verification.md` define the optional `AMAZON_S3_ADR053` profile under Consumer Contract version 13. An application deliberately selects that exact profile in this one policy owner and completes its static, behavior, isolated real-AWS, dated deployment, and complete-gate evidence. Packaged guidance or the synthetic framework reference proof alone cannot establish adoption.

For a generic "may switch?" review, inspect `tools/test-consumer-project/amazon-s3-file-transfers.php` as the nearest framework test of the synthetic installed-reference proof. Its direct caller is `tools/test-consumer-project.php` at `proveInstalledAmazonS3FileTransferVerificationReference(...)`; inspect those named sites without searching other test families for consumer implementation. The exact checker source in `docs/file-transfers/amazon-s3-verification.md` is a template for the adopting application's `tools/verify-amazon-s3-file-transfer-source.php`, not a checker installed in PHPThis. Its manifest, concrete S3 operation sources, behavior tests, real-AWS test, and deployment verifier belong to that consumer. Without those consumer files and results, answer conditionally from the accepted profile; do not claim that a particular consumer has adopted or proved it.

The profile keeps this file as the sole application policy owner and adds no `.ai/s3.md`, framework AWS dependency, client, storage abstraction, presigner, lifecycle service, or checker rule. S3 cannot add `X-Content-Type-Options: nosniff` to its direct response; Contract version 13 accepts fixed `application/octet-stream` attachment delivery without that header only as this profile's narrow exception, while `LOCAL_ADR026` remains unchanged. The finite profile pins Put `StorageClass: STANDARD`, absent HeadObject storage/archive indicators, no S3 Lifecycle rule/action whose filter can cover `private-documents/v1/`, and CloudTrail S3 data-event coverage for `PutObject`, `HeadObject`, `ListObjectVersions`, `GetObject`, and `DeleteObject`. The framework reference remains a synthetic non-adopter marked `NOT_APPLICABLE(FILE_TRANSFER)` plus `REFERENCE_ONLY(AMAZON_S3_FILE_TRANSFER_VERIFICATION_STRUCTURE)`.
