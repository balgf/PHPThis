# Request boundary contract

`RequestBoundary` is the one framework transport boundary. The application-owned terminal coordinator wraps it without becoming framework middleware. `RequestBoundary` calls `RequestReader`, optionally begins one `SessionLifecycle`, delegates the resulting immutable request to one `RequestHandler`, and consults `ErrorResponseRegistry` only when a failure crosses that path.

Rules:

- Read PHP superglobals only in `example/public/index.php`, pass `$_SERVER`, `$_GET`, `$_POST`, and `$_FILES` explicitly to the application-owned terminal coordinator, and let it call the one bounded `RequestBoundary`.
- Configure the maximum body bytes, `php://input` URI, and optional separate multipart request bytes explicitly in the composition root. A `null` multipart limit disables multipart input.
- Keep the fixed metadata bounds: 8,192 request-target bytes, 64 top-level query parameters, 64 headers, and 8,192 bytes per header value.
- Validate the complete raw `REQUEST_URI`, including its query suffix, before splitting at the first `?`. In addition to the 8,192-byte bound and existing fragment rejection, reject exactly raw bytes `0x00` through `0x20` and `0x7F` with `REQUEST_URI has an invalid or oversized request-target representation.`
- After that validation, strip only the query suffix and require a non-empty path beginning with `/`. Do not URL-decode or otherwise reinterpret percent spellings, collapse slashes, resolve dot segments, rewrite backslashes, reject high bytes through a new allowlist, or reinterpret an absolute URI.
- Normalize CGI header names once to lowercase hyphenated names. Collapse identical CGI/HTTP duplicates, but reject conflicting collisions, non-string values, control bytes, and invalid tokens.
- Preserve query values as `mixed`; an endpoint-specific named boundary must parse any values it uses.
- Accept parsed multipart input only for `POST` with one bounded boundary parameter, canonical `Content-Length`, no `Transfer-Encoding`, no text fields, and at most one normalized flat file. Normalize it once to `RequestUpload`, preserve it through routing, validate then discard client `full_path`, and keep filename and media type conspicuously untrusted. PHP has already collapsed duplicate raw scalar parts; do not claim they were rejected.
- Keep error registration literal and exact-class-only. Unknown failures must be rethrown to the application-owned terminal coordinator, which retains its current generic-response and summary behavior.
- When the application-owned terminal coordinator catches an unknown failure, retain it only long enough to record its ADR 023 safe class and call `UnknownFailureBoundary::respond()` without passing the failure to select the generic 500 response.
- Under Contract version 18, the sole supported HTTP front controller loads ordinary Composer autoloading and the generic-boundary types, constructs the exact generic response, then establishes one application-owned `Throwable` catch around configuration, bootstrap, composition, and coordinator invocation. Select the already-constructed generic response before protected outer-event or detailed-renderer attempts; renderer failure remains generic. Keep response emission outside under its separate `ResponseEmissionFailed` catch.
- Do not extend development details into a failure the terminal coordinator has already converted. A pre-coordinator failure has no `X-Request-ID` or terminal-summary guarantee. An alternate deployed HTTP adapter is ineligible pending a separate accepted decision.
- When sessions are configured, call `SessionLifecycle::begin` only after successful request parsing, finish normal and registered-error responses, and abort before rethrowing an unknown failure.
- Beginning a lifecycle records the cookie header only. Do not start native storage or emit a cookie unless application code explicitly reads or mutates session state.
- A protected matched route may delegate to one application-owned action-specific request-policy adapter. That adapter executes authentication, tenant resolution, and authorization inside the explicit handler path; it does not change `RequestBoundary`, `Application`, `Request`, or the routing contract.
- A matched route may hold an application-owned request-handler decorator only as its explicitly constructed handler object. That decorator receives the immutable `Request` downstream of `Application`; it does not wrap, replace, configure, or take ownership from `Application`, this `RequestBoundary`, the terminal coordinator, or `ResponseEmitter`.

Do not put session, principal, tenant, or authorization state on `Request` or turn this boundary into generic or framework middleware, an event pipeline, a request helper bag, automatic input binding, a policy registry, a service locator, a storage facade, or automatic file persistence.

ADR 023 changes no `RequestBoundary` observability responsibility. The application front-controller path around it owns generated correlation, `X-Request-ID`, finite budget/trace observation, the terminal event, and one failure-isolated sink invocation attempt. ADR 061 adds only the separate generic-first outer HTTP failure boundary before coordinator availability; do not move it, its optional details, or its outer event into `RequestBoundary`, the coordinator, or framework core. ADR 026 only adds explicit parsed multipart arguments and typed normalization. Read `.ai/observability.md`; do not move terminal evidence into the framework boundary or `Connection`.
