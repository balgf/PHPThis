# Application AI context contract

This guide applies when changing `docs/consumer-contract.md`, `docs/knowledge-map.md`, `docs/getting-started.md`, `docs/configuration.md`, `docs/crud.md`, `docs/caching.md`, `docs/coordination.md`, `docs/jobs.md`, `docs/cli.md`, `docs/migrations.md`, `docs/websockets.md`, `docs/frontend-integration.md`, `docs/email.md`, `docs/workbench.md`, `docs/file-transfers/`, `docs/logging.md`, `docs/observability/`, `RELEASING.md`, `templates/application/`, `skeleton/`, or any accepted decision that changes application AI context or task routing. ADR 009, ADR 011, ADR 013, and ADR 044 are the primary ownership and routing decisions; concern-specific decisions remain conditional context for their own guides.

ADR 054 and `v0.1.0-alpha.7` define the latest immutable framework tag and source boundary. That boundary carries ADR 041 through ADR 046 and the other accepted Alpha 6 behavior forward, adds ADRs 048 through 054 in Consumer Contract version 13, and retains Strict Profile version 3, diagnostics `PHT001` through `PHT007`, and the readable 2,618-line core under the accepted 2,620-line ceiling. Issue #53 records both exact Alpha 7 candidates, required CI, both immutable tags and Packagist versions, and the clean Packagist-only public-distribution proof. Alpha 7 remains an unannounced partial coordinated release until both GitHub prereleases and the final announcement are separately authorized and recorded; Alpha 6 remains the latest fully completed and announced coordinated release. The `PENDING` candidate values and non-authority statements in ADR 054, the tagged Alpha 7 source-preparation notes, and the approved Alpha 7 source-preparation subsection in `RELEASING.md` are preserved acceptance-time history, not current publication state. The post-tag `main` change is mutable release-state documentation and its guardrail mirrors only; it changes no framework runtime, Consumer Contract, Strict Profile, diagnostic, dependency, candidate, tag, or published package. Release preparation, exact-candidate approval and proof, partial-publication recovery, publication, and exact-tag historical inspection follow their distinct routes in `RELEASING.md`.

Rules:

- Keep the framework-maintainer `AGENTS.md` and `.ai/` separate from the application template.
- Keep one routed current owner for every mutable authoring rule. Root entrypoints retain only universal authority, safety, scope, and verification; concern-specific detail belongs in its current operational guide, and historical ADRs are read only for decision review or change.
- Preserve AI as the primary author and knowledge interface while keeping human intent, consequential approval, and accountability explicit.
- Require framework explanations to use the installed contract, knowledge map, source, and tests rather than model memory.
- Keep the framework consumer contract portable: do not include maintainer-only paths, framework source limits, example-specific behavior, or fixture mechanics.
- Use `application AI context` for project-owned instructions. Reserve `harness` for executable test and evaluation infrastructure.
- Keep `templates/application/` documentation-only for deliberate adoption by existing projects.
- Keep `skeleton/` independently installable, runnable, and free of unresolved template tokens; its health-only starter resolves CRUD policy as not applicable.
- Use visible `{{UPPER_SNAKE_CASE}}` placeholders rather than plausible sample facts.
- Require each placeholder to be replaced by a verified fact or an explicit not-applicable statement before feature work.
- Record a source and verification date for volatile scale or operational claims.
- Application rules may strengthen but never weaken the installed consumer contract or Strict Profile.
- Keep the CRUD reference profile optional application structure. Consumers may record one coherent alternate placement and naming rule, but cannot weaken the installed consumer contract or Strict Profile.
- Route consumer CRUD work through installed `vendor/phpthis/framework/docs/crud.md`, never the maintainer-only `.ai/crud.md`.
- Require application context to record identifier and route policy, including the narrowest fixed route type and immediate conversion of its validated path value to a concrete identifier before any narrower domain rule, plus pagination, create identity and conflicts, `PUT`/`PATCH` and concurrency, missing behavior, delete and retention, authorization, and audit ownership.
- Require application context to record every adopted application-owned request-handler decorator or `NOT_APPLICABLE(REQUEST_HANDLER_DECORATOR)`: its final class and exact routes, one downstream `RequestHandler`, visibly unrolled construction and nesting order, zero-or-one delegation with the exact same immutable `Request` instance, unchanged exception propagation, explicit immutable `Response` replacement with complete field preservation, named bounded side effects, and behavior evidence. Do not template a generic or framework middleware interface, pipeline, iterable registry, priority ordering, discovery, `$next` abstraction, context bag, hidden binding, or hidden I/O; do not move session, cache, request-policy, or terminal-observability ownership into a decorator.
- Require application context to record every adopted inbound operation's raw source, effective bounds, exact representations, absent-versus-null and unknown-field policy, normalization or explicit non-normalization, final readonly request or command, downstream typed behavior or one justified typed operation seam, parser position relative to request policy, public failure contract, duplicate-key proof limit, and adversarial exclusion from operation-owned work; a health-only application records `NOT_APPLICABLE(INPUT)`. For structured request-body content, record the complete structural phase before value rules and the default generic `400` structural versus exact application-owned generic `422` unacceptable-value split, or another explicit finite API contract. When an operation adopts the optional field-issue profile, route to installed `vendor/phpthis/framework/docs/errors.md#optional-application-owned-field-issues` and record its exact operation, code-owned path templates and code allowlists, cross-field choice, client and localization owners, compatibility rollout, and evidence without copying the profile into a second normative context owner. Query, header, route, and transport representations do not inherit that body-content default.
- Keep frontend delivery and optional HTML rendering application-owned. Prefer a separately built frontend that consumes the application's explicit HTTP API through a same-origin deployment; a cross-origin topology records its exact origins, methods, headers, credentials, preflight, CSRF consequences, and proxy or TLS owner at the outer boundary. An application may select and pin its own HTML renderer or template package, but PHPThis adds no frontend stack, CORS or automatic `OPTIONS` mechanism, templating API, or OpenAPI runtime. Route application work through installed `vendor/phpthis/framework/docs/frontend-integration.md`; record the selected topology and dependencies in the application's `.ai/architecture.md`, record evidence in its `.ai/testing.md`, and load other guides only when their concerns are entered.
- Keep stateless authentication application-owned and route adoption through installed `vendor/phpthis/framework/docs/stateless-authentication.md` plus the application's `.ai/request-policy.md`. PHPThis is Bearer-ready only at the bounded lowercase `authorization` header seam and supplies no JWT, opaque/PAT/API-token, OAuth, parser, verifier, issuer, revoker, identity-provider, or authentication runtime/API. Require one strict Bearer header over TLS with no query, body, cookie, path, alternate-header, or fallback source; separately record the selected JWT, opaque-token, or external-verification profile, pinned dependency, configuration, I/O budgets, lifecycle, outage, rate-limit, audit, redaction, frontend storage, CORS or cookie-CSRF consequences, current per-request policy order, and evidence. Never place credential values, signing material, raw-token verifiers, or provider secrets in application AI context.
- Keep transactional email composition and delivery application-owned. Require `.ai/integrations.md` to record `NOT_APPLICABLE(EMAIL)` or the adopted operation-specific final readonly message or view model, finite templates, pinned maintained mail or MIME package and exact version, one named transport boundary and provider contract, typed addresses and canonical links, text and optional HTML policy, size and execution bounds, timeouts, rate limits, idempotency, receipts, ambiguous failure, redaction, update policy, and evidence. Route adoption through installed `vendor/phpthis/framework/docs/email.md`, with configuration, durable jobs, operations, security, observability, and testing retained by their existing guides only when entered. Preserve the starter's no-external-service default and the checked welcome-delivery database-effect proof; do not add another always-read context file or template a framework mailer, renderer, notification system, queue, worker, webhook receiver, provider, or runtime dependency.
- Route application date and time work through installed `vendor/phpthis/framework/docs/date-time.md`. A selected third-party date-time or clock package remains an explicit application-owned dependency recorded in the affected architecture and project guides; do not add it to the framework or default-skeleton runtime requirements, hide it behind a template facade, or weaken exact parsing and deterministic clock composition.
- When sessions are adopted, require application context to record typed service boundaries and key ownership; the exact cookie name and prefix, canonical casing, host-only scope, `Secure`/HTTPS policy or isolated-development exception, SameSite mode, live no-`Expires`/no-`Max-Age` behavior, deletion scope, and TLS/HSTS owner; native file-storage topology, cleanup, and verified PHP settings; and each applicable authentication, regeneration, idle and absolute expiry, logout, revocation, CSRF, XSS, CSP/output, endpoint, and logging policy. Mark absent concerns explicitly not applicable.

Keep scheduler policy in `.ai/cli.md`, migration-writer policy in `.ai/migrations.md`, durable-job ownership in `.ai/jobs.md`, and cache, session, file-transfer, and deployment concerns in their existing owners; `.ai/operations.md` references those owners rather than duplicating them.
