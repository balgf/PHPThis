# Application AI context contract

This guide applies when changing `docs/consumer-contract.md`, `docs/knowledge-map.md`, `docs/getting-started.md`, `docs/configuration.md`, `docs/crud.md`, `docs/caching.md`, `docs/jobs.md`, `docs/cli.md`, `docs/migrations.md`, `docs/websockets.md`, `docs/workbench.md`, `docs/file-transfers/`, `docs/logging.md`, `docs/observability/`, `RELEASING.md`, `templates/application/`, `skeleton/`, ADR 009, ADR 011, ADR 013, or ADR 015 through ADR 041.

The accepted Alpha 5 authority is ADR 040. It carries ADR 015 through ADR 035 forward and rolls accepted ADR 036 through ADR 039 into Consumer Contract version 10 and Strict Profile version 3 without changing the historical Alpha 4 identity.

Rules:

- Keep the framework-maintainer `AGENTS.md` and `.ai/` separate from the application template.
- Preserve AI as the primary author and knowledge interface while keeping human intent, consequential approval, and accountability explicit.
- Require framework explanations to use the installed contract, knowledge map, source, and tests rather than model memory.
- Keep the framework consumer contract portable: do not include maintainer-only paths, framework source limits, example-specific behavior, or fixture mechanics.
- Use `application AI context` for project-owned instructions. Reserve `harness` for executable test and evaluation infrastructure.
- Keep `templates/application/` documentation-only for deliberate adoption by existing projects.
- Keep `skeleton/` independently installable, runnable, and free of unresolved template tokens; its health-only starter resolves CRUD policy as not applicable.
- Use visible `{{UPPER_SNAKE_CASE}}` placeholders rather than plausible sample facts.
- Require each placeholder to be replaced by a verified fact or an explicit not-applicable statement before feature work.
- Record a source and verification date for volatile scale or operational claims.
- Application rules may strengthen but never weaken the installed consumer contract or Strict Profile.
- Keep the CRUD reference profile optional application structure. Consumers may record one coherent alternate placement and naming rule, but cannot weaken the installed consumer contract or Strict Profile.
- Route consumer CRUD work through installed `vendor/phpthis/framework/docs/crud.md`, never the maintainer-only `.ai/crud.md`.
- Require application context to record identifier and route policy, including the narrowest fixed route type and immediate conversion of its validated path value to a concrete identifier before any narrower domain rule, plus pagination, create identity and conflicts, `PUT`/`PATCH` and concurrency, missing behavior, delete and retention, authorization, and audit ownership.
- Require application context to record every adopted application-owned request-handler decorator or `NOT_APPLICABLE(REQUEST_HANDLER_DECORATOR)`: its final class and exact routes, one downstream `RequestHandler`, visibly unrolled construction and nesting order, zero-or-one delegation with the exact same immutable `Request` instance, unchanged exception propagation, explicit immutable `Response` replacement with complete field preservation, named bounded side effects, and behavior evidence. Do not template a generic or framework middleware interface, pipeline, iterable registry, priority ordering, discovery, `$next` abstraction, context bag, hidden binding, or hidden I/O; do not move session, cache, request-policy, or terminal-observability ownership into a decorator.
- Require application context to record every adopted inbound operation's raw source, effective bounds, exact representations, absent-versus-null and unknown-field policy, normalization or explicit non-normalization, final readonly request or command, downstream typed behavior or justified seam, parser position relative to request policy, public failure contract, duplicate-key proof limit, and adversarial exclusion from operation-owned work; a health-only application records `NOT_APPLICABLE(INPUT)`.
- When sessions are adopted, require application context to record typed service boundaries and key ownership, cookie policy, native file-storage topology, cleanup, verified PHP settings, and each applicable authentication, regeneration, expiry, logout, revocation, and CSRF policy; mark absent concerns explicitly not applicable.
- Require application context to record an explicit HTTP response policy and separately adopt or reject server-side data caching. An adopted data cache records its narrowly named typed services, backend and topology, bounded versioned tenant-aware keys and payloads, finite lifetimes, invalidation and stale-refill behavior, failure and stampede behavior, redacted aggregate observability, and cold-cache plus cache-specific concurrency evidence.
- Require every application to own `.ai/observability.md` naming its terminal coordinator and sink, generated correlation policy, at most eight finite database-source labels and distinct budgets/traces, destination behavior, redaction evidence, and exactly-one-attempt plus throwing-sink tests. Do not template core logging types or a durable-delivery claim.
- Include `.ai/jobs.md` in the current skeleton and template with `NOT_APPLICABLE(JOBS)` or the adopted backend, same-transaction publication, finite envelope, idempotency, lease, bounded retry, redacted dead-letter, one-shot worker, supervisor, and complete test policies. Contract version 9 does not make that additional file a checker requirement for an existing application with no durable-job path, and Contract version 10 carries that optionality forward; an application must add it before adopting or changing durable jobs. Do not template a framework queue or exactly-once external-effect claim.
- Require an application adopting file transfers to record its exact multipart fields, transport and operation limits, upload-error mapping, metadata trust, provenance, storage ownership, permissions, retention, authorization, response headers, range policy, emission-failure behavior, deployment buffering, and real-SAPI evidence. Route that work through installed `vendor/phpthis/framework/docs/file-transfers/README.md`; do not template a generic storage interface or automatic lifecycle.
- Require skeleton and template application context to record `NOT_APPLICABLE(CLI)` or the sole application console, finite command and typed-argument map, closed exit and stream contract, explicit clock and cadence, one-pass behavior, same-host overlap lock and topology, supervisor, redaction, and real-console evidence. Route adopted work through installed `vendor/phpthis/framework/docs/cli.md`; do not template a core command API, command discovery, scheduler facade, daemon, or distributed-lock claim.
- Include `.ai/workbench.md` in the current skeleton and template with `NOT_APPLICABLE(WORKBENCH)` or one checked project-relative bootstrap, concrete final workspace type, explicit exposed values and operations, complete arbitrary-PHP development authority, excluded elevated credentials, side-effect and finite-delivery policy, resource and hang limits, and retained automated evidence. ADR 041 leaves Consumer Contract version 10 and Strict Profile version 3 unchanged, and this optional file is not a checker requirement. Do not add the package or Composer script to the skeleton without approved adoption, verified availability from the approved Composer source, and clean consumer-install evidence; never template a container, registry, generic dispatcher, automatic booting, HTTP or remote access, batch mode, production path, sandbox claim, or validity claim.
- Include `.ai/migrations.md` in the current skeleton and template with `NOT_APPLICABLE(MIGRATIONS)` or the adopted engine, engine-specific decision, sole command, finite ordered unrolled manifest, identifier and checksum policy, bounded ledger, per-migration transaction, exact elevated required and prohibited capabilities, authority-transition ownership, same-host lock, forward correction and deactivation, release ordering, output, redaction, and complete test evidence. Contract version 9 does not make that additional file a checker requirement for an existing application with no migration path, and Contract version 10 carries that optionality forward; an application must add it before adopting or changing migrations. Do not template a framework migration API, schema builder, DSL, discovery, runtime `.sql` loader, inferred rollback, HTTP-startup execution, permission helper, or portable-DDL claim.
- Treat migrations as specialized application-owned database evolution. Recommend `src/Database/Migrations/` with the matching application namespace for a new application that adopts migrations, but require `.ai/migrations.md` to record the actual path and namespace and preserve any coherent application-owned alternative. Never add checker or filesystem enforcement, discover migrations from placement, or silently relocate established application source. Keep the database-free skeleton free of an empty migrations directory. Do not infer or template a generic `Database/Queries` directory, repository layer, or second SQL execution boundary from this recommendation.
- When multiple named database connections adopt independent migration histories, require `.ai/migrations.md` to record each connection's source, namespace, command, manifest, ledger, authority, and evidence boundary plus any application-selected connection-owned subdivision. Do not prescribe a subdivision spelling or scaffold speculative connection directories for a single-database application.
- Include `.ai/websockets.md` in the current skeleton and template with `NOT_APPLICABLE(WEBSOCKETS)` or one adopted application-owned third-party runtime, separate process and composition root, exact handshake and current-policy path, bounded typed message command, sequential backpressured send path, finite connection and lifecycle limits, redacted connection summary, supervisor and scaling decisions, and real process/socket evidence. ADR 034 left Consumer Contract version 9 and Strict Profile version 2 unchanged; Contract version 10 carries the optional profile forward under Strict Profile version 3, and this additional file is not a checker requirement. Route adoption through installed `vendor/phpthis/framework/docs/websockets.md`; do not template framework runtime primitives, HTTP adaptation, generic middleware, channels, broadcasters, pub/sub, context, discovery, hidden retry, replay, acknowledgement, resume, or exactly-once delivery.
- Require `.ai/configuration.md` under Consumer Contract version 10. A configuration-free application records `NOT_APPLICABLE(CONFIGURATION)`; an adopting application records one environment-reading PHP file, exact names without values, adopted process-specific factories and final readonly types, validation bounds, applicable authority separation without fallback, failure before application-controlled I/O, rotation/restart, redaction, and child-process parser or adopted-entrypoint tests. It records injection sites when process or infrastructure composition is selected, or explicitly deferred connection composition for configuration-only scope. Route adoption through installed `vendor/phpthis/framework/docs/configuration.md`; do not template framework configuration runtime, string-keyed bags, global helpers, facades, containers, discovery, automatic dotenv, secret-manager abstractions, or hidden reload.
- Keep startup and probe semantics aligned across installed configuration guidance, application routing, `.ai/operations.md`, `.ai/testing.md`, and the skeleton. `Connection::connect()` constructs PDO eagerly and may perform driver- and DSN-specific I/O or fail during composition. The starter `GET /health` explicitly composes no database, cache, queue, or network dependency in its shared bootstrap, but its terminal coordinator invokes the deployment-configured `error_log` sink synchronously before returning. That sink's destination may itself involve network or remote-filesystem I/O. Until its destination and latency are verified, describe the starter only as the current liveness route and HTTP composition proof, not as external-service-independent liveness. Each adopted HTTP or non-HTTP probe records its exact claim, composition root, every synchronous dependency and destination, bounded work, failure response or process behavior, local or deployment operations owner or explicit non-applicability, and evidence. Do not add a framework probe API, lazy connection, hidden bypass, second HTTP execution path, universal readiness definition, or checker diagnostic for operational semantics.
- Keep the ADR 037 database setup scope gate in both application `AGENTS.md` entrypoints and change workflows. An ambiguous database-engine request resolves configuration-only, existing-server connection, or project-local provisioning separately from deferred or adopted migrations before external I/O or mutation. A current not-applicable marker is present-state evidence rather than adoption intent. Local development is context, not connection or provisioning authority; explicit prompts proceed without repeated scope questions, and production operations remain excluded unless requested.
- Keep ADR 038's application-owned database authority lifecycle in the consumer contract, both application contexts, and compact task routing. When database access is absent, `.ai/data.md` contains the canonical standalone `NOT_APPLICABLE(DATABASE)` line. When adopted, record the database and object definition source; database/catalog/schema/attachment namespace selection and qualification as supported; namespace and object control-or-ownership model, explicitly not applicable when unsupported; each named operation's exact required objects and actions; prohibited actions; engine-specific effective-authority resolution; elevated required and prohibited capabilities only when adopted; one activation/deactivation owner and non-HTTP path; exact-engine positive and negative evidence; and release ordering through traffic enablement and later authority deactivation. Direct, role or inherited, public or default, database or global, ownership-chain, IAM, and filesystem or process authority are examples to record only when the engine uses them. `GRANT` and `REVOKE` are engine-specific mechanisms, not universal requirements. Configuration, connectivity, object existence, and migration completion do not activate authority. Do not prescribe a namespace, identity topology, default privilege, universal deployment order, permission helper, runtime introspection, or automatic hook.
- Keep authentication, authorization, session state, permissions, secrets, and other security decisions outside an initial application data-cache slice unless a later accepted decision defines stronger invariants and evidence.
- Do not add a generic CRUD runtime, discovery mechanism, filesystem enforcement, or checker rule for directories and names.
- Require `.ai/data.md` to name every connection's engine/version, PDO extension, non-secret configuration reference, database and object definition source, supported namespace selection and qualification, namespace and object control-or-ownership model or explicit non-applicability, dialect authority, per-operation runtime authority, elevated capabilities when adopted, authority activation/deactivation owner, exact-engine verification, integration command, and lack of cross-connection atomicity; exact input names and typed configuration factories belong in `.ai/configuration.md`, while release sequencing belongs in `.ai/operations.md`.
- Never place credentials, tokens, private keys, customer data, production payloads, runtime dumps, or chat transcripts in the template.
- Do not claim that Composer dependency installation inherits root scripts or development dependencies; the skeleton must declare both explicitly.
- Keep framework `bin/phpthis` and installed `vendor/bin/phpthis` dedicated to the framework-owned check. Application operational commands use the one application-owned console recorded in project context.
- Keep the optional development Workbench in the separate `phpthis/workbench` `require-dev` package. Its fresh strict expression processes and application-owned `$workspace` are exploratory only. A real job publication may invoke only the existing adopted business operation and transaction; one queued delivery and production one-offs remain in the application's recorded finite tested console commands.
- Keep the installed duplication scan a report-only review signal over the same application manifest. Never turn it into a consumer-configured validity rule, suppression path, automatic refactor, layout convention, or reason to generalize explicit SQL, finite unrolled operations, security sequencing, or independent tests.
- Keep template links valid after the files are copied to an application root; do not link back with repository-relative `../../` paths. Treat every hardcoded `vendor/phpthis/framework/` path in copied `AGENTS.md` and `.ai/` files as one installation assumption that must be updated together when Composer uses a non-default vendor directory.
- Keep the role, authority, and human-decision language aligned across the consumer contract, skeleton, and application template.
- Require every observable behavior change to add or update application-owned automated tests while leaving the test library, runner, file placement, and organization application-owned. Static analysis, documentation, manual verification, and no-op commands are not behavior evidence.
- Keep Alpha scope approval separate from authorization to create tags, repositories, package-host entries, releases, or announcements. The actual Packagist-preferred artifacts and unchanged public create-project path must pass `RELEASING.md` before announcement; tracked package authority does not record mutable publication state.

Run `composer check`, inspect unresolved placeholders in the documentation-only template, execute the isolated skeleton-consumer proof, and verify the exact framework archive inventory before a release.
