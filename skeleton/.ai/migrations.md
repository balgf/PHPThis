# Application migration contract

`NOT_APPLICABLE(MIGRATIONS)`: the health-only starter has no database, migration source directory or namespace, migration command, namespace or object transition, elevated identity, authority activation path, manifest, checksum policy, ledger, transaction or DDL atomicity policy, coordination topology, per-history release constraints, partial-failure recovery policy, or migration evidence. No migration directory, code, or dependency is included, and HTTP startup performs no data-definition or authority-transition work.

Database migrations are specialized application-owned database evolution. On first adoption with no established structure, PHPThis recommends `src/Database/Migrations/` and the skeleton's matching `App\Database\Migrations` namespace. Record the actual adopted directory and namespace in this file. A coherent consumer-selected alternative is authoritative; neither PHPThis nor the consumer checker enforces the recommendation or discovers migration files, and AI must not relocate an established structure without explicit human approval.

If multiple named database connections later adopt separately tracked migration histories, keep one application console executable but give each history one stable application-owned name and record its explicit source path, namespace, finite command ownership, manifest, ledger, typed-configuration/process-identity reference, database-authority reference, supported writer topologies, and evidence boundary. Every engine/version, engine decision, coordinator, manifest, ledger, atomicity, coordination, recovery, output, and evidence fact below is recorded per separately tracked history. Never combine migration credentials or allow one history to obtain another's identity/configuration. Each history pair proves disjoint managed objects, data, authority transitions, and coordination domains or shares explicit serialization, release, and recovery ownership plus cross-history partial-deployment evidence. Create an application-selected connection-owned subdivision only for an adopted separately tracked history; do not pre-create or prescribe connection subdivisions for this database-free skeleton or a single-database application.

Before adoption, read installed `vendor/phpthis/framework/docs/migrations.md` and record:

- the actual adopted migration source directory and matching application namespace;
- the exact engine and supported version; accepted engine-specific database definition or provisioning, supported namespace/control model, data-definition, authority, coordination, recovery, and integration decision; sole application console executable; and each separately tracked history's finite explicit command plus typed-configuration/process-identity reference to `.ai/configuration.md` and database-authority reference to `.ai/data.md`;
- each separately tracked history's exact initial baseline, which may be empty, include recorded pre-provisioned objects, or include a separately reviewed existing schema, data state, or ledger prefix whose exact structure and assumptions are proved; enumerate every accepted present object, data assumption, ledger row, and checksum plus every application-managed object or history entry that must be absent, and never infer or manufacture a ledger prefix;
- each separately tracked history's separately named migration configuration source, factory, final readonly type, injection, process identity, failure, rotation/restart, and secret redaction in `.ai/configuration.md`, without inheritance, fallback, or combined credentials;
- stable-history references to exact required and prohibited migration capabilities, effective runtime/migration overlap or supported isolation, activation/deactivation owner, and authority evidence in `.ai/data.md`; the selected authority-transition implementation source and complete non-HTTP implementation path remain here and are checksum-covered when a migration owns engine-supported statements; migration configuration and process-entry identity remain unavailable to HTTP through `.ai/configuration.md`, with `GRANT` and `REVOKE` only where supported;
- one final application-owned coordinator, permanent identifier grammar, finite manifest maximum, explicit migration-step order, unrolled private step methods, canonical SHA-256 checksum byte sequence covering every statement, code-owned binding name/type/literal value or finite binding-derivation policy, and ordered DDL/data/authority effect, plus one bounded ledger per separately tracked history; unreviewed deployment environment, command, or network input never changes a migration binding;
- complete engine-specific compile-time-constant SQL at direct `Connection` calls with no database call in a loop;
- each bounded ledger containing the required position, identifier, and checksum; any selected extra metadata, including a timestamp, has an explicit source, representation, and bound, is parsed and validated as non-executable data, and cannot select work, define order, or grant authority; also record the row maximum, parser bounds, finite exact-engine accepted metadata and explicitly permitted supporting objects, and rejection of missing, incompatible, or additional unrecorded ledger-related objects before history parsing or pending work;
- the engine/version's transaction behavior and DDL atomicity limits, the design that keeps migration effects and ledger records consistent, immutable history, and every partial-failure detection, forward-correction, backup, restore, and recovery path;
- every supported topology from which a migration writer can run, with one explicit application-local, database/server, deployment, or external coordination or serialization mechanism per topology, including stable identifier/namespace, collision boundary, exact creation, acquisition, use, and release permissions or authority, owner, scope, contention or serialization behavior, acquisition failure, expiry or loss, process/session termination, and exact hosts or runners covered;
- shared exclusion across concurrently reachable topologies for one history or pairwise authority gating that prevents their identities/configurations from being active together, with proof for every reachable pair;
- coordination or serialization effective before ledger bootstrap or creation plus authoritative definition/history validation and retained through every checksum-covered effect and either accepted ledger completion or a finite fail-closed failure outcome; no partial state recorded as applied; stop before the next mutation on detected loss; fence an expiring or lost owner from later mutations or confirm termination with no in-flight work; and require the next owner to reacquire coordination and re-detect exact state before mutating;
- disjoint managed objects, data, authority transitions, and coordination domains between separately tracked histories, or shared serialization, release, and recovery ownership with cross-history partial-deployment behavior and evidence;
- the history's engine-specific compatibility, authority-verification, failure-stop, and handoff constraints, with the application-wide release sequence recorded only in `.ai/operations.md`; required authority precedes dependent traffic, and dependent code is drained before its required authority or namespace is removed;
- exact finite success and error outputs with complete redaction; and
- exact-baseline and accepted-ledger-prefix validation, every pending checksum-covered DDL/data/authority effect, rerun, drift, malformed and overflowing ledger, required position/identifier/checksum plus every selected extra metadata field's source/representation/bound/validation/non-authoritative use, finite exact-engine ledger-metadata acceptance and rejection of missing/incompatible/additional unrecorded ledger-related objects before history parsing or pending work, every supported and cross-topology writer pair, exact transaction and DDL atomicity limits, ledger consistency through every effect and accepted completion or finite failure, no applied partial state, detected-loss stop, owner fencing or confirmed termination, next-owner reacquisition and redetection before mutation, partial-failure recovery, separate no-fallback configuration/identity, cross-history isolation or shared-boundary partial-deployment behavior, finite stable output, redaction, exact-engine, and no-HTTP-startup tests. Application-local and database/server mechanisms require concurrent real-console proof; deployment/external serialization requires proof at that boundary that a bypass cannot obtain migration identity/configuration.

Migration success alone does not prove runtime authority is active. Complete engine-supported transition statements belong visibly and checksum-covered in a migration, in a separately authorized application stage, or in a named external provisioning source. `GRANT` and `REVOKE` are transition forms only where the engine supports them. Activate and verify required authority before dependent code receives traffic, stop the dependent stage on failure, and drain or remove dependent code before authority deactivation or namespace/object removal.

ADR 027 remains the accepted SQLite reference proof. Only when the application deliberately adopts that exact shape, record and prove one explicit transaction per migration and ledger insert, active-transaction rollback with earlier commits preserved, one application-private nonblocking same-host `flock` released in `finally`, the stricter SQLite ledger-definition proof, and its `applied` or `up_to_date` success names. Those mechanics and names are not another engine, topology, or application's defaults.

Do not add a framework migration API, schema builder, DSL, discovery, runtime `.sql` loading, stored executable SQL or class names, generic database facade, permission helper, role registry, runtime authority introspection, automatic privilege hook, transaction callback, inferred down migration, hidden retry, HTTP-startup migration, cross-engine coordination abstraction, or cross-engine claim. Every adoption requires its own engine/version transaction and DDL atomicity limits, ledger-consistency design, coordination, privilege, recovery, and integration evidence.
