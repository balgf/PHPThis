# Application data contract

`NOT_APPLICABLE(DATABASE)`

The exact standalone declaration above is present-state application context: the starter opens no database connection. A direct canonical `PHPThis\Database\Connection::connect` call cannot coexist with it. Replace the declaration and complete the database contract before adopting a connection. The starter also has no persisted resource, CRUD-shaped behavior, SQL, structural selector, bounded data list, database identity or privilege, CRUD resource route, pagination, mutation policy, deletion policy, resource authorization, or audit event.

`NOT_APPLICABLE(MIGRATIONS)`: `.ai/migrations.md` owns each future history's source and namespace; exact initial baseline; engine/version decision; command plus typed-configuration/process-identity and database-authority references; manifest and checksum-covered DDL/data/authority effects; bounded exact-engine ledger metadata; exact atomicity and ledger-consistency transitions; stable coordination namespace, collision, creation/acquisition/use/release permissions, reachable-topology exclusion, and lost-owner behavior; transition implementation; relationship to other histories; per-history compatibility, handoff, recovery, and evidence. `.ai/configuration.md` owns exact no-fallback configuration and process identity, this file owns effective authority facts and accountable transition ownership, and `.ai/operations.md` alone owns the application-wide release and cross-history recovery execution sequence. Do not infer migration adoption or placement, namespace selection, a namespace or object control or ownership model, or active authority from a database definition or provisioning source.

`NOT_APPLICABLE(UUID_POLICY)`: the health-only starter has no UUID resource identifier, accepted UUID domain policy, generated UUID, generator, UUID persistence representation, or UUID ordering assumption.

Before UUID adoption, replace that declaration with `UUID_POLICY(ADOPTED)` and record each policy group's concrete identifiers, accepted canonical versions, generated version and purpose or explicit not applicability, generation owner and exact application source path, selected package and version, database facility and engine version, or external owner, generated-value metadata and time-disclosure decision, accepted metadata-bearing UUID exposure and handling, same-timestamp ordering scope, clock-regression behavior, failure and no-fallback policy, narrower domain rules, persistence representation and ordering assumptions, and evidence source. Keep acceptance separate from generation. The reference acceptance policy is canonical lowercase RFC-variant versions 1 through 8. Version 7 is recommended for newly generated database row identifiers when embedded approximate creation-time disclosure is accepted; version 4 is the random-only alternative when that disclosure from newly generated values is unacceptable; version 5 is only for a recorded deterministic namespace and exact-name-byte policy. Choosing version 4 does not prevent metadata disclosure if accepted or persisted time-bearing versions such as 1, 6, or 7 are exposed. A generated-version choice does not reject or convert other accepted versions, and PHPThis selects no generator, package, database facility, schema rule, or persistence representation.

`NOT_APPLICABLE(CACHE)`: the starter has no typed cache projection, authoritative rebuild source, versioned key schema, environment or tenant cache namespace, payload parser or bound, TTL or staleness bound, invalidation policy, or corruption and eviction behavior.

`NOT_APPLICABLE(REQUEST_POLICY)`: the starter has no authentication, tenant-resolution, authorization, or protected-handler connection, query budget, trace, protected write, or authorization-to-write race.

Before adding data access, record every connection's engine and version, PDO extension, non-secret configuration reference, database definition or provisioning source, database/catalog/schema/attachment namespace selection and qualification as supported, namespace and object control or ownership model or explicit N/A, dialect authority, integration command, scale, query budget, indexes, and transaction constraints. An engine-default namespace, an application-specific namespace, or explicit not applicability where the engine has no namespace or ownership model are all valid recorded decisions; none is inferred or prescribed. Record exact external input names and typed factories without values in `.ai/configuration.md`. Also record each SQL structural choice and finite code-owned mapping, every bounded-list shape and maximum cardinality, each cursor's version, stable tie-break and snapshot policy, and each named operation's complete statement source, runtime identity, exact required targets and capabilities, selected prohibited capabilities, and effective authority resolution source. Record only applicable mechanisms, which may include direct privileges, roles or inheritance, public or default access, database or global privileges, ownership chains, IAM, or filesystem and process authority. Record one accountable non-HTTP owner and authoritative implementation reference for every adopted authority activation and deactivation, `GRANT` and `REVOKE` only where supported, exact-engine positive and negative evidence with its verification date, and one separately named no-fallback identity/configuration profile per adopted migration history plus a separate administrative profile when adopted. Keep the transition source and complete implementation path in `.ai/migrations.md` when migration adoption owns it. Configuration, connectivity, target existence, and migration completion do not activate runtime authority. Activate and verify required authority before dependent code receives traffic; drain or remove dependent code before authority deactivation or namespace/object removal.

Every SQL data value must use a distinct exact case-sensitive named placeholder and binding for each occurrence; repeated logical values still use separate names and bindings. SQL must execute through a direct `Connection` call and resolve natively in PHPStan to finite non-blank compile-time constants under PHT006. PHT008 checks each finite alternative for repeated recognized names at analysis time; it does not compare the parameter array or reject SQL at runtime. Unknown selectors and unsupported list shapes must fail before database work; do not introduce a sanitizer. Before CRUD-shaped behavior, also record all operation semantics above; the optional layout does not decide them.

`NOT_APPLICABLE(RESOURCE_ROUTE_IDENTIFIERS)`: before adopting a resource route, record its narrowest fixed declaration among `positive-int`, `uuid`, `ulid`, and genuinely opaque `token`, the matching `PathParameters` accessor, the application-owned route-specific identifier wrapper, and any narrower validation performed before database work. Route matching returns unchanged routing metadata; it does not normalize, bind or look up a record, generate an identifier, choose persistence, or fall back between types.

Before cache adoption, record each narrowly named service and owned projection, the authoritative source that can reproduce it, a versioned environment- and tenant-scoped key schema, bounded parsed payload shape, finite TTL and staleness limit, post-commit invalidation and failure policy, and corruption, eviction, and miss behavior. Treat cache payloads as untrusted external input and never as a source of truth.
