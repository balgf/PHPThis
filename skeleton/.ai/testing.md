# Application testing contract

## Complete validity gate

Run from the application root:

```bash
composer check
```

Its exact definition is in `composer.json`: `phpthis check` owns application-wide guardrails, the PHPThis Strict Profile, and maximum-level PHPStan; `composer test` owns behavior evidence.

## Automated behavior evidence

Every observable behavior change must add or update application-owned automated tests. The application owns the test library, runner, file placement, and organization; PHPThis does not require PHPUnit, Pest, a `tests/` directory, or a particular test category. Composer `scripts.test` must execute this evidence and return a non-zero status when it fails. Static analysis, documentation, manual verification, and a no-op test command are not behavior evidence.

## Focused commands

- Framework-owned profile and static analysis: `vendor/bin/phpthis check`
- Application behavior tests: `composer test`
- Configuration boundary and real-entrypoint tests: `NOT_APPLICABLE(CONFIGURATION)`
- Inbound-data boundary tests: `NOT_APPLICABLE(INPUT)`
- WebSocket integration and lifecycle tests: `NOT_APPLICABLE(WEBSOCKETS)`
- Database integration tests: `NOT_APPLICABLE(no database)`
- Request-policy tests: `NOT_APPLICABLE(public liveness route only)`
- Application-owned request-handler decorator tests: `NOT_APPLICABLE(REQUEST_HANDLER_DECORATOR)`
- HTTP cache policy tests: `composer test`
- Cache integration tests: `NOT_APPLICABLE(CACHE)`
- Durable-job integration and lifecycle tests: `NOT_APPLICABLE(JOBS)`
- Application CLI and scheduler tests: `NOT_APPLICABLE(CLI)`
- Database migration tests: `NOT_APPLICABLE(MIGRATIONS)`

Focused commands shorten feedback but never replace the complete gate.

## Starter evidence

- Automated tests for every observable behavior change cover expected success, expected failure, boundary validation, and applicable authorization, external side effects, and resource limits.
- `NOT_APPLICABLE(CONFIGURATION_EVIDENCE)`: before configuration adoption, prove every implemented parser or factory's valid final readonly construction; missing, empty, malformed, and oversized rejection before application-controlled I/O; fixed output containing none of the supplied bytes; and child-process environment delivery without application `putenv`. Configuration-only scope records infrastructure injection and connection evidence as deferred without dead wiring. A selected connection or process proves typed delivery at its real entrypoint. HTTP exclusion and no-fallback evidence is required when an elevated profile is adopted; otherwise elevated configuration evidence remains not applicable. Provisioning and production evidence is required only for explicitly selected scopes.
- Test the exact health response, unknown route, unsupported method, malformed runtime input, oversized declared body, and real front controller. This proves the current HTTP composition and response path, not external-service-independent liveness: the coordinator invokes deployment-configured `error_log` synchronously and no destination or latency bound is recorded. Before deployment adoption, verify that sink and every other synchronous dependency. If eager infrastructure is adopted, update the recorded probe claim and test its inherited dependencies, bounded work, and composition or dependency failure behavior; do not treat connection construction as database-authority or complete-readiness evidence.
- Test the terminal summary on health success, mapped failure, and unknown failure: exactly 32 lowercase-hex correlation characters, the identical `X-Request-ID`, generic outcome and status, class-only unknown failure, zero database aggregates and sources, complete request-value redaction, exactly one sink invocation attempt, and an unchanged response when the sink throws. This proves an attempt, not durable delivery or network emission.
- `NOT_APPLICABLE(INPUT_EVIDENCE)`: the health-only operation accepts no application-owned fields and constructs no typed request or command. Before adding product input, prove the exact final readonly value used by downstream behavior; absent and explicit-null behavior; unknown, wrongly typed, coercive, malformed, nested, and oversized representations; exact boolean, integer, enum, date, string, list, and object policy as applicable; and every recorded preservation, rejection, or explicit normalization. For application-owned structured request-body content, separately assert generic `400` for malformed or invalid complete shape/native types and generic `422` for correctly shaped and typed but unacceptable values, unless `.ai/architecture.md` records another explicit finite API contract. Include a mixed unacceptable-value plus wrong-native-type case and property-order variants that remain `400`, proving the complete structural phase precedes value rules. Query, header, route, and transport representations retain their separately recorded contracts. Assert exact generic response bytes, `no-store`, status-only known-failure summaries, and absence of submitted field names and values, credentials, and internal messages from bodies, headers, summaries, logs, and traces on both body paths. Keep `413`, `415`, persisted-state conflicts, and unexpected failures separate. Every rejection proves no operation-owned downstream I/O or mutation and zero typed-seam calls when one exists. Record and separately bound any request-policy work ordered before parsing, and record the native JSON duplicate-key limitation unless a separately accepted parser proves rejection.
- `NOT_APPLICABLE(WEBSOCKETS)`: before adoption, read `.ai/websockets.md` and add pure parser, current authentication and authorization, finite dispatch, typed-operation delivery, encoding, connection-summary redaction, and every recorded message, rate, connection, send, idle, heartbeat, lifetime, and shutdown-bound test. Real child-process and socket tests prove readiness without a blind sleep, accepted and denied handshakes, ordered success, malformed and oversized traffic, transport close behavior, backpressure, reconnect without unrecorded replay, occupied-listener failure, signal shutdown, bounded process exit, and cleanup in `finally`. Prove frames never become PHPThis HTTP `Request` or `Response` values and record the exact tested topology without generalizing it to production TLS, proxy, supervisor, capacity, scaling, or availability behavior.
- `NOT_APPLICABLE(REQUEST_POLICY_EVIDENCE)`: before protecting a route, test unauthenticated, ordinary forbidden, cross-tenant, permitted, and unexpected policy-failure paths, exact policy order, every failing stage, zero protected queries and writes on denial, explicit principal and tenant delivery, generic disclosure and cache policy, status-only denial summaries, class-only unexpected-failure summaries, redaction from responses, summaries, and traces, and independent replacement of every policy implementation. A concrete credential parser also tests malformed and rejected input, and any policy I/O has a budget and trace distinct from protected work.
- `NOT_APPLICABLE(REQUEST_HANDLER_DECORATOR_EVIDENCE)`: `HealthHandler` is constructed directly. Before adoption, prove the final decorator class and one downstream `RequestHandler`, direct route-local construction and complete unrolled order, zero-or-one downstream invocation, the exact same immutable `Request` instance, applicable early-return and delegated outcomes, unchanged exception identity, complete field preservation in any explicit immutable `Response` replacement, and every named side effect's applicable attempt, byte, time, statement, query-budget, and ordering bound. A short circuit performs no downstream query, mutation, or external effect, and no decorator wraps or owns `Application`, `RequestBoundary`, the terminal coordinator, `ResponseEmitter`, sessions, cache policy, request policy, or terminal observability.
- `NOT_APPLICABLE(RESOURCE_ROUTE_IDENTIFIER_EVIDENCE)`: the health-only starter has no path parameter, resource handler, UUID policy, generator, or database work. Before adding a resource route, prove its canonical `positive-int`, `uuid`, `ulid`, or genuinely opaque `token` representation reaches the handler through the matching `PathParameters` accessor. Invalid, normalized-only, alternate, or type-fallback spellings must select `404` with zero handler and database work; a canonical valid path with the wrong method must select `405`. A successful handler immediately wraps the unchanged value in an application-owned route-specific identifier and applies narrower domain checks before database work. UUID route and shared-representation evidence accepts the recorded canonical versions, including versions 1 through 8 and RFC variant nibbles `8`, `9`, `a`, and `b` under the reference policy, and rejects malformed, uppercase, compact, braced, URN, encoded, Nil, Max, version 0, versions 9 through 15, and non-RFC-variant spellings without normalization. When multiple concrete identifiers compose one recorded application-owned representation primitive, test its accepted and rejected canonical representations once, then test every concrete identifier's supplied construction and representation accessor; operation signatures continue to require the concrete identifier. Test generation separately from acceptance: prove the exact recorded generator source contract, every concrete identifier's adopted generated path, the chosen version and variant bits, applicable randomness and clock inputs for versions 4 or 7 or the namespace UUID, exact name bytes, and canonicalization for version 5, failure propagation with no fallback or partial mutation, and exact-engine behavior when generation is database-owned. Version and variant bits alone are insufficient. For version 7, test only the recorded timestamp, same-timestamp, clock-regression, process or node, and ordering claims; finite generated samples do not prove uniqueness or total creation order.
- `NOT_APPLICABLE(CRUD_EVIDENCE)`: the starter has no CRUD-shaped operations. For each operation later added, test its applicable route, identifier, conflict, pagination, missing-resource, concurrency, deletion, authorization, and audit policies; keep absent operations and concerns explicitly not applicable. For a resource exposed through multiple access surfaces, prove that each named route-area list selects its intended handler and its applicable policy path or recorded not-applicable policy; when protected, denial performs no protected work; and no surface executes SQL or side effects or emits fields outside its recorded operation contract and, when applicable, named authorization action and tenant or resource scope.
- `NOT_APPLICABLE(DATABASE_EVIDENCE)`: the exact standalone `NOT_APPLICABLE(DATABASE)` line in `.ai/data.md` remains while no direct canonical `PHPThis\Database\Connection::connect` call exists. Before database adoption, replace that declaration and add exact-engine integration and scale tests, adversarial bound-data tests, unknown-selector and oversized-list rejection before database work, query-budget and trace assertions, and dated per-operation authority evidence. Execute every intended statement under the runtime identity before traffic; safely verify selected prohibited namespace, data-definition, identity or role, authority-administration, migration-ledger, database or global, and unrelated-target capabilities using only mechanisms the engine supports. Resolve effective authority from the recorded source, which may involve direct privileges, roles or inheritance, public or default access, database or global privileges, ownership chains, IAM, or filesystem and process authority. Prove each adopted authority activation and deactivation has one visible non-HTTP owner and path, record `GRANT` and `REVOKE` only where supported, and prove elevated configuration remains unavailable to HTTP. A cursor or bounded list additionally proves its recorded omitted and empty-input behavior, every supported cardinality and order, stable equal-key traversal in static fixtures, the recorded snapshot policy, and exact zero- versus non-zero-statement bounds. Configuration, connectivity, target existence, migration success, PHT006, tenant predicates, and adversarial bindings are not universal authority, authorization, or injection proof; do not treat base PDO transport evidence as application-SQL certification.
- `NOT_APPLICABLE(SESSION_EVIDENCE)`: before session adoption, prove anonymous access without storage, invalid, duplicated, attacker-selected, stale, and obsolete identifier rejection, exact state bounds, callback rollback, lock release, unissued-ID cleanup, delayed-response cookie safety, explicit invalidation, cookie attributes, isolated save-path enforcement, and concurrent requests. Cleanup evidence proves exact primary identity after success; redacted retention after cleanup failure; coherent begun-request and earlier pending state after failed update or regeneration cleanup; invalidation commit-failure precedence without a stale live cookie; terminal reset after finish or abort; no retry after cleanup failure; and normal finalization of a registered original response after successful operation cleanup. Add authentication-time regeneration, expiry, CSRF, authorization, and revocation tests only when those recorded policies apply; mark each absent concern explicitly not applicable.
- `HTTP_RESPONSE_FRAMING`: every added response proves its final status, body, and headers. Ordinary content may omit `Content-Length`; when present its canonical decimal value equals the exact body byte length. `204`, `205`, and `304` have empty bodies and no `Content-Length`; `Transfer-Encoding` is not used. A `HEAD` route is explicit and returns an empty body without inferred representation length.
- `HTTP_CACHE_EVIDENCE(NO_STORE)`: application behavior tests prove exact `Cache-Control: no-store` policy for health success, route miss, method rejection, and mapped invalid and oversized input, plus exact `Cache-Control: private, no-store` for unknown failure. No current response is storable, so freshness, validators, conditional requests, `Vary`, and public-cache isolation tests are not applicable. Every response path added later requires exact policy evidence; deployment separately verifies that each configured intermediary preserves the field.
- `NOT_APPLICABLE(CACHE_EVIDENCE)`: before cache adoption, prove cold miss and authoritative rebuild, warm hit without hidden database work, finite expiry, bounded payload parsing, corruption handling, backend failure and recovery, environment and tenant isolation, versioned-key rollover, post-commit invalidation and invalidation failure, a concurrent miss racing an authoritative write, and the recorded stampede behavior under concurrent requests. Inspect bounded hit, miss, write, invalidation, failure, and stampede summaries without logging keys or payloads; cold-cache database tests must still prove constant query scaling.
- `NOT_APPLICABLE(JOBS_EVIDENCE)`: before durable-job adoption, prove commit-visible publication and rollback exclusion, bounded stored-envelope parsing and finite dispatch, idle and success, exact retry delays from freshly observed failure time, completion rollback when handler time reaches lease expiry, lease expiry and stale-token fencing, final-attempt and poison dead letters, duplicate idempotent effects, real subprocess termination and post-expiry recovery, one delivery per fresh process, complete diagnostics redaction, and constant transition statement counts across queue sizes.
- `NOT_APPLICABLE(CLI_EVIDENCE)`: before an operational console is adopted, execute the real console in fresh subprocesses and prove every finite command and exact argument bound, rejection before application I/O, exact exit and stdout/stderr bytes, every expected outcome, operational and unexpected failure redaction, one-pass resource bounds, and fresh HTTP and CLI state. When a scheduled pass is adopted, additionally prove explicit-clock cadence boundaries, not-due exclusion from work, its recorded overlap mechanism and cleanup or release, plus every missed-run, catch-up, repeated-slot, supervisor, and topology limit. A migration-only console proves its writer coordination or serialization through the migration evidence below, not through scheduler-overlap evidence. Do not treat Composer or `vendor/bin/phpthis check` as this evidence.
- `NOT_APPLICABLE(MIGRATION_EVIDENCE)`: before migrations are adopted, execute each history's real application console command in fresh subprocesses against its exact engine/version and prove its exact initial baseline, including every pre-provisioned object, already-present application-managed object, effect, or ledger row, and every state required absent; validate the accepted ledger prefix; prove every pending checksum-covered statement, code-owned binding value or finite binding-derivation policy, and DDL/data/authority effect in manifest order; the exact position/identifier/checksum ledger plus every selected extra metadata field's source, representation, bound, validation, and non-authoritative use; unchanged no-op rerun; binding/policy, statement, malformed, and overflowing history rejection; finite exact-engine ledger-metadata acceptance; and rejection of missing, incompatible, or additional unrecorded ledger-related objects before history parsing or pending work without imposing SQLite byte-for-byte comparison. Cover every supported migration-writer topology and every concurrently reachable topology pair. Prove application-local and database/server coordination with concurrent real-console processes; prove deployment/external serialization at its owning boundary and that bypassing it cannot obtain the history's migration identity/configuration. Evidence proves each stable coordination identifier/namespace, collision boundary, creation/access permissions, shared exclusion or pairwise authority gate, and protected interval. It proves coordination remains effective through every checksum-covered effect and either accepted ledger completion or a finite fail-closed failure outcome; no partial state is recorded as applied; detected loss stops before the next mutation; and an expiring or lost owner cannot overlap a successor because prior in-flight database work is fenced, the prior session/work is confirmed invalidated or terminated, or another exact-engine exclusion proves termination. The next owner reacquires coordination and re-detects exact state before mutating. It also proves each history's finite explicit command, separate engine decision, separately named configuration factory/final readonly type/process identity without inheritance, fallback, or combined credentials, exact transaction/implicit-commit/DDL atomicity behavior, recovery, output, and evidence; migration-effect/ledger consistency at every failure boundary; exact finite stable redacted output; fresh migration composition; and no data-definition or authority-transition work during HTTP startup. Multiple histories prove disjoint managed objects, data, authority transitions, and coordination domains before they are called independent, or explicit dependency, shared serialization/release/recovery, and every cross-history partial-deployment state. Prove migration success does not stand in for runtime-authority activation, required authority is verified before dependent traffic, transition or verification failure stops that stage, and dependent code is drained before later authority deactivation or namespace/object removal. When ADR 027's SQLite reference shape is adopted, additionally prove its explicit timestamp and stricter ledger definition, `applied`/`up_to_date` success names, nonblocking same-host `flock` contention and cleanup, active-transaction rollback with earlier commits preserved, and forward continuation. Do not generalize that SQLite transaction, file-lock, rollback, output, or filesystem-authority evidence to another engine or host topology.
- Migration evidence separately proves exact creation, acquisition, use, and release permissions or authority for every coordination mechanism. It consumes exact configuration/process-identity facts from `.ai/configuration.md`, effective database-authority facts and accountable transition ownership from `.ai/data.md`, transition implementation and per-history constraints from `.ai/migrations.md`, and application-wide sequence/runbook facts from `.ai/operations.md`; it does not create a second writable policy.
- Do not add runtime or checker assertions for optional CRUD directory and naming choices.
- Use generated or explicitly approved synthetic fixtures. Never copy production payloads, credentials, customer identifiers, tokens, or private keys into tests.
