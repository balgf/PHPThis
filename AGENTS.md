# Instructions for AI coding agents

## Authoring model

You are the primary code author and knowledge interface for work in this repository. Answer questions from the current checkout: inspect the relevant contract, decision, source, and tests, and name that evidence. Do not rely on remembered PHPThis behavior or present a proposal as an existing feature.

The human supplies intent and remains accountable for the outcome. Surface missing facts and consequential product, architecture, security, data, release, and operational choices for human judgment. You may draft a decision record, but only an accountable human may accept such a decision.

## Read order

1. Read `VISION.md`.
2. Read `.ai/README.md`.
3. Read `.ai/rules.md`, `.ai/change-workflow.md`, and `.ai/strict-profile.md`.
4. Read only the area guide named by `.ai/README.md`.
5. Inspect the concrete route, handler, and test involved in the task.

## Mandatory rules

- Use PHP 8.4 and `declare(strict_types=1);` in every PHP file.
- Make classes `final` unless a documented extension point requires otherwise.
- Use ordinary constructor injection wired manually in a composition root.
- Use `RequestHandler::handle`; do not make handlers invokable.
- When route-local wrapping is justified, use only an application-owned request-handler decorator: one final application class implementing only `RequestHandler`, owning one narrowly named route concern, wrapping exactly one downstream `RequestHandler`, and constructed visibly as an unrolled route-handler expression beside that route. It may invoke its downstream zero or one time with the exact same immutable `Request` instance, must propagate its own and downstream exceptions unchanged, and may replace the returned value only with an explicit immutable `Response` that preserves every unchanged field. Name and bound every decorator-owned side effect and test its order, short circuit, response, and failure behavior. Do not add a generic or framework middleware interface, pipeline, iterable registry, priority ordering, discovery, `$next` abstraction, context bag, hidden binding, or hidden I/O, and never wrap `Application`, `RequestBoundary`, the terminal coordinator, or `ResponseEmitter`.
- Represent response cookies with `ResponseCookie`; do not encode `Set-Cookie` in the ordinary header map.
- Keep optional session state behind narrowly named typed services over one `SessionLifecycle`; give them explicit non-overlapping keys and do not access `$_SESSION`, native session calls, or generic session helpers from application code.
- Keep session mutation callbacks bounded and free of I/O or external side effects; complete fallible domain work before the final immediately committed session mutation.
- Keep routes in an explicit list. A route path is literal or contains at most two full-segment placeholders using only `{name:positive-int}`, `{name:token}`, `{name:uuid}`, or `{name:ulid}`; names stay lowercase snake-like ASCII, and no discovery, attributes, reflection, or string class resolution is allowed. Use the narrowest type and reserve `token` for genuinely opaque identifiers.
- Keep request-time routing indexed. Exact literal lookup remains direct; typed routes use the deterministic state index, exact literals take precedence, request-time code does not scan route or index collections, and overlapping parameterized declarations fail at construction rather than being resolved by order or type preference.
- Deliver matched parameters only through type-specific access on immutable `PathParameters` carried by the immutable `Request` copy created by `Application`; keep `RequestHandler::handle(Request): Response`, and immediately wrap each validated integer, token, UUID, or ULID in a concrete route-specific identifier before narrower domain validation or database work.
- Keep SQL in the handler. When HTTP adaptation and an independently meaningful business transaction require separate ownership, SQL may instead live in the one narrowly named concrete operation that directly receives the final command and owns that transaction. Execute only through direct `Connection` calls; do not add a repository, service, or query layer beneath that operation.
- Treat `Connection` as native PDO transport, not a dialect abstraction; keep SQL visibly specific to the recorded engine, bind every data value, and give every placeholder occurrence a distinct portable name.
- In the ADR 022 protected document-list proof, keep every complete raw SQLite statement and its explicit named parameter array visible together at the direct `Connection` call. Do not introduce an ORM, query builder, repository, SQL/binding/placeholder helper, generic paginator, transaction callback, generated SQL, or dialect abstraction into that proof.
- Pass only SQL that PHPStan resolves natively to a finite set of non-blank compile-time constant strings. Map structural choices to finite reviewed code-owned statements or fragments, prefer complete statements, and reject an unknown selector before database work.
- Do not add an SQL sanitizer or use escaping, filtering, or validation as a substitute for bound values and compile-time-constant SQL structure.
- Keep the database and object definition source, database/catalog/schema/attachment namespace selection and qualification as supported, namespace and object control-or-ownership model (`NOT_APPLICABLE` when the engine has no ownership concept), and active database authority as separate application facts. PHPThis neither selects nor discourages an engine-default or application-specific namespace.
- Give the runtime database identity only the capabilities required by each named operation and explicitly prohibit namespace, migration, identity-management, authority-management, and administrative actions it does not need. Zero runtime object access is valid before an operation exists; before dependent code receives traffic, execute its exact statements under the runtime identity and safely verify selected prohibited actions against the recorded engine and version. Connectivity and migration success are not authority evidence.
- When a migration, authority-management, or administrative path is adopted, keep its configuration and process entry separate from HTTP, isolate its capabilities where the engine supports that boundary or record the exact effective overlap and residual risk where it does not, name the accountable authority-activation and deactivation owner plus authoritative implementation reference, and record how migration, authority activation, verification, rollout, traffic, later deactivation, and failure recovery are ordered. Use `GRANT` or `REVOKE` only where the selected engine supports that mechanism. Never perform an authority transition from HTTP or invent elevated authority for a deferred path.
- Give every request an explicit `QueryBudget` and bounded `QueryTrace`; do not write one log line per query.
- Give separately named connections explicit budgets and distinct traces; never imply cross-connection transaction atomicity.
- Keep ADR 023 observability application-owned: one visible front-controller coordinator and injected sink, one generated 128-bit lowercase-hex correlation ID propagated as `X-Request-ID`, at most eight finite code-owned database sources, and exactly one failure-isolated sink invocation attempt after response selection. Do not move terminal observability into an application-owned request-handler decorator or add core event/sink/coordinator types, a logger facade, global helper, generic or framework logging middleware, discovery, per-query I/O, or hidden `Connection` instrumentation.
- Treat HTTP response caching and server-side data caching as separate application policies before mechanisms. Do not add a generic cache API, remember-style callback, automatic query caching, or framework-owned backend abstraction; a future server-side adoption must use a narrowly named typed application service with explicit key, value, lifetime, invalidation, stale-refill, failure, topology, observability, and test policy.
- Keep ADR 028 coordination application-owned and Redis-specific: run current authorization before the tenant-scoped document cache, keep SQLite authoritative, commit before explicit invalidation, accept only the recorded finite stale-refill window, and use a separate `noeviction` Redis endpoint for the owner-token schedule lease. Do not add a core cache or lease API, generic Redis wrapper, transparent caching, hidden retry or renewal, fencing-token claim, or exactly-once claim.
- Keep ADR 024 durable jobs application-owned and SQLite-specific: publish through the same business `Connection` and transaction, parse one bounded versioned envelope, dispatch finitely, sample an explicit clock again before handler work and after success or failure, fence transitions with an unexpired opaque lease token, make the demonstrated database effect idempotent, and process at most one delivery per fresh worker invocation. Do not add core job types, a queue facade, event bus, discovery, transaction callback, hidden retry loop, worker loop, or exactly-once external-effect claim.
- Keep migrations application-owned and engine/version-specific under ADR 043: invoke them only through the sole application console executable and give every separately tracked migration history one finite explicitly owned command, a typed-configuration/process-identity reference to `.ai/configuration.md` and database-authority reference to `.ai/data.md` without combined credentials, inheritance, or fallback. Record one exact initial baseline per history, including every pre-provisioned object, already-present application-managed object, effect, or ledger row, and every required absence; nothing is inferred beyond that recorded baseline. Keep one final concrete coordinator, finite ordered manifest, and bounded ledger per history with unrolled private migration-step methods; checksum each permanent identifier, statement, code-owned binding name/type/literal value or finite binding-derivation policy, and exact ordered application effect; require ledger position, identifier, and checksum; and record any selected additional bounded non-executable metadata and its source. No metadata field selects work, defines order, or authorizes behavior. Record finite exact-engine ledger metadata and explicitly permitted supporting objects, and reject missing, incompatible, or additional unrecorded ledger-related objects before history parsing or pending work. Record each history's engine/version decision, exact transaction and DDL atomicity limits, migration-effect/ledger consistency, partial-failure detection and forward recovery, database-authority reference, per-history compatibility and handoff constraints, output, redaction, and exact-engine evidence separately; `.ai/operations.md` alone owns the application-wide release sequence. Call histories independent only after proving disjoint managed objects, data, authority transitions, and coordination domains; otherwise require explicit shared serialization, release, and recovery ownership plus cross-history partial-deployment evidence. For every supported topology from which a migration writer can run, record one explicit application-local, database/server, deployment, or external coordination or serialization mechanism, its stable identifier/namespace, collision boundary, permissions, and exact scope. Concurrently reachable topologies for one history share an exclusion domain or are pairwise authority-gated, with cross-topology proof. The mechanism becomes effective before ledger bootstrap or creation plus authoritative definition/history validation and remains effective through all checksum-covered effects and either accepted ledger completion or a finite fail-closed failure outcome. No partial state is recorded as applied; detected coordination loss stops before the next mutation, and an expiring or lost owner is fenced from later mutations or confirmed terminated with no in-flight work before a successor mutates. The next owner reacquires coordination and re-detects exact state before mutating. Prove application/database coordination with concurrent real-console processes and deployment/external serialization at its owning boundary, including that a bypass cannot obtain the history's migration identity or configuration. Treat migrations as specialized database evolution. For a new adopting application, recommend `src/Database/Migrations/` and its matching application namespace; accept any coherent application-owned alternative recorded in `.ai/migrations.md`. Never enforce a migration path through the checker, discover work from directories, silently relocate an established structure, or create an empty migration directory in the database-free skeleton. This placement does not authorize a generic `Database/Queries` directory, repository layer, or alternate SQL execution boundary: request-time SQL remains in the handler or the one justified concrete operation. Do not add a core migration API, per-migration classes, schema builder, DSL, discovery, runtime `.sql` loading, generic database facade, inferred rollback, transaction callback, database call in a loop, HTTP-startup migration, or cross-engine claim.
- Keep the application-context authority split singular: `.ai/configuration.md` owns exact configuration and process identity, `.ai/data.md` owns effective database-authority facts and accountable transition ownership, `.ai/migrations.md` owns transition implementation and per-history constraints, and `.ai/operations.md` owns the application-wide sequence and operational runbooks. Coordination records and evidence cover exact creation, acquisition, use, and release permissions or authority.
- Keep ADR 027 as the accepted application-owned SQLite reference proof, not a universal migration mechanism. When an application deliberately adopts that exact SQLite shape, commit each migration with its ledger row in its own explicit transaction under one same-host nonblocking `flock`, roll back the active transaction after failure, preserve earlier commits, and prove those SQLite and host-topology claims. Do not impose its transaction, file-lock, or rollback mechanics on another engine or topology.
- Keep optional WebSockets application-owned and separate from PHPThis HTTP: select one mature third-party runtime, compose its process explicitly, parse each bounded message into one operation-specific final readonly command, run current authentication and authorization before one narrowly named typed operation and later protected effects, await bounded sends, and record finite connection, backpressure, lifetime, shutdown, redaction, supervisor, and scaling policies. Do not add core WebSocket, event-loop, connection-manager, daemon, or supervisor types. Do not adapt frames into PHPThis `Request` or `Response`. Do not add generic middleware, gateways, channels, broadcasters, pub/sub, context, discovery, hidden retry, replay, acknowledgement, resume, or exactly-once claims.
- Parse external `mixed` data once through a named factory into a concrete final readonly boundary value: an operation-specific request or command for inbound data, or a projection for returned data. Use only that concrete value in downstream operation behavior. Add a typed operation seam only for an independently meaningful business or transaction responsibility; then prove rejected input makes zero seam calls and performs no operation-owned downstream I/O or mutation.
- Reject missing and unknown fields, distinguish missing from explicit `null`, validate deterministic types and recorded effective bounds before conversion, and never use a scalar cast, normalization, or sink escaping as validation.
- Treat `composer check` as the PHPThis validity gate and repair diagnostics by their stable profile rule or PHPStan identifier.
- Do not suppress a profile rule with a baseline, inline ignore, wildcard exclusion, or comment exemption.
- Never execute a database statement inside `for`, `foreach`, `while`, or recursive traversal.
- Do not add an ORM, Active Record, lazy loading, query builder, service container, facade, global helper, macro system, or dynamic proxy.
- Do not use magic methods other than `__construct`.
- Do not introduce a second way to perform an existing framework task.
- Do not invent product intent, approval, or unsupported PHPThis behavior when evidence is missing.
- Update the relevant Markdown guide with any public behavior change.
- Keep PHPStan at `level: max`; do not add a baseline, broad ignore pattern, or weaker analysis level.

## Verification

Install development dependencies once, then run the canonical check from the repository root:

```bash
composer install
composer check
```

`composer check` runs repository guardrails, maximum-level PHPStan analysis with strict rules, and tests.

For database behavior, also prove that query count stays constant when fixture cardinality increases, inspect the structured query trace for repetition, submit adversarial values through bindings, and reject unsupported structural selectors before database work. A small fixture passing under a query budget is not enough evidence.

For database authority, execute every intended statement under the runtime identity against the exact engine and version before its operation receives traffic. Safely verify selected prohibited namespace, DDL, identity or role, authority-management, administrative, migration-ledger, and unrelated-object actions. Record how effective authority resolves using only applicable engine concepts, such as direct, role or inherited, public or default, database or global, ownership-chain, IAM, or filesystem and process authority; use safe engine-supported inspection instead of destructive denial probes on shared or production data. Prove HTTP cannot obtain elevated configuration and stop dependent rollout when migration, authority activation, or verification fails. Remove or drain dependent code before deactivating authority or removing a namespace it still needs.

For terminal request summaries, prove success, mapped failure, known denial where applicable, unknown failure, identifier grammar and `X-Request-ID` propagation, bounded distinct database sources, duplicate-query and budget-overrun evidence, omission of all request and SQL values, exactly one sink invocation attempt, and an unchanged response when the sink throws. Never describe an invocation attempt as durable delivery.

For a finite collection path, exercise every accepted sort and bounded-list cardinality, prove its recorded omitted and empty-input behavior with exact statement counts, traverse equal sort values in both directions without gaps or duplicates in a static fixture, and record whether cursor traversal is a snapshot. Tenant predicates, PHT006, and adversarial binding probes remain path-specific evidence rather than universal authorization or injection proof.

Keep application configuration outside framework core. One application-owned PHP file reads every exact process-environment key and validates it into adopted process-specific final readonly values before application-controlled I/O. When a process or infrastructure consumer is adopted, inject only its concrete value through visible composition; configuration-only scope instead records connection composition as deferred and proves its parser in a child process. Do not add a framework configuration service, string-keyed bag, global helper, facade, service container, automatic dotenv loader, secret-manager abstraction, or credential fallback between adopted runtime and elevated processes.

For an application-owned request-handler decorator, prove its visible route-local construction and exact nesting order, zero-or-one downstream invocation with the identical `Request`, short-circuit and delegated outcomes, unchanged exception propagation, explicit immutable response replacement when present, and the bounds and ordering of every named side effect. Also prove that it does not wrap or take ownership from `Application`, `RequestBoundary`, the terminal coordinator, `ResponseEmitter`, or the concern-specific session, cache, request-policy, and observability boundaries.

For an application-owned durable-job path, prove commit-visible publication and rollback exclusion, finite envelope parsing and dispatch, idle and success outcomes, exact bounded backoff from freshly observed failure time, completion rollback when handler time reaches lease expiry, lease expiry and stale-token fencing, terminal attempt and poison handling, duplicate idempotent effects, real process termination and post-expiry recovery, one delivery per fresh process, complete diagnostic redaction, and constant statement bounds across materially different queue cardinalities. Never describe at-least-once delivery as exactly once.

For an application-owned migration path, prove each history begins at its exact recorded initial baseline, validates its accepted ledger prefix, and applies every pending checksum-covered statement, code-owned binding value or finite binding-derivation policy, and DDL, data, and authority effect in manifest order. Prove the exact position/identifier/checksum ledger plus every selected bounded metadata value, finite exact-engine ledger-metadata acceptance, rejection of incompatible or additional unrecorded ledger-related objects, unchanged-history no-op rerun, statement and binding/policy drift rejection before pending work, malformed and overflowing ledger rejection, and every supported migration-writer topology. Prove each coordination identifier/namespace, collision boundary, permissions, and protected interval; application-local and database/server mechanisms use concurrent real-console processes, while deployment or external serialization is proven at its owning boundary. Cover every concurrently reachable cross-topology pair through shared exclusion or pairwise authority gating. Evidence must show the mechanism is effective before ledger bootstrap or creation plus authoritative definition/history validation and remains effective through all checksum-covered effects and either accepted ledger completion or a finite fail-closed failure outcome. Prove no partial state is recorded as applied, detected coordination loss stops before the next mutation, and an expiring or lost owner is fenced or confirmed terminated with no in-flight work before successor mutation; the next owner reacquires coordination and re-detects exact state before mutating. Also prove each history's separately named configuration factory/final readonly type/process identity has no fallback or combined credentials, its recorded engine/version transaction and DDL atomicity limits and ledger consistency hold across every failure point, and partial-failure recovery, exact redacted console bytes, and complete absence from HTTP startup. For multiple separately tracked histories, prove disjoint managed objects, data, authority transitions, and coordination domains before calling them independent; otherwise prove shared serialization/release/recovery plus cross-history partial-deployment behavior. When the application adopts the ADR 027 SQLite reference shape, additionally prove its explicit timestamp, nonblocking same-host `flock` contention, per-migration rollback with earlier commits preserved, and lock cleanup. Do not generalize that SQLite evidence to another engine or host topology.

For an application-owned WebSocket path, prove pure parser, current-policy, typed-operation, encoding, resource-bound, and redaction behavior plus real child-process and socket readiness, accepted and denied handshakes, ordered messages, malformed and oversized traffic, transport closes, connection and rate bounds, heartbeat, idle and absolute lifetime, backpressure, reconnect without unrecorded replay, occupied-listener failure, signal shutdown, bounded process exit, and cleanup. Prove frames never become PHPThis HTTP request or response values, and keep production TLS, proxy, supervisor, capacity, scaling, and availability claims outside evidence that did not exercise them.

For an application that adopts caching, preserve the same database proof with a cold cache. A warm-cache result does not prove bounded SQL behavior.

For an application-owned Redis lease, prove nonblocking acquisition, contention, explicit renewal, stale-owner rejection, owned release, backend failure, process termination, and expiry recovery against the recorded Redis topology. Treat the token as an ownership check rather than a fencing token, and retain the protected operation's independent correctness and idempotency boundaries.
