## Shared migration rules

Database migrations are specialized application-owned database evolution. Read installed `vendor/phpthis/framework/docs/migrations.md` before adoption. When the application has no established migration layout, PHPThis recommends `src/Database/Migrations/` and the matching `{{APPLICATION_ROOT_NAMESPACE}}\Database\Migrations` namespace. Record the actual adopted directory and namespace above. A coherent consumer-selected alternative is authoritative; neither PHPThis nor the consumer checker enforces the recommendation or discovers migration files, and AI must not relocate an established structure without explicit human approval.

When multiple named database connections have separately tracked migration histories, retain one application console executable but record each history's source path, namespace, finite explicit command, engine/version and decision, initial baseline, final coordinator, manifest, ledger, stable typed-configuration/process-identity reference to `.ai/configuration.md`, stable database-authority reference to `.ai/data.md`, atomicity, supported writer topologies, coordination, recovery, output, evidence boundary, and any application-selected connection-owned subdivision. Call histories independent only after proving their managed objects, data, authority transitions, and coordination domains are disjoint. Intersecting histories require an explicit dependency order, one shared exclusion or serialization boundary, every cross-history partially completed state, and application-wide forward recovery. Never combine migration credentials or allow one history to obtain another's identity/configuration. Do not prescribe or create subdivisions for a single-database application or a connection without a separately tracked migration history.

For each history, keep every migration step in one final application-owned coordinator with one permanent identifier, complete engine-specific compile-time-constant statements at direct `Connection` calls, explicit named bindings where data exists, and a checksum covering the identifier, every statement, every code-owned binding name/type/literal value or finite binding-derivation policy, and every exact ordered DDL, data, and authority effect the step owns. Name and invoke every private step method explicitly in that history's finite ordered unrolled manifest; no database call occurs in a loop.

For every supported topology from which a migration writer can run, record one concrete application-local, database/server, deployment, or external coordination or serialization mechanism and only the hosts or runners it actually covers. Record its stable application/environment/history identifier or namespace, collision policy, exact creation, acquisition, use, and release permissions or authority, and loss behavior. All topologies that can reach one history share one exclusion domain or use pairwise authority gating that makes overlap impossible, with evidence crossing every reachable pair. The mechanism becomes effective before ledger bootstrap or creation plus authoritative definition/history validation, remains effective through every checksum-covered effect and either accepted ledger completion or a finite fail-closed failure outcome, and rejects missing, incompatible, or additional unrecorded ledger-related objects before history parsing or pending work. Never record a partial state as applied. Detected coordination loss stops before the next mutation. When ownership can expire or be lost, a successor cannot mutate until prior in-flight database work is fenced, the prior session/work is confirmed invalidated or terminated, or another exact-engine exclusion boundary proves termination; an exited client or post-statement check alone is insufficient. The next owner reacquires coordination and re-detects exact state before later work. Prove application/database mechanisms with concurrent real-console processes; prove deployment/external serialization at its owning boundary, including that a bypass cannot obtain migration identity/configuration. Per history, record the exact engine/version's transaction, implicit-commit, and DDL atomicity behavior, how every checksum-covered effect and ledger record remain consistent across every failure point, and how each partial state is detected and recovered without editing applied history. The finite history command uses its own fresh separately composed typed state and never runs during HTTP startup. Migration success alone does not prove runtime authority is active. If an authority transition is owned by a migration, its complete engine-supported transition statements are visible and checksum-covered with that step; otherwise a separately authorized application stage or named external provisioning source owns it. `GRANT` and `REVOKE` are transition forms only where the engine supports them. Activate and verify required authority before dependent code receives traffic, stop the dependent stage on failure, and drain or remove dependent code before authority deactivation or namespace/object removal.

ADR 027 remains the accepted SQLite reference proof. Only when this application deliberately adopts that exact shape, commit each pending migration and its ledger row in one visible transaction, roll back only an active failed transaction while preserving earlier commits, hold one application-private nonblocking same-host `flock` with release in `finally`, apply the stricter SQLite ledger-definition proof, and use its `applied` or `up_to_date` success names. Those mechanics and names are conditional SQLite/example policy, not portable defaults.

Do not add a framework migration API, schema builder, DSL, discovery, runtime `.sql` loading, stored executable SQL or class names, generic database facade, permission helper, role registry, runtime authority introspection, automatic privilege hook, transaction callback, inferred down migration, hidden retry, portable-DDL claim, or cross-engine coordination abstraction. Every adoption requires separate engine/version transaction and DDL atomicity limits, ledger-consistency design, coordination, privilege, recovery, and integration evidence.
