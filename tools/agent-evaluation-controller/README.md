# PHPThis Agent Evaluation Controller v0.2

This maintainer-only controller implements the accepted ADR 048 lifecycle:

```text
prepare -> generate -> freeze -> score -> validate -> retain -> cleanup
```

It remains under export-excluded `tools/` and changes no framework runtime, public API, Consumer Contract, Strict Profile, application checker, skeleton requirement, or Composer dependency. Issue #68 adds the opt-in real adapter to the synthetic controller introduced by #42. The accepted [ADR 048](../../docs/decisions/048-isolated-agent-evaluation-controller.md) remains the historical decision; it is not rewritten as implementation evidence.

## Fixed composition

`tools/agent-evaluation-controller.php` explicitly requires, in order:

1. `contract.php`
2. `workspace.php`
3. `process.php`
4. `codex.php`
5. `gemini.php`
6. `scoring.php`
7. `controller.php`

There is no module or task discovery, runner selector, provider facade, dependency-injection container, arbitrary command setting, or arbitrary output-path setting. `process.php` is the only controller file that owns native process primitives. The explicitly versioned task inventory remains the sole task authority. The legacy smoke command in v0.2 accepts only `change.simple-ping` revision 29 with `comparative_claims: false`. Issue #69 separately admits the three pinned v2 comparison tasks through the same lifecycle and fixed native process owner. Issue #73 introduces the Gemini evaluation adapter (`gemini-exec` and `fake-gemini`).

## Ordinary checks

```bash
composer test:agent-evaluation-controller
php tools/agent-evaluation-controller.php validate
```

The ordinary self-test exercises the deterministic test-only `fake-codex` and `fake-gemini` lifecycles and pure proxy protocol controls. It performs no model request, needs no credential or OCI engine, contacts no external endpoint, and executes no AI-authored candidate. `composer check` and normal CI retain that synthetic route. These tests prove controller logic, not container containment or real-model behavior.

A legacy `run <run-id>` without its explicit live configuration still fails with `AGENT_EVALUATION_CONTROLLER_LIVE_CODEX_UNAVAILABLE` or `AGENT_EVALUATION_CONTROLLER_LIVE_GEMINI_UNAVAILABLE`. Missing or unverifiable live controls fail closed; there is no direct-host, native macOS, `sandbox-exec`, arbitrary-shell, discovered-runner, or second-runner fallback.

## Live execution boundary

The accepted real runners are `codex-exec` and `gemini-exec`, each a fixed invocation of the pinned runner executable in the generation image. Exact model and reasoning/thinking settings come from the reviewed profile, with a fresh bounded home and runner state directory. The runner receives no upstream credential, ambient host environment, Git metadata, checkout, home mount, or engine socket. Optional client integrations and network tools are disabled in its fixed configuration; those settings do not replace OCI containment.

For `codex-exec`, the host proxy exposes the Responses create and token-counting operations. For `gemini-exec`, the host-side `gemini-api-run-proxy` credential broker mediates requests to Google Gemini models, requiring a configured `thinking_budget` (`low`, `medium`, `high`, `max`, or `off`).

Generation uses Docker networking `none`. Its only provider connection is a loopback HTTP relay in the container, carried over the controller-owned standard-input/output channel to the host-side `responses-api-run-proxy`. There is no candidate network route to a host listener, Docker bridge, DNS server, or upstream API. The relay disables dumpability before starting candidate processes; relay failure or candidate interference fails the run.

The host proxy exposes only the selected Responses create operation. It rejects a different model or reasoning setting, stateful server conversation references, hosted tools, remote media, duplicate JSON members, unexpected paths, and unbounded bodies. Before each upstream create request, it calls the fixed Responses input-token-count endpoint, reserves the counted input plus bounded maximum output against the shared run allowance, and permits no concurrent pending reservation. The upstream destinations are fixed official count/create endpoints, with no redirects or retries. Each SSE response is buffered within a 4 MiB transport bound and released only after terminal model/usage validation. An ambiguous request revokes the run and retains its reservation; an exhausted quota fails the run.

The 128-create limit bounds total accepted response traffic to 512 MiB, processed one response at a time. The downloader independently rejects a body exceeding 4 MiB. For bodies reaching proxy validation, the ledger checks the current request count, individual body size and prior byte total before addition; oversized bodies or inconsistent counters fail at `response_bytes` and retain their unsettled reservations. This transport bound is independent of the profile's 4 MiB retained command-output allowance. Earlier implementations applied the single-response ceiling cumulatively and could reject an individually admissible response before validating its usage. A later fix cannot recover unretained terminal evidence or settle that historical reservation; new execution requires a fresh implementation snapshot and configuration.

The candidate-facing operation is exactly `POST /v1/responses`. The host additionally calls `POST /v1/responses/input_tokens` as the fixed quota prerequisite. This interprets ADR 048's single-operation boundary as the candidate's exposed authority; it does not claim that only one upstream endpoint is called. The implementation follows the official [token-counting contract](https://developers.openai.com/api/docs/guides/token-counting) and [reservation/uncertain-request guidance](https://developers.openai.com/cookbook/articles/per_run_spending_controller_responses_api). Exact CLI/configuration fields were checked against the pinned client and official [non-interactive Codex](https://learn.chatgpt.com/docs/non-interactive-mode) and [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) documentation. Ordinary smoke and comparison runs enforce token accounting; their recorded spending ceilings are reviewed bounds. The separately admitted calibration mode below also enforces a fixed monetary reservation policy.

Proxy totals are the authority for token usage. Runner-reported usage is separately retained; missing categories remain unknown. Candidate events and command text are untrusted evidence. The report does not infer zero attempted sockets from a network-disabled container or claim complete telemetry for every denied action.

The Codex proxy ledger also retains optional `request_diagnostics`, at most 128 records for requests reaching reservation. Each has `authority: diagnostic_only`, the observed request ordinal, counted input and remaining cumulative tokens, reservation outcome (`reserved` or `rejected`), reserved output, a finite rejection reason, and nullable settled usage. Input-count parsing failures leave counts unknown; upstream count failures never reach reservation. Rejected counts preserve the token or spending limit that blocked create. Validated terminal usage alone populates the input/output/cache/reasoning fields, including settled failed or incomplete responses; ambiguous responses leave them `null`. These observations contain no request text, provider payload, or credentials, do not affect admission or scoring, and cannot reconstruct missing details in older evidence. Cached input remains part of the cumulative token total. The existing totals and reservations retain accounting authority.

Response-validation diagnostics retain a response hash, a finite rejection stage, and bounded structural observations separately from settled accounting. Observed terminal status, identity checks, response identifier, or integer usage fields cannot release a reservation or establish a validated charge. Raw response text, tool arguments, arbitrary error messages, credentials, and headers are not diagnostic fields. A rejected response still blocks the run and retains any unsettled reservation; diagnostics neither retry it nor relax the model, tier, usage, or token-budget checks.

`generation-process.json` may additionally contain `upstream_failure`, absent or `null` when no such observation is retained. A present record has exactly six fields: `schema_version: 1`; `operation: "input_tokens" | "responses"`; `category: "http_status" | "curl" | "response_limit"`; `http_status` as an integer from 100 through 599 or `null`; `curl_code` as an integer from 0 through 999 or `null`; and boolean `response_limit_exceeded`. A locally overflowing response callback takes precedence, followed by failed cURL execution, then a non-200 HTTP status. The fixed failure marker remains `AGENT_EVALUATION_CONTROLLER_PROXY_UPSTREAM_FAILED`.

These observations retain no bodies, headers, URLs, `curl_error` text, or arbitrary messages and do not establish the underlying cause. An `input_tokens` failure occurs before reservation; a `responses` failure preserves the pending reservation and unknown aggregate usage. Existing failure precedence, budgets, settlement, and no-retry behavior remain unchanged. Evidence admission rejects malformed present records, including failed attempts, but accepts absent older records without reconstructing a diagnosis. Pure/replay controls and the six deterministic [OCI upstream-failure controls](oci/README.md#optional-integration-command) must prove this boundary; they are not paid evaluation results.

An SSE event-identity failure additionally retains the data-event ordinal, a finite identity reason and type family, a header/type comparison, and bounded presence/kind/length/hash metadata for the event name and JSON `type`. Missing, malformed, empty, mismatched, and unsupported identities can therefore be distinguished without retaining arbitrary names or payloads. This observation exists only for that rejection stage and resets before the next response; it neither reinterprets a conflicting event as a provider error nor changes SSE acceptance. Older evidence with only `sse_event_identity` cannot acquire these missing observations retrospectively. The exact `keepalive` event name is admitted only as ignored transport data after the same header/type identity check. Its payload cannot establish a response, output, usage, or completion. All other unsupported event families still fail closed; a missing or invalid terminal response keeps the request reservation unresolved.

A provider `error` event also retains a separate unvalidated observation of its envelope, recognized error code/type and request-parameter root, and bounded presence/type/length/hash metadata for its error fields. Unknown codes and parameter roots remain unknown. The documented top-level fields take precedence; a nested error object is a diagnostic fallback only when top-level error fields are absent. Parameter suffixes and message text are never retained, and these observations cannot establish a charge or make a failed request retryable. The error event and its bounded metadata identify what the provider reported; they do not independently establish its underlying cause.

The recognized billing labels include `credit_balance_exhausted` and `insufficient_quota`. OpenAI documents `credit_balance_exhausted` as exhausted organization prepaid credits; further generation requires restoring API credits. A billing error still leaves unreported usage unknown and never clears a pending reservation or authorizes a retry. See the [official error-code guide](https://developers.openai.com/api/docs/guides/error-codes#api-errors).

The separate [calibration v1](../agent-evaluation/calibration-v1.md) admits six runs with 200,000 cumulative tokens and an enforced USD 1.00 token-charge limit each. `calibration-prepare`, `calibration-run`, and `calibration-report` share the existing lifecycle and require the explicit calibration policy; ordinary comparison/smoke commands retain their original budgets. Before each calibration request, integer monetary reservations use uncached input plus bounded maximum output, then settle only validated terminal usage with validated cache discounts. Missing cached usage is charged conservatively for admission. Unknown responses retain both reservations. The six fixed slots bound total allocation to USD 6.00; calibration records and reports remain separate and contain no comparison rates.

[Calibration v2](../agent-evaluation/calibration-v2.md) keeps that monetary policy and admits exactly 1,000,000 cumulative tokens with a separate 200,000-token counted-input ceiling per request. Its new prompt suffix gives concrete targeted discovery instructions. The configured revision flows through preparation, generation, evidence validation and reporting; v1 policy/prompt identities stay unchanged. Only the explicit million-token profile selects the 1,000,001 compaction threshold. `model_input_limit` is a pre-create refusal, distinct from cumulative-token and spending exhaustion.

Reporting verifies the six-slot retained ledger, distinct regular file identities, exact starts, and each final attempt's complete evidence inventory. Unplanned entries, orphan scores or execution directories, and omitted or substituted evidence are rejected. Valid interrupted starts, failed preparation, and missing scores remain reportable without implying success. During scoring, each application-check or observation container must have verified cleanup before the next observation starts; a cleanup failure retains the completed prefix and marks remaining observations unavailable.

The launcher verifies digest-pinned generation and scoring image identities and exact PHP, Composer, Python, Codex, and relay identities as applicable. Generation and scoring must use identical PHP and Composer versions. Every candidate/scorer container uses a non-root numeric identity, read-only root, dropped capabilities, no-new-privileges, private PID namespace, and finite CPU, memory, disk, process, wall, and output limits. Unsupported engine controls fail preflight. Scoring uses a distinct image and identity with no Codex or relay.

Local image resolution uses a bounded repository-filtered index and inspects its candidate image IDs. Exactly one inspected image must contain the configured immutable repository digest; tags and bare image IDs remain invalid configuration inputs. Every container is created from that verified image ID and its inspected image must match. This avoids a second repository-reference lookup during creation while preserving the reviewed digest and actual image identity. Missing, ambiguous, malformed, or mismatched identities fail before candidate execution; the controller does not pull or rebuild an image.

The candidate filesystem lives in a bounded tmpfs-backed Docker volume. A fixed, read-only, no-network holder keeps that volume mounted after generation stops, so the controller can inspect output without restarting the candidate. Generation is stopped and its PID cleared before export; all exported paths, types, modes, counts, and sizes are validated before import. The existing workspace policy then rejects protected/unlisted changes, links, special files, unexpected executables, and edit-limit violations. The holder is infrastructure, not another runner. Host import explicitly sets validated directories to `0755`, independently of the controller process umask, before the unchanged freeze policy validates them. Private control and evidence roots remain private.

Prepared package bytes are immutable and must contain no files in `vendor/.phpthis`. The controller creates that empty mount point only in its copied dependency volume. The checker-owned `vendor/.phpthis` cache and the application's `tmp/` test scratch space use separate bounded temporary mounts in generation and scoring. Their contents are excluded from the frozen source. Export accepts only the exact empty underlying infrastructure mount points and rejects unexpected nested files there. Candidate, temporary, cache, and shared-memory allocations are included in the fixed disk allowance. No dependency installation or candidate-owned Composer script runs during preparation.

The tmpfs sizes enforce storage capacity. End-of-run free-space readings are snapshots, not durable records of every failed write: a candidate could encounter `ENOSPC`, delete a file, and leave free space again. The controller rejects an observed full mount and retains this telemetry limit; it does not infer zero earlier disk-exhaustion attempts. Generation memory and PID exhaustion use persistent cgroup event counters. Scoring retains actual container exits and Docker's OOM state; that state alone cannot establish zero earlier child-level exhaustion attempts. Wall, output, and model-token allowance exhaustion terminates the run.

## Freeze, scoring, retention, and cleanup

Generation ends before output is exported and frozen. The controller validates the canonical candidate tree and patch, creates the read-only scoring copy, and destroys the generation container before introducing any scorer. Fresh scoring containers have no network, runner, relay, key, checkout, or writable frozen source; their cache and test scratch mounts start empty. They execute the unchanged application `composer check` and exact public scorer in separate fixed command slots; actual exits and bounded streams determine the result. A container startup failure is inadmissible. Candidate-owned checks never replace the controller-owned public scorer.

The controller validates unchanged v0.1 run and score records and retains bounded hashed task/prompt/profile, source/dependency identities, proxy and process observations, candidate patch/manifest, scoring results, validation, and cleanup evidence. Failed attempts retain phase and available structural evidence; a preparation failure cannot fabricate a completed generation record. The source and dependency identities remain linked to the selected task, not a later task registry.

Only recognized freeze failures add `primary_failure.reason_code`, selected from fourteen code-owned tags in `agentEvaluationControllerFreezeFailureReason()`. They distinguish baseline/dependency mutation, directory or file policy changes, and patch-limit violations. The classifier accepts only exact `RuntimeException` instances with those fixed codes; unknown exceptions and subclasses remain unclassified. It never derives a reason from exception text or candidate paths. Existing phase, class, `termination_reason`, cleanup precedence, and failed-attempt status are preserved. This bounded diagnostic is not a new admissibility decision or containment proof.

Cleanup runs after success, failure, or catchable interruption (`SIGINT`/`SIGTERM`). It stops and destroys only run-owned containers and volumes, checks their absence, removes temporary controller/proxy state and disposable workspaces, and retains the approved evidence. Container destruction establishes that candidate descendants are gone. Cleanup failure preserves the primary failure and makes an otherwise passing run fail.

Before each OCI resource creation, the controller persists its exact owner, run ID, and pending resource name in a bounded private `owned-resources.json` ledger. It checks ownership before removal and updates the ledger after verified destruction. The final ledger and cleanup result are retained even when cleanup fails. A failed standalone preflight preserves its control directory when resources remain unresolved.

A timed-out or interrupted Docker create request may still finish in the daemon after its client exits. Such names remain under `pending-creation-*` roles, along with the run's dependent volumes, and cleanup is unverified. A momentarily absent name does not settle that operation. Manual recovery must reconcile the pending creation before releasing those volumes.

`SIGKILL`, host failure, or an unavailable Docker daemon can prevent cleanup. Such an attempt has no successful cleanup claim. Recovery must inspect the private temporary `phpthis-oci-control-*` directory's ledger, or the retained evidence ledger, and select resources with **both** recorded `org.phpthis.evaluation.owner` and `org.phpthis.evaluation.run_id` labels. Verify each exact name and both labels before removing it; do not use a global Docker prune. Confirm absence afterward and record that manual recovery separately from the original run's immutable evidence.

The ordinary synthetic proof still establishes only original-process-group cleanup and cannot contain a native descendant that escapes its process session. The opt-in OCI proof must demonstrate the real container boundary separately. A deterministic Responses fixture using the real Codex executable is OCI/client integration evidence, not a real model trial. A paid public smoke pass still has `comparative_claims: false`; its public scorer is not a confidential holdout.

Stable boundary markers:

- `AGENT_EVALUATION_CONTROLLER_VERSION(2)`
- `AGENT_EVALUATION_CONTROLLER_OCI_ONLY`
- `AGENT_EVALUATION_CONTROLLER_FAKE_RUNNER_CI_ONLY`
- `AGENT_EVALUATION_CONTROLLER_NO_NATIVE_FALLBACK`


## Common-change comparison preparation

The separate [bounded comparison protocol](../agent-evaluation/comparison-v1.md) owns the fixed 60-slot design and limits. The following commands use the same controller; they do not install another runner:

```bash
php tools/agent-evaluation-controller.php comparison-prepare /absolute/path/comparison-configuration.json
php tools/agent-evaluation-controller.php comparison-run /absolute/path/comparison-configuration.json
php tools/agent-evaluation-controller.php comparison-report /absolute/path/comparison-configuration.json
```

`comparison-prepare` validates the frozen implementation/protocol, all six task/condition preparations, source and installed documentation identities, model/settings, exact images/toolchains, private holdout separation, approval record shape, dated pricing, and expanded schedule. It reads no credential, starts no OCI engine, creates no campaign, and makes no model call. Its output contains planned attempts only. A pending approval uses a zero spending ceiling; the document is reviewable preparation, not authorization.

The campaign configuration uses schema version 1 with exact fields `campaign_id`, `source_revision`, `protocol_sha256`, `implementation_sha256`, `profile`, `engine`, `approval`, `pricing`, `model_revision_note`, and `inputs`. The shared profile uses condition `comparison-v1`; each of the six input records selects its pinned task and condition and supplies task/source-context hashes, canonical external dependency/lock paths and hashes, installed-context hash, and private holdout path. The code hash binds both entrypoints and both tool directories, in addition to the enclosing source commit. Retained implementation bytes permit reproducing an explicitly frozen development snapshot over that source commit even when the preparation changes had not yet been committed. The full model snapshot is requested where available; an unavailable provider revision stays null with its provenance explanation. Only the task sources and installed packages are supplied as context.

Comparison fixtures compose the one maintainer-owned `tools/agent-evaluation/references/phpstan/` source into each application's `docs/phpstan/` before fixture hashing and source-context validation. The materializer writes separate regular copies; candidates do not share files or writable reference storage. The retained implementation snapshot includes the shared bundle once and resolves it within that snapshot. A source-storage change needs a new implementation identity; revision-5 task/context/base hashes remain valid only after exact materialized byte and mode parity is proved.

`comparison-run` requires accountable approval naming the exact model, 60 runs, and a spending ceiling covering the conservative token-price bound. It then reads the host-only API key. A fresh `agent-evaluation-runs/<campaign-id>/` directory beside the checkout retains the exact configuration and a hash-verified snapshot of both tool directories and entrypoints, all 60 planned records before any request, started records, terminal attempts and scores, and each run's raw evidence. Existing campaign IDs cannot be reused or overwritten. The initial generation may use public checks, but private feedback never causes another generation. Known token/time/output/memory failures remain outcomes and the next slot proceeds only when cleanup passed and the proxy proves no outstanding billed reservation or ambiguous request. Preparation, evidence-retention, uncertain provider, and unresolved cleanup failures stop the campaign. Remaining slots become `not_run`; partial records after an uncatchable host interruption remain visible as missing outcomes. There are no automatic resumes or replacement attempts.

Every real attempt verifies matching PHP/PDO/SQLite identities and the digest-pinned OCI controls. After generation stops and the candidate is frozen, the generation container is destroyed. The protected `composer check` and fixed `evaluation/observe.php` command run without a provider relay, credential, network, private expected answers, or writable frozen sources/dependencies. Only bounded individual case input crosses stdin. Raw output is retained before host comparison; exit zero, printed `PASS`, omitted cases, forged counts, and an absent observation cannot establish success. Accountable human review remains necessary because in-process query instrumentation cannot prove that a candidate did not bypass it.

`comparison-report` revalidates retained identities and hashes and recomputes automated scores from raw observations. Reviewers fill the separate human-review fields in each score record with their identity, decisions, reasons, and genuinely observed effort/intervention metrics; automated fields must remain equal to replayed evidence. The report retains failed and missing slots, component outcomes, token categories, dated estimated charge, context exposure, and unknowns. No correctness rates appear until all 60 outcomes and their required human reviews exist. Preparation and deterministic OCI proofs do not satisfy issue #69's real-trial requirement.
