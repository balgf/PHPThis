# ADR 053: Application-owned Amazon S3 file transfers

Status: accepted

Accountable-human approval: accepted on 2026-08-13 (Asia/Manila). The approval selects the narrow direct-S3 exception and the coordinated Consumer Contract version 13 change recorded here. The same follow-up separately authorizes committing and pushing this repository change to `main` and closing Issue #52. It does not authorize a tag, release, package publication, production AWS mutation, or a claim that a particular consumer has adopted or production-proved the profile.

## Context

ADR 026 accepts one bounded multipart-ingestion and local-file-response path. Consumer Contract version 12 consequently requires visible `move_uploaded_file` durable storage and a full local `200` response, and it excludes remote object stores and pre-signed delivery. Those requirements cannot truthfully describe a server-mediated Amazon S3 `PutObject` followed by a short-lived pre-signed `GetObject` redirect.

The existing local `OPAQUE_BYTES` posture also requires `X-Content-Type-Options: nosniff`. A direct S3 `GetObject` response can override only its documented finite response fields and cannot add that header. Because this profile excludes a PHP proxy and CDN/offload layer, it cannot claim complete equivalence with the accepted local opaque-byte response policy. The accountable human explicitly accepts fixed `application/octet-stream` plus attachment without `nosniff` as a narrow `AMAZON_S3_ADR053` exception; `LOCAL_ADR026` retains `nosniff` unchanged.

Applications nevertheless need a narrow way to preserve PHPThis's explicit security, ownership, failure, and evidence philosophy when they deliberately select Amazon S3. A generic storage interface, framework AWS client, interchangeable “S3-compatible” claim, or static checker that pretends to certify an external service would hide the relevant semantics.

## Decision

PHPThis adds one optional application-owned profile named `AMAZON_S3_ADR053`. It reuses ADR 026's bounded PHP multipart normalization and the common application policy before storage, but replaces only the durable local move and local response path with the exact Amazon S3 path below. `LOCAL_ADR026` remains the accepted local profile and ADR 026 otherwise remains unchanged.

The first S3 profile is intentionally finite:

- PHPThis remains on PHP 8.4.x. The adopting application pins `aws/aws-sdk-php` exactly to `3.392.1`, `guzzlehttp/guzzle` exactly to `8.0.2`, the S3 API model to `2006-03-01`, and the SDK-required JSON, PCRE and SimpleXML extensions plus the selected cURL extension/runtime; PHPThis, its skeleton, and its example add no AWS dependency.
- One environment selects one AWS commercial-partition account, one region, one general-purpose regional private bucket with an exact lowercase DNS-compatible no-dot name that rejects AWS's reserved `xn--`, `sthree-`, `amzn-s3-demo-`, `-s3alias`, `--ol-s3`, `--x-s3`, and `--table-s3` forms, one exact expected account identifier, and one customer-managed same-account/same-region single-Region AWS KMS key ARN with a lowercase UUID key ID, `SYMMETRIC_DEFAULT`, `ENCRYPT_DECRYPT`, `AWS_KMS` origin, Enabled state and 365-day automatic rotation. KMS aliases, `mrk-` multi-Region key IDs, external/custom key-store origin and disabled/pending-deletion keys, directory buckets/S3 Express, access points, Multi-Region Access Points, Outposts, transfer acceleration, custom endpoints, other partitions, and arbitrary S3-compatible services are excluded.
- Application composition directly constructs Guzzle `8.0.2`'s cURL-only `CurlHandler` with `TransportSharing::NONE`, a Guzzle client with redirects and environment proxies disabled, and the AWS SDK's Guzzle handler, then passes that exact handler to the S3 client. It uses the exact region, API version, legacy defaults mode, Signature Version 4 over HTTPS as the sole auth preference, disabled endpoint discovery/request compression/client monitoring/app identifier/stats, enabled parameter validation, one explicit named provider wrapped by `CredentialProvider::memoize`, shared-configuration loading disabled, configured-endpoint environment overrides ignored, path-style and accelerated/dual-stack endpoint selection disabled, one code-owned hash-pinned readable regular non-symlink CA bundle, debug disabled, finite connection and operation timeouts, and SDK retries disabled with `retries => 0`. The provider source reads the manifest-bound `$configuration->credentialSource`; neither `CredentialProvider::defaultProvider` nor `CredentialProvider::chain` is permitted. The complete lockfile and immutable deployment image pin transitive dependencies and the PHP/ext-curl/libcurl/TLS tuple. Request values and ambient extension, endpoint, proxy, telemetry or CA settings never select credentials, transport, region, endpoint, bucket, prefix, encryption, or retry policy. Provider-specific fetch, HTTP, timeout, retry, lifetime, refresh, skew and outage facts remain application behavior, real-service and deployment evidence, with explicit `N/A` where the selected provider has no such mechanism.
- Deployment enables all four S3 Block Public Access settings, `BucketOwnerEnforced` object ownership, bucket versioning exactly `Enabled` and never suspended, Requester Pays disabled, MFA Delete disabled, Object Lock/legal hold disabled and not applicable, no S3 replication, no external backup/restore, no S3 Lifecycle rule or action whose filter can cover `private-documents/v1/`, a non-TLS deny, and least-privilege separate upload/validation, download-issuance, reconciliation, and deletion capabilities. The upload/validation role has object-scoped `s3:PutObject` and `s3:GetObjectVersion`; the pre-signing role has object-scoped `s3:GetObjectVersion`; the reconciler has `s3:ListBucketVersions` constrained by `s3:prefix` plus object-scoped `s3:GetObjectVersion`; and the deletion role has object-scoped `s3:DeleteObjectVersion`, never `s3:DeleteObject`, with the constrained list/read permissions only if that process owns post-delete observation. Each gets only its real-test-proved KMS actions. Server-executed `PutObject`, `HeadObject`, `ListObjectVersions`, and SDK `DeleteObject` requests set `ExpectedBucketOwner`. A browser top-level navigation cannot supply that signed request header, so the pre-signed GET instead relies on the fixed bucket/key/version, issuance role and bucket policy, and expected AWS regional hostname; evidence verifies the account and bucket before release.
- The reference content posture is an S3-specific `OPAQUE_BYTES` variant. It stores a fixed code-owned object name and serves only a fixed `application/octet-stream` attachment. Direct S3 delivery cannot add `X-Content-Type-Options: nosniff`; Contract version 13 accepts that missing header only as this profile's narrow exception, not as an inherited safety claim or a change to `LOCAL_ADR026`. `INSPECTED_CONTENT` remains possible only after an application records and proves its separate complete inspection definition; it is not covered by this reference.

The protected upload keeps this visible sequence: `authenticate -> resolve tenant when applicable -> authorize upload -> validate CSRF when applicable -> admission -> atomic quota reservation -> storage`. It accepts one bounded normalized PHP multipart upload, verifies the PHP temporary-file provenance and actual byte count, computes SHA-256 over those temporary bytes, and generates a 128-bit lower-case hexadecimal identifier. The only object-key grammar is `private-documents/v1/{32-lowerhex}/content`. The application records exact request/file, principal, tenant, deployment, object-count, retained-byte, request-rate, concurrency, egress, request-cost, and storage-cost bounds plus one atomic reserve/commit/release/reconcile owner; every inapplicable principal or tenant dimension is explicit.

The application durably creates a `pending` metadata record and quota reservation before making exactly one SDK `PutObject` attempt with the one configured bucket and generated key, `ContentLength`, `StorageClass: STANDARD`, both `ChecksumAlgorithm: SHA256` and the base64 SHA-256 checksum, `IfNoneMatch: *`, explicit customer-managed `aws:kms` encryption and exact key ARN, fixed metadata, and `ExpectedBucketOwner`. A successful response must supply one non-empty exact `VersionId` and `ChecksumSHA256` exactly equal to the submitted base64 SHA-256; a missing or mismatched field remains non-serving in `reconciliation_required`. Response encryption is then validated on the retained object rather than inferred from request intent. The application publishes `stored` only after that response validation, then issues one exact-version server-side `HeadObject` with `ChecksumMode: ENABLED` and `ExpectedBucketOwner` to validate retained SHA-256, size, encryption and KMS-key facts before publishing `accepted`. Because S3 omits the `StorageClass` response field for STANDARD objects, acceptance requires that field to be absent, together with absent `ArchiveStatus`, `Restore`, and `Expiration` indicators; the real-service test pins the exact SDK `3.392.1` result shape. ETag is not treated as a universal content digest. S3 conditional creation evaluates the current version and may succeed when that current version is a delete marker, so an application identifier and key is never reused even after deletion. A definite `412` transitions this record to `failed` with the code-owned reason `failed_collision`, releases only this request's reservation, emits the recorded security/operations event, and never inspects, adopts or deletes the pre-existing object. A concurrent `409` remains an ambiguity requiring reconciliation. The operation never replays `PutObject` for that key; any later authorized semantic attempt receives a new identifier, key and quota reservation.

Application metadata uses only the finite states `pending`, `stored`, `accepted`, `failed`, `reconciliation_required`, `deletion_pending`, and `deleted`. Database/quota state and Amazon S3 are separate systems: no transaction spans them. Every Put follows a durable pending row/key/reservation, so the bounded reconciler owns an object still linked to that record or a post-Put metadata-transition failure. Total authoritative-row loss is outside its fault envelope and goes to a named database restore/security incident policy; no broad S3 listing may infer ownership, adoption or deletion. A timeout, disconnect, missing or contradictory response, or process death around a write or delete enters `reconciliation_required` or remains `deletion_pending`. After local request termination, one named bounded reconciler with separate least authority makes exactly one retries-disabled finite-timeout `ListObjectVersions` call using the fixed bucket, full-key Prefix, `MaxKeys: 2`, and expected owner; it rejects non-equal keys, markers, multiples, truncation and malformed or ambiguous results before exact-version Head validation. An empty listing remains non-serving with quota retained because S3 exposes no maximum remote-completion bound for the earlier ambiguous write. A definite `412` never permits inspection, adoption, or deletion of the pre-existing object. The reconciler never blindly repeats an ambiguous write or delete. PHP temporary paths are never application-persisted; the effective `upload_tmp_dir` deployment owner retains bounded stale-file cleanup.

The first profile prohibits every S3 Lifecycle rule and action whose filter can cover `private-documents/v1/`, including current and noncurrent transitions, current and noncurrent expiration, expired-object delete-marker actions, and any other lifecycle mutation. Application metadata enters `deletion_pending` before the sole deletion path sends one retries-disabled SDK `DeleteObject` request for the fixed bucket/key/exact VersionId and expected owner under `s3:DeleteObjectVersion`. Absence is observed through one exact-full-key `ListObjectVersions` call with `MaxKeys: 2`, expected owner, equality checks, no markers/continuation/siblings and a completely empty result. Under the proved no-reuse/no-other-writer invariant and S3's strong delete/LIST consistency, only that empty post-delete result completes. After an ambiguous delete, one returned exact recorded version may be exact-version Head-validated before at most one reconciled Delete and one final list; every other or second non-empty/ambiguous result remains `deletion_pending` for incident ownership. This post-delete empty rule never changes the incident-only empty result after an ambiguous Put. Quota releases only after proved exact-version absence and the durable `deleted` transition. Lifecycle rules for a disjoint test or unrelated prefix require exact prefix non-overlap and deployment evidence. Operator drift can still make an accepted version missing, noncurrent, archived, or otherwise reclassified; affected metadata becomes non-serving and enters reconciliation rather than letting lifecycle configuration infer application state. S3 replication and external backup/restore are explicitly disabled/not applicable in this first profile. Retention, noncurrent-version cost, quota release, abandoned pending records, failed object cleanup, and KMS-key lifecycle each have an application/deployment owner and evidence.

A protected download authenticates, resolves tenant when applicable, authorizes the named download action before confidential lookup, loads only the exact accepted metadata, and issues an empty `303` response with `Content-Length: 0`, `Cache-Control: private, no-store`, and `Referrer-Policy: no-referrer`. `Location` is a pre-signed HTTPS `GetObject` for the exact bucket, key and `VersionId`, with fixed `application/octet-stream`, fixed attachment name, fixed cache override, a lifetime no greater than 300 seconds, an inclusive 4,096-byte URL bound, and the expected AWS regional hostname. The real-service test must prove that the selected temporary-credential form fits; overflow fails closed pending an accountable profile adjustment. The application never logs, traces, persists, enqueues, or exposes the query string separately. The eventual S3 `200` has no `nosniff` header under this direct-delivery profile; the initial application's `303` header cannot impose that policy on the separate S3 response.

The URL is a reusable bearer capability until expiry. The profile claims no one-time use, immediate revocation, client receipt, network completion, or durable delivery. Amazon S3 may honor a client's single-range request; omitting a `Range` input during signing does not justify `Accept-Ranges: none` or a full-response guarantee. A top-level browser navigation does not require CORS; another browser integration requires its own exact CORS and CSRF decision.

Adoption evidence uses one application-owned Composer script named `file-transfers:s3:verify`, wired through `test` into the complete `check` gate. It combines finite local static checks, application behavior and mutation evidence, an isolated real-AWS integration path, and separately dated deployment evidence. A canonical non-secret manifest, hashed application configuration source, and separate hashed credential-provider source pin the exact allowed region, bucket, expected account, `private-documents/v1/` prefix, KMS ARN, CA path/hash, named credential source, and explicit memoized-provider construction. The static portion may also pin the exact reviewed operation/configuration hashes, Composer packages and lock, explicit CurlHandler/GuzzleHandler construction, fixed client construction, fixed object-key derivation, finite state transitions, forbidden request-controlled infrastructure choices, and the absence of a generic storage facade or registry. It cannot prove the actual PHP/ext-curl/libcurl/TLS/CA runtime, deployment of those source bytes, provider-specific credential acquisition/refresh behavior, AWS identity, bucket policy, public blocking, versioning, KMS, checksum behavior, ambiguous failure, pre-signing, deletion, lifecycle, alarms, failover, capacity, cost, or production topology. Required real-service facts or credentials missing from release CI fail closed rather than skip or use a fake. Dated runtime evidence records the immutable image digest, exact extension/native-library/TLS tuple, CA-bundle origin/version/hash and update owner. The deployment record selects CloudTrail S3 data events for `PutObject`, `HeadObject`, `ListObjectVersions`, `GetObject`, and `DeleteObject` under the application prefix, names the exact management-event coverage for bucket/IAM/KMS/configuration drift, and records event destination, retention, access, alert, cost, redaction, and incident owners. CloudTrail-recorded keys are restricted audit metadata and redacted elsewhere; object content, sensitive raw/base64 checksums, and pre-signed URLs/query strings are not recorded.

PHPThis adds no S3 client, configuration, credential provider, presigner, retry, storage interface, facade, registry, lifecycle worker, runtime dependency, Strict Profile diagnostic, or framework checker rule. The application's `.ai/file-transfers.md` remains the sole writable policy owner; there is no `.ai/s3.md`.

Direct browser upload, pre-signed PUT/POST, S3 multipart/resumable upload, arbitrary multiple-file ingestion, PHP proxy streaming, CDN or proxy offload, public objects, active-content serving, provider-neutral storage, and automatic backend selection remain outside this profile.

## Contract effect

Consumer Contract version 13 splits the prior unconditional file-transfer rules into:

1. common bounded multipart and application policy;
2. the existing accepted `LOCAL_ADR026` durable-move and local-response profile; and
3. the new optional `AMAZON_S3_ADR053` direct-S3 and pre-signed-response profile.

This decision partially supersedes ADR 026 only for its remote-object-store and pre-signed-delivery exclusion when `AMAZON_S3_ADR053` is deliberately selected. The accountable choice is the direct-S3 fixed-octet-stream attachment without `nosniff` as a narrow profile exception. It does not weaken or rewrite `LOCAL_ADR026`, retains Strict Profile version 3 and diagnostics `PHT001` through `PHT007`, and adds no framework runtime behavior or checker diagnostic. The packaged pages, template fields, and reference proof are authoritative guidance after this decision and Contract version 13; they do not by themselves establish that a consumer adopted the profile or proved an AWS deployment.

## Consequences

An adopting application gains a concrete, inspectable S3 path without making storage interchangeable. It also owns more code, pinned HTTP transport and native-library/CA maintenance, configuration, external-service tests, reconciliation, IAM, KMS, versioning, retention and exact-version deletion, cost, and incident operations than the local example demonstrates. The first profile's `STANDARD` object pin and prohibition on every S3 Lifecycle rule/action covering `private-documents/v1/` preserve application-state authority and availability shape but require explicit bounded cleanup and cost operations.

The profile narrows overwrites and accidental public exposure, preserves byte and version identity, and makes ambiguous cross-system outcomes visible. It does not make Amazon S3 transactional with application metadata, exactly once, one-time-download, malware-safe, range-free, or production-certified.

The health-only skeleton remains `NOT_APPLICABLE(FILE_TRANSFER)`. The executable example remains the public non-production `LOCAL_ADR026` reference and adds no AWS dependency, configuration, credential source, network call, or S3 behavior.

## Non-goals

- A framework storage API, adapter, backend registry, facade, disk helper, AWS client factory, credential loader, presigner, or lifecycle service.
- Portable S3-compatible, multi-cloud, multi-bucket, multi-region, access-point, S3 Express, Outposts, acceleration, CDN, direct-browser, multipart, resumable, proxy-streaming, or public-object behavior.
- Automatic retry of a write or delete whose outcome is ambiguous.
- One-time URLs, immediate revocation, exact client receipt, range suppression, malware safety, or exactly-once claims.
- Static certification of an AWS account, IAM policy, bucket, KMS key, external failure semantics, deployment, cost, or operations.
- Adoption by the framework, starter, or executable example.

## Reconsider when

Reconsider the exact SDK/API pin when the accountable update owner has reviewed upstream changes and rerun all static, behavior, real-service, and deployment evidence. Reconsider the first profile if a real application requires direct browser transfer, objects beyond the single-upload bound, another AWS endpoint form, SSE-S3 instead of the selected customer-managed KMS posture, content inspection, another download topology, cross-region behavior, or a different service.

Reconsider a smaller shared primitive only after multiple independent applications prove the same boundary without hiding key derivation, identity, authorization, quota, encryption, checksum, version, retry, ambiguity, lifecycle, or service semantics. A passing reference proof still is not consumer adoption or production certification.
