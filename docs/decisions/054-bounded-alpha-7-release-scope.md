# ADR 054: Bounded Alpha 7 release scope

Status: accepted

Publication state is external. This decision accepts only the bounded Alpha 7 identity, notes, and source-preparation scope. It does not establish that any Alpha 7 candidate, tag, package, dedicated skeleton, GitHub prerelease, public installation, or announcement exists.

## Context

Alpha 6 is the latest completed coordinated framework-and-skeleton release. Its immutable framework tag `v0.1.0-alpha.6` peels to commit `118feb46801045bea35ef45ae1e5716e6f64238c` and carries Consumer Contract version 11, Strict Profile version 3, permanent diagnostics `PHT001` through `PHT007`, a 2,600-line core ceiling, and a 198-file framework package inventory. The external Alpha 6 evidence in Issue #37 records the matching skeleton, both package artifacts, the clean public `composer create-project` path, both GitHub prereleases, and the final announcement as complete. Later mutable repository wording must be reconciled with that evidence without changing the tag or treating a later `main` file as historical Alpha 6 source.

Accepted work after the Alpha 6 boundary now includes ADRs 048 through 053, Consumer Contract versions 12 and 13, one bounded response-cookie runtime correction, optional application-owned guidance, maintainer-only evaluation and proof tooling, and a modular installed-consumer harness. At the pre-preparation `main` commit `725f1c008834318f382b9f19265d73c7011c0389`, the exact `v0.1.0-alpha.6..main` delta contains 18 commits and 192 changed files, and the package inventory contains 216 files. Adding this decision and its release notes produces a 218-path source-preparation inventory. These numbers describe preparation input, not a frozen Alpha 7 candidate: the accountable-human acceptance recorded below changes tracked source bytes, and the final inventory, archive, Git export, installed package, and executable must be proved again for an exact candidate commit.

ADR 049 is the only post-Alpha-6 change to framework runtime source. It narrows the accepted values of the existing response-cookie path, advances Consumer Contract version 11 to version 12, raises the core ceiling from 2,600 to 2,620 lines, and leaves the final readable core at 2,618 lines. It deliberately rejects some cookie constructions that Alpha 6 accepted and therefore requires an explicit prerelease migration even though it adds no class, method, constructor parameter, runtime dependency, Strict Profile rule, or permanent diagnostic.

ADR 053 advances Consumer Contract version 12 to version 13 by splitting the optional file-transfer contract into common bounded multipart and application-policy requirements plus exactly one selected `LOCAL_ADR026` or `AMAZON_S3_ADR053` profile. It changes no framework runtime or checker rule. The accepted direct-S3 profile has a narrow fixed-attachment response exception without a guaranteed `X-Content-Type-Options: nosniff`; it does not weaken the local profile or establish that any application or AWS deployment adopted or proved S3.

The remaining work adds optional authoring guidance or maintainer evidence. It needs one bounded prerelease identity and a precise Alpha 6 upgrade path without presenting advisory patterns, synthetic proof, or external-service documentation as framework runtime, consumer adoption, or production certification.

On 2026-08-14 in Asia/Manila, the accountable human accepted this bounded Alpha 7 scope, exact release identity and both tag names, planned date, release notes, and source-preparation state. The same approval accepts a bounded Alpha 7 deferral of unavailable model/context token telemetry: no lexical source-token metric is substituted, and the deferral creates no general evaluation or release precedent. It explicitly excludes the real WebSocket consumer migration and its temporary proposed decision 002 from Alpha 7; the unresolved conflict between that consumer's unknown-prefixed-environment rejection policy and PHT007 remains unapproved application policy.

This acceptance does not approve either exact candidate commit and does not authorize a commit, push, tag, package-host update, dedicated-skeleton write, GitHub release, announcement, issue closure, production-system mutation, or any other external operation. Issue #53 is the Alpha 7 work item and must record every later exact-candidate approval and operation authorization separately.

## Decision

The exact approved source-preparation identity is:

- Composer version: `0.1.0-alpha.7`
- framework tag: `v0.1.0-alpha.7`
- skeleton tag: `v0.1.0-alpha.7`
- planned release date: `2026-08-18` (Asia/Manila)
- bounded scope: `docs/decisions/054-bounded-alpha-7-release-scope.md`
- release notes: `docs/releases/0.1.0-alpha.7.md`
- framework candidate commit: `PENDING`
- skeleton candidate commit: `PENDING`
- release evidence and operation authorizations: Issue #53

The framework continues receiving its Composer version from the Git tag; root `composer.json` does not gain a `version` field. The planned date remains distinct from every observed external-operation timestamp. Both exact candidate commits remain `PENDING`; this source-preparation approval does not approve, freeze, or authorize action on either candidate.

Alpha 7 source preparation is limited to the exact `v0.1.0-alpha.6..candidate` rollup below. A new feature or consequential decision outside this list leaves the bounded scope and requires explicit review before candidate freeze.

### Runtime, public API, and consumer validity

- Carry ADR 049's existing-constructor response-cookie correction and Consumer Contract version 12. `ResponseCookie` retains the same constructor and serialization path but requires an HTTP-token name and cookie-safe ASCII value whose combined length is at most 4,096 bytes; a 1-through-1,024-byte absolute path beginning with `/` and containing only bytes `0x21` through `0x7E` except `;`; a four-digit-UTC-year expiration from `1` through the smaller of `PHP_INT_MAX` and `253402300799`; and a maximum age from `0` through `34560000` seconds.
- One `Response` may carry at most 50 cookies, no repeated case-sensitive cookie name even on different paths, and at most 8,192 aggregate bytes across its `ResponseCookie::headerValue()` results, excluding transport-owned `Set-Cookie: ` field-name and line-framing bytes. ASCII-case-insensitive recognition of `__Secure-`, `__Host-`, `__Http-`, and `__Host-Http-` enforces the accepted `Secure`, root-path, and `HttpOnly` combinations without normalizing the supplied name. `Domain`, `Partitioned`/CHIPS, and `Priority` remain unsupported.
- Native-session behavior retains its existing lifecycle and fixed cookie shape. Evidence becomes exact about live and deletion fields and no longer describes absence of `Expires` and `Max-Age` as a guaranteed browser-session lifetime. HTTPS, `Secure`, authentication, authorization, idle and absolute expiry, logout, revocation, CSRF, XSS, CSP/output, browser, and deployment policies remain application-owned.
- Carry ADR 053's Consumer Contract version 13 file-transfer split. A non-adopter remains `NOT_APPLICABLE(FILE_TRANSFER)`. A local adopter deliberately selects `LOCAL_ADR026` and retains ADR 026's visible `move_uploaded_file`, local `LocalFileBody`, complete `200`, `nosniff`, and deferred-range behavior. An S3 adopter deliberately selects `AMAZON_S3_ADR053` and owns its exact application, real-AWS, and dated deployment evidence, including the narrow no-`nosniff` direct-response exception.
- Retain Strict Profile version 3 and permanent diagnostics `PHT001` through `PHT007` unchanged. Add no accepted-PHP syntax, checker diagnostic, public API spelling, runtime dependency, or framework-owned external-service client.
- Retain PHP `~8.4.0`. PHP 8.5 remains outside the reviewed and supported Composer range.
- Retain zero third-party framework runtime dependencies and the accepted 2,620-line core ceiling. The observed 2,618-line implementation leaves two unallocated lines; they authorize no adjacent cookie attribute, helper, authentication mechanism, session mechanism, response feature, or other runtime work.

### Optional application-owned guidance

- Add native-first date and time guidance that distinguishes instants, calendar dates, local date-times, elapsed durations, and calendar intervals; uses explicit timezones and operation-specific clocks; and keeps parsing, precision, persistence, arithmetic, scheduling, and any third-party package application-owned.
- Add frontend integration guidance for separately owned clients, explicit HTTP handoffs, a same-origin reverse-proxy default when appropriate, an advisory `data` plus optional `meta` structured-success convention, exact decoder evidence, bounded application-owned HTML rendering, and deliberate API-description adoption. Existing response shapes are not rewritten automatically.
- Add a fixed-operation nested-resource profile that performs one bounded operation-owned I/O plan independent of parent-page cardinality, followed by I/O-free mapping and encoding. It adds no relationship loader, serializer, repository, ORM, generic paginator, response wrapper, or generated API layer.
- Add optional field-addressable `422` issue guidance with a finite code-owned field/code vocabulary, deterministic ordering and bounds, generic redaction, and an explicit compatibility decision. The existing generic `400` and `422` recommendation remains valid and unchanged for non-adopters.
- Add application-owned transactional-email guidance covering deterministic MIME composition, contextual encoding, one pinned transport, durable intent when selected, provider feedback, sender operations, redaction, and real integration evidence. PHPThis adds no mailer, renderer, provider client, queue, worker, or webhook runtime.
- Add application-owned stateless Bearer, JWT, opaque/PAT/API-token, and external-identity-provider guidance with exact parsing, current authorization, credential lifecycle, frontend handoff, and evidence. It adds no authentication, token, key, discovery, refresh, or identity-provider runtime.
- Add ADR 050's optional development-only local environment launcher: one finite application command/profile map, one strict declarative ignored file, atomic selected-profile precedence, and an array-form shell-free private-child handoff with an exact environment. It adds no dotenv loader, configuration bag, cache, automatic bootstrap loading, production launcher, or checker rule.
- Add ADR 051's optional structured destination envelope, finite level mapping, UTC occurrence time, daily-file or managed-stream profile, and asynchronous Grafana Alloy-to-Loki route without changing the closed request-summary payload or synchronously calling a remote collector from a request. The skeleton and executable example remain non-adopters.
- Strengthen the existing local file-transfer guidance around effective ingress and PHP upload settings, protected request-policy order, temporary-directory ownership and cleanup, content posture, atomic quotas, retention, deletion, reconciliation, deployment evidence, and redaction without changing `LOCAL_ADR026` runtime behavior.
- Add ADR 052's backend-neutral durable-job adoption and `jobs:verify` evidence route. ADR 024 remains the first and only checked backend-specific profile and keeps its SQLite-specific transaction, claim, lease, fencing, retry, dead-letter, idempotency, and one-delivery process semantics. Another backend must name and prove its own publication, recovery, delivery, acknowledgement, ordering, ownership-window, stale-owner, duplicate-effect, retry, terminal, security, retention, backup/restore, and operations behavior; it does not inherit SQLite claims.
- Add ADR 053's exact optional application-owned Amazon S3 profile with pinned SDK and HTTP transport, one explicit credential source, fixed bucket/key/version/KMS policy, checksum and encryption validation, finite cross-system states, ambiguous-outcome reconciliation, exact-version deletion, lifecycle prohibition, pre-signed-download limits, IAM, audit, cost, and incident ownership. The framework, source skeleton, dedicated skeleton, and executable example add no AWS dependency, configuration, credential source, route, network call, or S3 behavior.
- Carry application ownership of `AGENTS.md`, `.ai/` context, source layout, decisions, schemas, product policy, external services, deployments, and evidence. An upgrade may reconcile those files deliberately but never overwrite, relocate, or silently adopt optional profiles.

### Alpha 6 to Alpha 7 migration

Before adopting a future Alpha 7 candidate, an Alpha 6 application completes this exact sequence:

1. Review Consumer Contract version 11 to version 12 and then version 13. Strict Profile version 3 and diagnostics `PHT001` through `PHT007` remain unchanged.
2. Inventory every direct `ResponseCookie` construction, every immutable response-copy path carrying `Response::$cookies`, and every configured `SessionConfiguration::$cookieName` plus its selected `cookieSecure` value.
3. Replace every cookie outside the accepted name/value, path, expiration, maximum-age, prefix, per-response count, unique-name, and aggregate serialized-byte bounds above. When both `Expires` and `Max-Age` exist, confirm deliberately that `Max-Age` is authoritative and `Expires` is the fallback rather than an inferred clock-relative equality.
4. When native sessions are adopted, treat `__Host-`, `__Secure-`, and `__Http-` prefixes ASCII-case-insensitively; every such configured session-cookie name requires `cookieSecure=true`, with the fixed root path and `HttpOnly` session shape supplying the remaining accepted prefix attributes. Enable `Secure` or rename an insecure mixed-case prefixed session cookie before upgrading. Then assert the exact live cookie name and identifier, `Path=/`, selected `Secure`, `HttpOnly`, SameSite, absent `Expires`, absent `Max-Age`, and complete serialized header. Assert the deletion cookie's same name and scope, empty value, past `Expires`, `Max-Age=0`, and complete serialized header. Retain explicit application policy and evidence for HTTPS, authentication, authorization, expiry, logout, revocation, CSRF, XSS, CSP/output, logging, browser behavior, and deployment.
5. For no file transfers, retain multipart-disabled behavior and `NOT_APPLICABLE(FILE_TRANSFER)`. For an existing local adopter, record `LOCAL_ADR026`, preserve its local response and `nosniff` behavior, reconcile the strengthened ingress, temporary-file, authorization, quota, content, lifecycle, deletion, reconciliation, and deployment evidence, and run the complete application gate. Do not select S3 merely because the installed contract offers it.
6. Adopt `AMAZON_S3_ADR053` only through a separate accountable application decision. Pin and implement the exact installed profile, wire `file-transfers:s3:verify` through `test` into `check`, and supply the required application behavior, isolated real-AWS, and dated deployment evidence. Missing evidence fails closed. Updating PHPThis never authorizes an AWS mutation or establishes S3 adoption.
7. Treat every other Alpha 7 guidance addition as advisory and conditional. Do not silently wrap an existing success response in `data`, change an error shape, embed nested resources, add field issues, adopt a clock package, frontend, email transport, stateless credential, local launcher, structured destination, jobs backend, or S3 path, or copy reference limits without a concrete application requirement and the applicable compatibility or operational decision.
8. Reconcile installed guidance with project-owned `AGENTS.md`, `.ai/` context, source layout, dependencies, and decisions without overwriting or relocating them. Preserve every established application contract not deliberately changed.
9. Update only to the exact approved Alpha 7 prerelease after reviewing its final tagged notes, then run the application's complete project gate on PHP 8.4.x and its selected real-service or deployment evidence where applicable.

### Candidate and publication evidence limits

Before source preparation can advance through an exact Alpha 7 candidate and publication, Issue #53 and `RELEASING.md` must record and prove the following at their applicable ordered gates:

- one clean exact framework candidate commit matching this bounded scope, the final package inventory, Consumer Contract version 13, Strict Profile version 3, diagnostics `PHT001` through `PHT007`, and the 2,618-line core under the 2,620-line ceiling;
- `composer validate --strict`, a no-interaction preferred-distribution install from the unchanged reviewed dependency graph, and the complete `composer check`, including guardrails, maximum-level PHPStan, both maintainer evaluation stages, permanent profile fixtures, installed-consumer proof, database-driver certification, query-scaling evidence, and framework behavior tests;
- exact archive and Git-export agreement with `tools/package-files.txt`, executable `bin/phpthis`, no unexpected package file, and no unreviewed runtime or development dependency change;
- exact-commit GitHub CI for PHP 8.4 validity and the SQLite, MySQL, and PostgreSQL PDO transport jobs;
- separate approval before pushing the exact framework candidate, and separate approvals for framework tag creation, tag push, and framework Packagist publication;
- after the exact framework distribution is proved, a separately authorized dedicated-skeleton export that removes the source-evaluation override, pins exact `0.1.0-alpha.7` through Packagist, commits the resulting lockfile, matches the framework inventory, passes its own complete gate and exact-commit CI, and receives separate candidate, push, tag, and package approvals; and
- one new Packagist-only preferred-distribution `composer create-project` proof with exact framework and skeleton versions, inventories, executables, resolved context, complete application gate, and loopback health behavior before either GitHub prerelease or the final announcement is authorized.

The framework gate can prove only the reviewed source, package, synthetic fixtures, and exact services it actually exercises. In particular:

- the fake evaluation runner does not prove real model quality, OCI containment, credential isolation, arbitrary network denial, or comparative performance;
- packaged S3 guidance and its synthetic reference structure do not prove AWS identity, IAM, KMS, bucket state, TLS/native transport, failure semantics, cost, monitoring, deployment, or consumer adoption;
- packaged jobs, email, stateless-authentication, frontend, launcher, and destination guidance does not prove a consumer's selected provider, broker, credential, browser, supervisor, filesystem, collector, or production topology;
- a green static check, mock, fake service, or source hash does not replace required real-service, process, browser, filesystem, failure, and dated deployment evidence; and
- complete prerelease publication proof would establish only the exact experimental artifacts and installation path, not production readiness, backward compatibility, a support SLA, deployment certification, capacity, availability, security completeness, durable delivery, exactly-once effects, one-time S3 URLs, or universal AI correctness.

## Consequences

If separately proved and published, Alpha 7 gives consumers one explicit migration for the only post-Alpha-6 runtime compatibility break while making a broad set of application-owned integration and operational decisions easier for an AI and human reviewer to inspect. The accepted scope preserves the framework's small runtime, one checked PHP profile, visible composition, direct SQL, and application ownership instead of converting the new guides into framework services.

The installed package would contain substantially more public knowledge and application-context templates. That larger guidance surface requires exact package inventory, routing, marker, source-versus-installed, and isolated-consumer evidence. It does not imply a larger runtime API or make every guide ordinary task context; agents still begin with one routed current guide and add another concern only when the task enters it.

Cookie producers accepted by Alpha 6 may fail under a future Alpha 7 candidate. That rejection is intentional and must remain prominent in the final release notes and upgrade proof. Applications that do not use the newly documented optional profiles should gain no new runtime dependency, route, process, external request, configuration input, or production obligation.

This accepted source-preparation scope keeps Alpha 7 experimental. Until the exact candidate and every ordered public-artifact gate pass under separate authorization, Alpha 6 remains the latest completed release and its proved installation command remains the public starting point.

## Reconsider when

Reconsider before exact-candidate approval if the exact `v0.1.0-alpha.6..candidate` diff contains a change not represented above; if the final runtime, dependency, package inventory, contract, Strict Profile, diagnostic, or core-line evidence differs; if an optional guide is presented as mandatory adoption; if the cookie migration omits one newly rejected construction; or if Issue #53 cannot distinguish preparation, candidate approval, and each external operation.

After any future candidate approval or publication, reconsider the smallest affected boundary when independent consumer evidence shows that a selected cookie bound or application-owned profile causes a concrete correctness or review failure, or when package and public-install evidence cannot reproduce the candidate. Publish a new separately approved identity rather than moving either Alpha 7 tag, weakening evidence, or silently expanding this scope.
