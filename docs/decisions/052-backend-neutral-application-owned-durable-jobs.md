# ADR 052: Backend-neutral application-owned durable jobs

Status: accepted

Accountable-human approval: 2026-08-13 (Asia/Manila). This approval accepts the decision only; it does not authorize a commit, push, release, or issue closure.

## Context

ADR 024 accepts one safe application-owned SQLite durable-job recipe. Its guarantees depend on one SQLite database and connection, explicit transactions, `UPDATE ... RETURNING`, opaque lease-token fencing, a fresh one-delivery process, bounded retries and dead letters, and an idempotent database effect. Those are concrete strengths, not universal queue semantics.

Applications may instead choose Redis Streams, RabbitMQ, SQS, Kafka, or another service. Publication, publisher confirmation, claim, acknowledgement, receipt handles, visibility, reclaim, consumer groups, offsets, ordering, persistence, retry, and failure behavior differ materially. A PHPThis checker per backend would create an expanding maintenance surface and imply guarantees static analysis cannot establish. A universal `QueueInterface` or transport adapter would conceal the semantics an application must understand and prove.

The framework needs to route an application toward explicit safe decisions without making an unproved backend portable or weakening the accepted SQLite profile. That route preserves `NOT_APPLICABLE(JOBS)` for applications without durable deferred work.

## Decision

PHPThis uses three documentation layers:

1. a backend-neutral application-owned durable-job contract;
2. one exact application adoption record plus an executable application-owned jobs verification gate for the selected backend; and
3. optional backend-specific profiles only after a pinned implementation supplies real-service evidence.

The common contract requires the application to record the exact backend and client versions, topology, durability configuration, network boundary, tenant and environment isolation, credential rotation and revocation, TLS, least-privilege producer, consumer, relay, inspector and administrator identities and capabilities, privileged-operation authorization and audit, update ownership, publication, recovery and loss model, and a minimum positive durable-publication invariant: after reported success, the intent/message survives producer or request termination and remains recoverable or deliverable until acknowledgement, terminal outcome, or explicit finite cancel/expiry under one named proved durability/fault envelope, with restart/failover only when separately exercised. It also records a bounded versioned JSON envelope, payload classification/minimization, encryption-at-rest and key ownership where applicable, region/residency, full-envelope access and retention across any selected terminal or dead-letter/DLQ store, backup, replica and snapshot, finite dispatch, job-type publication authority, durable non-secret tenant/owner/principal/action binding or explicit tenantless non-applicability, current authorization/revocation/state recheck or an explicit committed system-owned obligation, actual delivery semantics, maximum handler duration relative to any ownership window, exact extension, renewal, heartbeat or session-liveness owner/cadence/bounds and failure/expiry/actual stale-owner behavior, rejection or fencing only where supported and otherwise bounded overlapping stale work plus duplicate-safe recovery, or explicit non-applicability only when no such mechanism applies, duplicate-safe semantic effects, exact semantic-effect/idempotency uniqueness scope, durable retention/deletion owner and protection horizon beyond every retry, redrive, terminal-retention, replay and provider-deduplication window, explicit post-horizon behavior, and backup/restore preservation or fail-closed reconciliation of corresponding queued-message and effect/idempotency state, finite version-controlled retries and terminal policy with an exact owner, process lifecycle, capacity and backpressure, redacted observability, outage and recovery ownership, and the canonical application-owned Composer evidence script name `jobs:verify` wired into the complete project gate. Ambiguous/failed publication and catastrophic loss outside the envelope remain separate; an explicit recorded terminal rejection/exhaustion, finite cancellation/expiry, or bounded catastrophic loss outside that envelope can yield zero handler executions. Redis Pub/Sub, process memory and other fire-and-forget paths do not qualify. Diagnostic redaction does not imply that a selected durable store lacks the full envelope. Broker consumer credentials do not count as domain authorization, and PHPThis adds no identity, middleware or context API. `jobs:verify` is not a runtime command or checker API.

When an independently meaningful database write and a broker publication cannot share one proved transaction, the application owns a transactional outbox or another explicitly proved recovery mechanism. An outbox relay must recover death before publish, death after broker acceptance but before durable confirmation is recorded, ambiguous confirmation, and duplicate publication. An after-commit call or publisher confirmation alone is not described as atomic with the independently committed database transaction.

Stored input remains a bounded versioned JSON envelope with finite code-owned types, application-generated idempotency identity, operation-specific payload bounds, and strict parsing before handler work. Dispatch remains a finite explicit code choice. Stored PHP objects or class names, reflection, discovery, service-container lookup, generic dispatch, and queue facades remain excluded.

The application describes the backend's exact claim, acknowledgement, receipt, visibility, lease, reclaim, consumer-group, offset, ordering, and redelivery behavior without translating it into stronger generic terminology. Where an effect depends on order, it records and proves the exact ordering, partition or sequence key and concurrency scope plus service enforcement or one monotonic/version guard, rejection or reconciliation path for stale, out-of-order and replayed work; order-independent effects record explicit non-applicability. Where an ownership window or session-liveness rule applies, it records and proves maximum handler duration relative to that window, the exact extension, renewal, heartbeat or session-liveness owner, cadence and finite bounds, renewal failure or expiry and actual stale-owner behavior. Rejection or fencing is required only where supported; otherwise evidence bounds overlapping stale work and proves duplicate-safe recovery. Explicit non-applicability applies only when no ownership or session-liveness mechanism exists. Assume a delivery may occur more than once and make semantic effects duplicate-safe. Separately prove publication, recovery, loss, expiry and cancellation boundaries because this assumption does not guarantee that every publication reaches handler work even once. Zero handler executions are compatible only with an explicit recorded terminal rejection/exhaustion, finite cancellation or expiry, or bounded catastrophic loss outside the named proved durability/fault envelope. A stronger backend feature never upgrades handler execution or external effects to exactly once. Acknowledgement occurs only after the intended durable semantic effect, or atomically with that effect only when one exact storage mechanism proves the same boundary, never by implication across independent systems. External timeout ambiguity requires provider idempotency where available, durable request and receipt state, reconciliation, compensation, and explicit safe-replay policy. Duplicate protection has an exact uniqueness scope and a retained horizon longer than every possible redelivery or replay; after that horizon the application rejects, reconciles or creates a new semantic operation rather than silently replaying an unprotected effect. Backup/restore preserves corresponding queued-message and effect/idempotency state or stops consumption until mismatches are reconciled, so restoring old work cannot resurrect an unprotected effect. This decision makes no exactly-once execution or effect claim.

Retry, redrive, poison-envelope handling and terminal behavior are finite, version-controlled and owned by named application code, broker configuration or infrastructure as code. The selected terminal state or destination and its retention are explicit, including any adopted dead-letter/DLQ mechanism or explicit non-applicability. Privileged inspection, replay, cancellation and deletion require exact identities, least privilege, authorization, audit and redaction. Replay preserves or replaces the original idempotency identity only under an explicit compatibility and semantic policy. Cancellation defines pending, claimed or in-flight, effect-started, acknowledged and terminal behavior using mechanisms the selected backend actually supports; it does not imply recall of already executing or completed work.

Worker entrypoint, concurrency, prefetch or backpressure, maximum handler duration relative to any ownership window, applicable extension, renewal, heartbeat or session-liveness policy, timeouts, reconnect, shutdown, deployment replacement, supervision, capacity, lag, retention, backup, outage and recovery remain exact application and deployment facts. Each visibility, lease, TTL, delay, retry and retention decision names its selected service-owned or application-owned time source, representation, units, rounding, precision and skew limits. Application evidence exercises only that selected time mechanism and real service for backend-behavior claims. Its unique run-ID-scoped resources have bounded ordinary `finally` cleanup plus a finite abandoned-run lifetime and exact run-ID-scoped stale-run reconciliation owner/mechanism because hard termination can skip cleanup; broad deletion remains forbidden. Mocks may shorten the development loop but do not replace release-gate real-service evidence or production topology, persistence, authentication, authorization, TLS, failover and alarm evidence.

The recommended verification shape is one explicit application-owned ordered PHP entrypoint over three cohesive application modules: publication, delivery, and operations. The entrypoint only aggregates application-specific failure lists and emits fixed bounded redacted pass or fail bytes with exit `0` or `1`. It does not discover tests, interpret a backend, provide a generic validator, simulate broker behavior, or treat absence, a mock fallback, or a skip as release evidence. Release CI fails closed when required real-service configuration or observations are absent. The canonical application-owned Composer evidence script `jobs:verify` runs from `test`, and `test` runs from the complete `check` gate.

The installed application checker continues enforcing only the existing Consumer Contract and Strict Profile rules. Finite job dispatch and prohibited dynamic resolution remain application source, review and behavior evidence unless the application adds its explicitly owned optional static check inside `jobs:verify`. That application check requires one honest mechanically decidable owner, pinned versions, diagnostics, positive and negative fixtures and mutation evidence; it cannot claim broker durability, publication atomicity, outbox recovery, publisher confirmation, acknowledgement ordering, visibility expiry, redelivery, idempotency, TLS or authorization configuration, failover, throughput, retention, or production topology. PHPThis neither hosts nor discovers it. This decision adds no checker rule.

A future backend-specific profile names exact supported service and client versions, concrete publication and delivery mechanisms, acknowledgement, retry and selected terminal behavior, including any adopted dead-letter/DLQ mechanism or explicit non-applicability, topology and security assumptions, copyable application-owned implementation structure, real-service automated evidence, deployment evidence, and unsupported claims. A checklist without that evidence is not a checked profile.

ADR 024 and the complete SQLite guide remain the current accepted first checked profile and are not superseded. Their same-connection transaction, one-row claim, lease and fencing, one-shot lifecycle, query bounds, idempotency, retries, dead letters, redaction, and operations evidence do not become defaults for another backend. ADR 024 remains governed by its existing accepted evidence and does not retroactively certify an exact deployable SQLite version; the stricter exact service/client version and real-service bar above applies to every profile added under ADR 052. The accepted backend-neutral pages and application-template routes are current optional guidance under this record.

Consumer Contract version 12, Strict Profile version 3, diagnostics `PHT001` through `PHT007`, framework core, runtime dependencies, application checker validity, and the starter's non-adopting behavior remain unchanged.

## Consequences

Applications selecting another backend receive a consistent decision and evidence checklist without a misleading common runtime API. The application owns more explicit code, tests, configuration, deployment proof, and operational records, but backend failure semantics and accountability remain locally inspectable.

The documentation distinguishes common obligations from profile-specific mechanisms. The accepted SQLite material lives intact in substance in a clearly named checked profile, while the common index routes adopters to the selected profile or their own exact application design.

PHPThis does not certify an application's broker or production deployment. A green checker, a unit test with mocks, a publisher confirmation, or service documentation remains insufficient for claims outside the evidence actually exercised. Real-service tests may require separately provisioned CI resources and credentials; production failover, security, capacity, alarms and recovery still require deployment evidence.

The starter continues to record `NOT_APPLICABLE(JOBS)` and gains no job table, client dependency, command, worker, or configuration. Existing consumers using ADR 024 retain their implementation and evidence.

## Non-goals

- A framework queue API, `QueueInterface`, facade, dispatcher, worker, scheduler, supervisor, event bus, transport adapter, or runtime dependency.
- One PHPThis checker or generic validator per backend or client library.
- Automatic backend discovery or runtime selection.
- Portable names that hide backend-specific delivery and failure behavior.
- Certification of every queue, stream, log, or messaging service.
- Exactly-once execution or exactly-once external-effect claims.
- Treating static analysis, mocks, publisher confirmations, or service marketing as production evidence.
- Installing durable deferred work in a non-adopting application.

## Reconsider when

Reconsider this documentation boundary if independent real applications show that one stated common obligation is not backend-neutral. Reconsider any narrower shared runtime primitive only after multiple independent real applications and materially different backends prove the same smaller boundary without hiding publication, delivery, acknowledgement, idempotency, retry, lifecycle, security, or operational semantics.
