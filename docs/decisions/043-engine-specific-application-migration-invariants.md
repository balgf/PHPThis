# ADR 043: Engine-specific application migration invariants

Status: accepted

## Context

ADR 027 proves one application-owned SQLite migration ledger with transactional DDL and ledger insertion, rollback of the still-active migration transaction, and one same-host nonblocking `flock`. Those choices are concrete strengths of that proof, but they are not portable properties of database migrations. MySQL commonly commits DDL implicitly. PostgreSQL supports transactional DDL broadly but has command-specific exceptions and server-side coordination semantics. Other engines and deployment topologies expose different atomicity, locking, ownership, and recovery boundaries.

Some later guidance presented ADR 027's per-migration transaction and local file lock beside requirements for every adopting engine. That wording could lead an AI either to copy an invalid SQLite mechanism into a server database or to conclude that PHPThis does not support an application-owned migration path for another engine. The framework needs one engine-neutral validity floor while keeping every executable mechanism and proof engine-specific.

On 2026-08-08 in Asia/Manila, the accountable human approved Issue #30 and this separation of universal application-owned migration invariants from the unchanged SQLite reference proof.

## Decision

PHPThis accepts application-owned migrations for an explicitly selected database engine and version when the application records and proves the invariants below. PHPThis supplies no cross-engine migration implementation. Every adopting application owns its statements, ledger, coordinator, authority, coordination, per-history compatibility and handoff constraints, application-wide release sequence, and recovery behavior. `.ai/configuration.md` owns exact configuration and process identity, `.ai/data.md` owns effective database-authority facts and accountable transition ownership, `.ai/migrations.md` owns the per-history migration constraints and transition implementation, and `.ai/operations.md` alone owns the application-wide sequence and operational runbooks.

When an application owns multiple separately tracked migration histories, it applies this decision separately to each history. Engine and version, source, command, configuration, authority, coordinator, manifest, ledger, atomicity, coordination, recovery, output, per-history compatibility and handoff constraints, and evidence never inherit implicitly from another history. Histories are independent only when the application records and proves that their managed objects, data, authority transitions, and coordination domains do not intersect. Otherwise it records their dependency order, one shared exclusion or serialization boundary, every cross-history partially completed state, and the application-wide forward recovery that preserves already accepted history; `.ai/operations.md` owns that executable cross-history sequence.

### Universal application-owned invariants

Every adopted migration path must:

- run only through the application's sole explicit operational console; each separately tracked migration history has one finite explicit command spelling plus separately scoped configuration and migration authority, and it never runs during request startup, from dependency hooks, or through framework `vendor/bin/phpthis`;
- use one final concrete coordinator with a finite bounded manifest, permanent ordered identifiers, checksum-covered exact statement sequences plus every code-owned binding value or finite binding-derivation policy, and explicit unrolled migration-step calls; no directory, filename, class string, attribute, ledger value, or runtime `.sql` file selects executable work, and no database call occurs in a loop;
- keep complete engine-specific SQL as finite compile-time-constant statements at direct `Connection` calls, bind every data value, and give the migration connection its own finite query budget and bounded trace;
- maintain one bounded, inspectable application ledger whose complete definition, maximum size, manifest position, permanent identifier, checksum, parser bounds, accepted history prefix, and any selected bounded operational metadata are explicit for the selected engine; additional fields are finite, non-executable, validated, and never select migration work, define order, or authorize behavior; its definition decision enumerates the finite accepted catalog or metadata surface and the rejection policy for unrecorded or incompatible columns, types, nullability, defaults, keys, constraints, indexes, triggers, rules, policies, ownership, and authority as applicable rather than inheriting SQLite byte comparison;
- validate the complete bounded applied history before pending work and fail closed on overflow, malformed values, gaps, duplicates, reordering, unknown identifiers, or checksum drift; the ledger never stores executable SQL, PHP class names, callbacks, serialized objects, credentials, or output;
- treat applied identifiers, order, and checksum-covered content as immutable; correct a defect through a new forward migration or a separately human-authorized recovery action, never an inferred down migration, silent edit, repair, deletion, or manufactured baseline;
- keep separately named migration configuration and its process-entry identity unavailable to HTTP; record the exact effective-authority overlap between migration and runtime; isolate required migration capabilities where the selected engine supports that boundary, or explicitly record the residual risk where it does not, including SQLite file-level authority limits; keep every authority activation or deactivation on an explicit non-HTTP path; and verify the dependent runtime statements under the runtime identity before traffic;
- expose finite stable success and failure outcomes without paths, DSNs, credentials, SQL, bindings, exception details, ledger contents, schema contents, or application data; and
- record old-code and new-code compatibility, abort gates, authority handoff, deployment ordering, backup or restore ownership, partial-failure handling, and the exact-engine evidence that permits shared or production use.

These invariants require ledger consistency, not one universal transaction shape. A completed ledger entry must correspond to every checksum-covered migration effect that the application accepts as applied, including DDL, data changes, and authority transitions when the step owns them. The engine-specific decision records whether those effects and the ledger write can commit atomically for each statement sequence, while separately stating the selected engine's DDL atomicity limits. When they can and the application selects that behavior, the transaction boundary remains explicit. When they cannot, the application must enumerate every observable state between each migration effect and ledger update, detect those states before later work, stop rather than claim success, and define the reviewed forward reconciliation, restore, or other recovery action. It must not insert an applied ledger row before all corresponding migration effects exist or claim rollback that the engine cannot provide.

These invariants also require explicit concurrency decisions, not one universal lock. The application records every migration-writer topology it intends to support and one concrete coordination mechanism for each topology; the stable application-, environment-, and history-specific coordination identifier or namespace plus its collision policy; the coordination owner; exact creation, acquisition, use, and release permissions or authority; acquisition, contention, timeout, loss, expiry, session, process, and crash behavior as applicable; and evidence that concurrent writers cannot silently advance the same history. All writer topologies that can reach one history must participate in one shared exclusion domain or use explicit authority gating that makes cross-topology overlap impossible; isolated same-topology proofs are insufficient. A same-host file lock, database advisory lock, externally serialized deployment stage, or another engine-supported mechanism is valid only for the exact topology and failure behavior that the application records and proves. A ledger-locking protocol is valid only when its coordination object already exists before ledger bootstrap or its separately coordinated bootstrap behavior satisfies the same protected-interval and evidence requirements. No mechanism is inferred from the PDO driver.

The engine-specific decision also defines the protected or serialized interval. An application- or database-owned mechanism becomes effective before ledger bootstrap plus authoritative definition and history validation and remains effective through all checksum-covered migration effects and either accepted ledger completion or a finite fail-closed failure outcome. If coordination can expire or be lost, detected loss stops before the next mutation and returns the recorded finite failure. An expiring or losable mechanism is valid only when a successor cannot begin a mutation while an earlier owner's statement may still be executing: the decision proves database-enforced fencing, confirmed invalidation or termination of the prior owner's database session and in-flight work, or another exact-engine and topology-specific exclusion boundary. Merely checking ownership after a long statement or observing that the client process exited is insufficient. A partial state is never recorded as applied. After loss or process termination, the next owner reacquires coordination and re-detects the exact engine state before later work. Deployment or external serialization surrounds the complete console invocation and retains the same prior-owner database-work termination or fencing obligation when a runner disappears. Its evidence runs at that external boundary and proves that a bypassing invocation cannot obtain the migration configuration or authority; two unconstrained console subprocesses do not prove an external coordinator.

Before implementing any adoption, the accountable human approves an application decision that records the application and deployment facts below. An exact ADR 027 SQLite reference adoption may cite ADR 027 for mechanism fields it adopts unchanged, but it still records its exact baseline, SQLite version, filesystem and writer topology, authority overlap and residual risk, recovery and operational constraints, release handoff, and evidence:

- the exact accepted initial state for the history, including every externally pre-provisioned database, catalog, schema, role, authority, or coordination object, every application-managed object, effect, or history entry already present, and every state that must be absent; an empty database is one possible baseline, not a universal requirement;
- exact engine and version, namespace and ownership model, statement set, code-owned binding values and finite binding-derivation policies, DDL lock behavior, timeouts, and operational availability limits;
- exact ledger DDL, finite accepted catalog or metadata surface, incompatible or unrecorded-object rejection, any selected operational metadata and its source and representation, history query, row bound, and parser rules;
- transaction and implicit-commit behavior for ledger bootstrap and every migration statement sequence, including DDL, data, and authority effects as applicable;
- every possible non-atomic or crash-visible intermediate state and its fail-closed detection and recovery path;
- migration authority, runtime-authority handoff, prohibited capabilities, and per-history compatibility and handoff constraints, with the application-wide release order recorded only in `.ai/operations.md`;
- every coordination topology, its stable identifier or namespace, creation/acquisition/use/release permissions or authority, shared cross-topology exclusion or authority gate, selected mechanism and protected interval, including what it does not coordinate, how expiry or loss fences or terminates prior work, and how an unauthorized bypass is denied; and
- exact-initial-state, rerun, ledger-definition mismatch, drift, malformed-history, same- and cross-topology concurrency at the owning coordination boundary, coordination-permission and bypass denial, partial-failure, cross-history when applicable, recovery, real-console, redaction, no-HTTP-startup, and exact-engine authority evidence.

### SQLite reference proof

ADR 027 remains the executable SQLite specialization. This record does not change its transaction, ledger, or `flock` mechanism; it clarifies that a separate migration configuration and process entry do not prove SQLite capability isolation. Its selected SQLite statements and ledger insert share one explicit transaction per migration; a failure rolls back that still-active transaction and preserves earlier committed migrations. Its application-private nonblocking `flock` coordinates only cooperating processes using the verified path on one host and filesystem. Its byte-exact SQLite ledger-definition comparison, `unixepoch()` timestamp, busy policy, query bounds, failure vocabulary, and recovery evidence remain proof-local choices.

An application may adopt those choices only when it adopts and proves the same SQLite boundary. MySQL, PostgreSQL, and other engines must not relabel ADR 027 by changing a DSN. They use the universal invariants above plus their own reviewed engine decision and executable evidence. PHPThis currently supplies no second engine reference implementation and makes no portable DDL, transaction, lock, rollback, or crash-recovery claim.

Consumer Contract version 10 and Strict Profile version 3 remain unchanged. This record both corrects the nonportable scope of existing migration guidance and makes the application-owned safety decisions needed to substantiate an engine-specific adoption explicit. Those are reviewed application policy and evidence obligations; they do not accept or reject a materially different PHP program shape or add a framework runtime, dependency, checker diagnostic, schema builder, permission helper, or migration abstraction.

## Consequences

An AI can distinguish the properties every PHPThis migration adoption must preserve from the mechanisms demonstrated only by SQLite. A server-database consumer no longer has to pretend that `flock` coordinates its deployment or that all DDL rolls back with a ledger insert. Reviewers can identify the exact non-atomic states, authority handoff, and recovery evidence instead of relying on a generic "transactional migrations" claim.

Applications targeting another engine still carry substantial design and test work. That cost is intentional: a universal runner would conceal the very DDL, lock, privilege, topology, and recovery differences that must remain reviewable. The checksum proves history identity, not SQL correctness, authorization, performance, reversibility, or production readiness.

No framework migration API, schema builder, DSL, discovery rule, generic ledger or lock type, transaction callback, permission abstraction, automatic rollback, runtime SQL loading, HTTP-startup behavior, core change, contract-version change, or Strict Profile change is introduced.

## Reconsider when

At least two independent applications targeting the same non-SQLite engine prove a smaller repeatable boundary under materially different histories and deployment topologies, or an exact-engine adoption exposes an invariant that cannot be represented without unsafe ambiguity. Reconsider an engine-specific reference proof first. Do not generalize its transaction, locking, authority, or recovery mechanism into a cross-engine runtime without separate human approval and evidence.
