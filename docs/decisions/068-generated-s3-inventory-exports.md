# ADR 068: Generated S3 inventory exports and bounded internal reads

Status: accepted by the accountable maintainer on 2026-10-15 for offline implementation. Real AWS execution and production adoption remain unapproved and unverified. Consumer Contract 22; Strict Profile 4 and PHT001–PHT008 remain unchanged.

Scope refinement accepted on 2026-10-15: offline tests are sufficient for the reference recipe; real S3 and deployment verification are deferred until application adoption. This replaces the initial requirement to keep #109 open for live AWS evidence. It changes reference completion criteria, with no consumer migration or change to Contract 22's adoption requirements.

## Need and decision

Issue [#109](https://github.com/balgf/PHPThis/issues/109) needs application-generated artifacts and internal object reads. ADR 053 only describes PHP uploads and protected redirects. Extend its optional `AMAZON_S3_ADR053` profile with one concrete inventory-export operation. Keep its upload provenance, bucket, versioning, KMS, credential, transport, ownership and reconciliation requirements.

The application generates a fixed CSV from at most 1,000 typed SQLite inventory rows using one direct SELECT with LIMIT 1001. It rejects overflow. Generated bytes are an immutable operation value, never a fabricated `RequestUpload`. Bytes remain opaque, 1–65,536 inclusive, stored as `application/octet-stream`. No browser, HTTP upload, content-safety or spreadsheet-consumption claim is added.

Use the existing exact AWS SDK 3.392.1 and Guzzle 8.0.2 pins, with PSR-7 3.1.0 and a reviewed complete lock. The optional reference owns these dependencies. PHPThis runtime and skeleton gain none. Its concrete S3 calls remain visible; no storage interface, backend registry, middleware or discovery is introduced.

Reserve durable ownership and count/byte capacity before one conditional Put. Persist the exact non-null VersionId and require exact-version Head validation before acceptance. An internal read performs one exact-version Get into a bounded memory sink, validates retained metadata and actual SHA-256, then returns a typed byte value. Streams close on every outcome. Control/error bodies also have a bounded memory sink. Neither path stages bytes on disk.

Keep ADR 053's seven states. A definitive 412 releases this reservation as `failed_collision` without inspecting or deleting the conflicting object. Ambiguous writes retain capacity and are never replayed. An empty listing cannot resolve an ambiguous Put because it may complete later. Reconciliation only accepts one exact owned version after validation. Persist at most two deletion attempts across restarts; release capacity only after exact-version absence and a durable `deleted` transition. Missing ownership metadata requires incident recovery, never inference from a key name.

The reference selects single-host nonblocking flock, separate writer/reader/reconciler/deletion process inputs and short-lived identities, 24-hour eligibility, 32 live/reserved objects, 2 MiB and 256 retained identities. Reconciliation makes at most four remote calls in one pass. The application/deployment owns private SQLite durability, clocks, supervision, transport and process limits, IAM/KMS, monitoring, retention and restoration. Further archival, multi-host operation, active content and external URL delivery require their own decisions.

## Evidence and migration

[Generated exports](../file-transfers/generated-exports.md) owns current guidance and routes the executable reference. The existing offline recipe tests and complete framework `composer check` suffice for reference completion and #109. They prove application behavior and pinned SDK loopback transport, while retaining `REFERENCE_ONLY` status. They cannot prove Amazon S3, IAM, KMS, TLS deployment or production durability. The application-adoption gate continues to fail closed until its real-service and deployment evidence exists; it is not a reference-completion gate.

Existing applications keep their adopted upload/redirect or local policy. Adoption of the generated mode is explicit in the single application `.ai/file-transfers.md`; HTTP-only fields become explicitly inapplicable for a CLI-only operation. Keep the original seven-role upload/redirect verifier unchanged. The generated mode requires its own reviewed source, behavior, real-service and deployment modules under `file-transfers:s3:verify`. Dependency updates do not migrate metadata or authorize cloud work.
