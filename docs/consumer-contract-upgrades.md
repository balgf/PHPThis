# PHPThis consumer contract upgrades

This is the upgrade and history companion to the current [PHPThis application contract](consumer-contract.md). Load it only when upgrading an application across contract versions, reviewing contract evolution, or changing the decision history. Ordinary implementation uses the current contract and concern guide routed by [the knowledge map](knowledge-map.md).

## Contract evolution

### Contract version 16

Contract version 16 carries Contract version 15 and Strict Profile version 4 forward with permanent diagnostics `PHT001` through `PHT008`. Through [ADR 059](decisions/059-bounded-application-source-prefix-discovery.md), the installed checker retains only the exact lowercase direct and shebang forms for extensionless PHP, detects broader direct and launcher prefixes under unsupported suffixes or noncanonical extensionless names within a 4,096-byte bound plus one-byte lookahead, fails conservatively when a continuing prefix remains ambiguous or a non-`.php` regular file cannot be read, and rejects every application symlink outside dependency and VCS exclusions before target-content inspection.

Before adopting version 16:

1. Replace every application symlink outside the resolved Composer dependency directory and VCS directories with an application-owned regular file or real directory, or move genuinely dependency-owned material behind the resolved dependency boundary.
2. Give every PHP file the `.php` extension unless it begins at byte zero with exact lowercase `<?php`, or exact `#!/usr/bin/env php`, one PHP-PCRE newline sequence, and immediate lowercase `<?php`; retain the documented long-tag boundary and replace unsupported suffixes or noncanonical extensionless prefixes rather than adding an ignore.
3. Make every non-`.php` regular file readable. If its first 4,097 bytes can remain a direct or post-launcher PHP preamble at the 4,096-byte decision boundary, put decisive non-PHP content within that bound or relocate it outside the application tree under an existing ownership exclusion.
4. Run the complete application gate on PHP 8.4.x and retain application tests for every executable entrypoint and any migrated asset or generated-file path.

Version 16 adds no runtime API, dependency, configurable ignore, second manifest, new PHPStan configuration path, Strict Profile rule, or `PHT` diagnostic. A later prerelease containing it must publish the all-application-symlink, ambiguous-prefix, and unreadable-prefix failures as an intentional compatibility break; accepting the contract selects no release identity or publication operation.

### Contract version 15

Contract version 15 carries Contract version 14 forward and adopts Strict Profile version 4 with permanent diagnostic `PHT008`. Through [ADR 057](decisions/057-distinct-named-sql-placeholder-occurrences.md), every direct canonical `Connection` call whose SQL is accepted by PHT006 must use a distinct exact case-sensitive portable named placeholder for each occurrence in every finite statement alternative.

Before adopting version 15, run the installed checker over every application-owned PHP file. For each `PHT008` finding, rename every repeated occurrence and add the corresponding explicit parameter-array entry, preserving the original value and scalar type when several occurrences intentionally receive the same data. Keep the SQL PHT006-finite, raw, engine-specific, and visibly paired with its bindings; do not generate or rewrite it. Verify each changed statement against every recorded engine and version, retain SQL-looking bound-data, structural-choice, query-budget, trace, and authority evidence, then run the complete application gate on PHP 8.4.x.

PHT008 recognizes only `:[A-Za-z_][A-Za-z0-9_]*` through a fail-closed common lexical subset, not a dialect parser. It ignores doubled-terminator single- and double-quoted segments; boundary-valid PostgreSQL `E'...'` escape strings; terminated non-nested block comments whose opener is neither `/*!` nor `/*+`; `--` only when the following byte is `0x00` through `0x20` or input ends; and runs of `::` structural colons. Ambiguous SQLite bracket text, backslash quote escapes in ordinary quotes, every backtick and `#` spelling, PostgreSQL dollar-quote-looking text, no-space `--`, MySQL executable or optimizer-hint block comments, nested block comments, and unterminated lexical forms are scanned fail-closed and must be rewritten unambiguously if they trigger a finding. After one of those unsupported or ambiguous openers is encountered outside an already ignored region, the rest of that SQL alternative is scanned without further lexical exclusions, so nested quote- or comment-looking bytes cannot hide occurrences. PHT008 checks each finite alternative independently and emits one non-ignorable `phpthis.pht008` finding at the direct call when any alternative repeats a name. `Connection` retains its existing parameter-key grammar and optional-leading-colon normalization. Version 15 adds no runtime SQL parser, binding-array comparison, positional-placeholder support, SQL rewrite, placeholder helper, query builder, dialect abstraction, runtime dependency, public runtime API, or core line. A later prerelease that includes this decision must publish the new rejection and migration as an intentional prerelease compatibility break. This contract change selects no release identity and authorizes no tag, package, release, or announcement.

### Contract version 14

Contract version 14 carries Contract version 13 forward and retains Strict Profile version 3 and permanent diagnostics `PHT001` through `PHT007`. Through [ADR 056](decisions/056-bounded-request-target-and-path-bytes.md), it adds one exact raw-byte exclusion to the existing request-target and path representations:

- the complete string-valued `REQUEST_URI`, including any query suffix, is validated before the first-`?` split and rejects raw bytes `0x00` through `0x20` and raw `0x7F` in addition to the existing 8,192-byte and fragment rules;
- direct `Request` and `Route` path-only values reject those same raw bytes in addition to the existing non-empty, leading-`/`, no-query, and no-fragment rules;
- the three fixed diagnostics do not echo the supplied target or path; and
- percent spellings, slashes, repeated slashes, dot segments, backslashes, and bytes `0x80` through `0xFF` remain raw and are not decoded, normalized, rewritten, or newly rejected. Existing route types, placeholder bounds, precedence, overlap checks, and unchanged-byte delivery remain in force.

Before adopting version 14, an application inventories direct `Request` construction, explicit `Route` declarations, alternate SAPI adapters, deployed ingress behavior, and fixtures that supply `REQUEST_URI`; removes every newly excluded raw byte; and confirms that no path depends on PHPThis trimming, decoding, or repairing a rejected representation. It adds adversarial evidence for the lower and upper excluded-byte boundaries, representative controls, raw space, DEL, query-suffix rejection before the split, direct request and route rejection, fixed non-disclosing diagnostics, and zero routing or handler work after reader rejection. It retains ordinary request-path and raw percent, slash, dot, backslash, and applicable high-byte evidence, verifies material server and proxy behavior separately, and runs the complete application gate on PHP 8.4.x.

Version 14 adds no Strict Profile rule, `PHT` diagnostic, checker rule, accepted-PHP syntax, decoder, normalizer, redirect, route type, runtime dependency, alternate request boundary, server policy, or proxy policy. The core remains 2,618 physical lines under the accepted 2,620-line ceiling; the remaining two lines authorize no adjacent mechanism. A later prerelease that includes this decision must publish the new rejections and migration as an intentional prerelease compatibility break. This contract change selects no release identity and authorizes no tag, package, release, or announcement.

### Contract version 13

Contract version 13 carries Contract version 12 forward and retains Strict Profile version 3 and permanent diagnostics `PHT001` through `PHT007`. Through [ADR 053](decisions/053-application-owned-amazon-s3-file-transfers.md), it splits the prior unconditional file-transfer path into common bounded multipart/application-policy requirements and exactly one deliberately selected optional profile:

- `LOCAL_ADR026` preserves ADR 026's visible `move_uploaded_file`, local `LocalFileBody`, complete `200`, `nosniff`, and deferred-range behavior unchanged; or
- `AMAZON_S3_ADR053` replaces only that durable-move and local-response portion with the exact accepted application-owned direct-S3 profile and evidence route. Its fixed `application/octet-stream` attachment is served by an exact-version pre-signed `GetObject` without a guaranteed `nosniff` header. This is an accountable profile-specific exception, not a claim that the application's `303` governs S3's separate response and not a relaxation of `LOCAL_ADR026`.

Before adopting version 13, an application with no file transfers keeps multipart disabled and records `NOT_APPLICABLE(FILE_TRANSFER)`. An existing local adopter records `LOCAL_ADR026`, confirms its accepted local behavior and evidence are unchanged, and runs the complete application gate. An S3 adopter records `AMAZON_S3_ADR053`; pins and implements the exact installed Amazon S3 guidance; supplies the application-owned static, behavior, isolated real-AWS, and dated deployment evidence; wires `file-transfers:s3:verify` through `test` into `check`; and fails closed when any required evidence is absent. A static or synthetic reference pass alone is not adoption or production evidence.

Version 13 adds no framework S3 client, AWS dependency, credential provider, presigner, retry policy, storage interface, facade, registry, lifecycle worker, provider-neutral backend selection, core PHP, accepted-PHP syntax, Strict Profile rule, or checker diagnostic. ADR 026 remains accepted and is partially superseded only for its remote-object-store and pre-signed-delivery exclusion when an application explicitly selects `AMAZON_S3_ADR053`. Updating PHPThis does not select a profile, alter an application's project-owned context, authorize an AWS environment change, or certify an external deployment.

### Contract version 12

Contract version 12 carries Contract version 11 forward and retains Strict Profile version 3 and permanent diagnostics `PHT001` through `PHT007`. Through [ADR 049](decisions/049-bounded-response-cookie-profile.md), it narrows the existing public cookie constructors rather than adding a second cookie path:

- a cookie name remains an HTTP token and its value remains cookie-safe ASCII, with `strlen($name) + strlen($value)` at most 4,096 bytes;
- `Path` is an absolute 1-to-1,024-byte ASCII value beginning with `/`, using bytes `0x21` through `0x7E` except `;`;
- `expiresAt`, when present, is from `1` through the smaller of `PHP_INT_MAX` and `253402300799`, inclusive, so every supported platform retains a four-digit UTC year; `maximumAgeSeconds`, when present, is from `0` through `34560000`, inclusive;
- when both expiration attributes are present, `Max-Age` is authoritative and `Expires` is its fallback rather than an inferred clock-relative equality;
- one response contains at most 50 cookies, has no repeated case-sensitive cookie name regardless of path, and has at most 8,192 aggregate bytes across its `ResponseCookie::headerValue()` results;
- ASCII-case-insensitive `__Secure-`, `__Host-`, `__Http-`, and `__Host-Http-` prefix recognition enforces their respective `Secure`, root-path, and `HttpOnly` requirements without normalizing the supplied name; and
- `Domain`, `Partitioned`/CHIPS, and `Priority` remain unsupported. Every accepted cookie is host-only, separate `Set-Cookie` emission remains mandatory, and manually encoded `Set-Cookie` remains invalid.

Session-cookie evidence asserts the exact configured name and identifier, `Path=/`, `HttpOnly`, explicit SameSite and deployment-selected `Secure`, absent live `Expires` and `Max-Age`, and the complete serialized field. Deletion evidence asserts the same identity and scope, an empty value, a past `Expires`, `Max-Age=0`, and the complete serialized field. “No `Expires` or `Max-Age`” replaces “browser-session lifetime”: browser restoration may retain such a cookie, while idle and absolute expiry remain application policy. `HttpOnly` prevents ordinary script access to the cookie bytes but does not prevent script-initiated authenticated requests or replace XSS, CSRF, CSP/output, endpoint, or logging controls. Production authentication and session cookies normally require `Secure` through an end-to-end reviewed HTTPS deployment; an insecure cookie belongs only to an explicitly isolated development profile. Cookie prefixes depend on supporting user agents and do not isolate ports.

Before adopting version 12, an application inventories every `ResponseCookie` construction and response-copy path; replaces every value outside the accepted grammar and bounds; removes or renames same-name cookies even when paths differ; confirms deliberate `Max-Age` precedence when both expiration attributes are present; and adds the exact live and deletion session-cookie evidence when sessions are adopted. It retains application ownership of HTTPS, authentication, authorization, CSRF, idle and absolute expiry, logout, revocation, browser integration, and deployment policy, then runs the complete application gate on PHP 8.4.x. A future prerelease containing this decision must publish those newly rejected constructions as an intentional prerelease compatibility break.

Version 12 adds no Strict Profile rule, checker diagnostic, accepted-PHP syntax, runtime dependency, cookie jar, middleware, global helper, authentication mechanism, browser runtime, or alternate session lifecycle.

Contract version 11 carries contract version 10 forward and retains Strict Profile version 3. It rejects final `1xx` responses, `Transfer-Encoding`, mismatched ordinary `Content-Length`, and ordinary body or `Content-Length` framing on `204`, `205`, and `304`; keep `HEAD` route handling explicit rather than inferring or suppressing a representation. It also makes session cleanup deterministic: cleanup success preserves the exact original failure, while a second cleanup failure is retained with that original through the narrow redacted `SessionCleanupFailed` and cannot be selected through registered response mapping. Before adopting version 11, replace contradictory response construction with one supported explicit response, add exact response-framing and session-cleanup precedence evidence, and run the complete application gate. Version 11 adds no new Strict Profile rule, dependency, logger, retry, middleware, response emitter request path, ORM, permission mechanism, or generic session/response abstraction.

Remove alternate reads, mutation, imports, wrappers, callable indirection, and indexed or non-canonical bare `$_SERVER`. Contract version 7 carries contract version 6 and Strict Profile version 2 forward.
