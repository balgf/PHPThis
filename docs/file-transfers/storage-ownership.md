# Storage ownership

Storage is an application operation, not a framework backend abstraction. Under `LOCAL_ADR026`, the example's one concrete `LocalDocumentFiles` owns this visible sequence:

1. verify upload error, operation byte limit, `is_uploaded_file`, and actual size;
2. generate a random code-owned identifier;
3. require a deployment-precreated non-symlink `0700` root and reserve one verified `0700` directory beneath it;
4. call `move_uploaded_file` to a fixed `content` destination;
5. use post-move `lstat` to verify regular non-symlink type, the exact `PendingDocumentUpload` byte count, and `0600` permissions; and
6. return only the generated identifier.

Before a successful move, PHP owns the temporary upload and removes it at request termination. Its temporary path is request-scoped input only and is never persisted, enqueued, logged, traced, or reused; durable work receives only the application-owned destination or bounded reference established after the move. After the move, the application owns the destination. If post-move verification fails, the operation visibly attempts to remove the destination and directory it created before the identifier can be returned or published. Checked filesystem calls suppress native path-bearing warnings and return only named path-free failures. PHPThis performs no destructor cleanup, shutdown cleanup, retention sweep, or background deletion.

The adoption record separates a dedicated effective web-SAPI `upload_tmp_dir` from durable storage and names one authoritative owner for each transition. The temporary root records the exact non-public path, named non-root request identity, owner, group, exact ACL or explicit `NONE`, modes, no-execute mount policy, capacity/inode monitoring and alert owner, request-termination behavior, and one bounded age/action owner for stale files. Deployment or test setup pre-creates the durable root before HTTP handling with its exact owner, group, ACL-or-`NONE`, modes, regular/non-symlink rules, local-versus-network/mount lifecycle, unrelated-writer exclusion, capacity/inode monitoring, and topology. The request identity has no authority or operational need to create, chmod, chown, repair, or replace the durable root. Neither root belongs in the public document tree or release directory, and uploaded bytes are never executable. A configuration file is not evidence of the effective web-SAPI path or authority.

Reads recheck the non-symlink `0700` root and identifier directory plus the `0600` file before returning a local-file response. The application authenticates, resolves any tenant, and authorizes the named download before lookup when existence is confidential; every retained metadata row, storage identity, and query remains bound to the applicable tenant, owner/principal, and named action, with inapplicable dimensions recorded. The application records collisions, overwrite behavior, quota reservation and release, content policy, retention start and expiry, legal hold, deletion, orphan and partial-write recovery, backup, replication, recovery, filesystem authority, and multi-host topology. A local filesystem proof does not establish network storage semantics.

When byte identity or integrity is claimed, record one exact digest algorithm and its computation point, trusted stored representation, verification points, mismatch behavior, content-reinspection interaction, retention, deletion, replica/backup and restore treatment, and algorithm transition. The example's test-only upload-time hash comparison proves one fixture copy only; byte count and `LocalFileBody` do not retain or verify an integrity digest.

Quota checks are not a count-then-write race hidden behind a helper. Name the concrete operation that atomically reserves capacity, its consistency and concurrent-writer behavior, the exact request/principal/tenant/resource/deployment/egress dimensions it enforces, and one reconciliation path that repairs accounting after failed moves or cleanup. Record whether retries create duplicates or use a bounded application-owned idempotency key and exact replay response. When a lifecycle operation deletes or reclassifies files, give it a finite selection bound, least authority, explicit failure result, supervision, replica/backup propagation and restore policy, and tests rather than implicit request-time or destructor cleanup.

Do not extract an interface merely to rename this operation as generic storage. A remote object store, pre-signed delivery, or proxy offload requires an accepted application path and failure contract.

Accepted ADR 053 and its [Amazon S3 page](amazon-s3.md) define one such direct-S3 path under `AMAZON_S3_ADR053`. They do not change the `LOCAL_ADR026` storage sequence above, authorize another remote store, or introduce a shared storage interface.
