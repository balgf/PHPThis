# Generated inventory and audio exports in Amazon S3

Consumer Contract 22 and [ADR 068](../decisions/068-generated-s3-inventory-exports.md) extend `AMAZON_S3_ADR053` with a concrete generated inventory export and bounded internal read. Use this alongside the existing [S3 owner](amazon-s3.md) for bucket, KMS, credentials, transport and operational obligations. The original HTTP upload/redirect path keeps its existing verifier and provenance requirements.

The [optional executable reference](https://github.com/balgf/PHPThis/tree/main/tools/generated-s3) implements this application operation. Its evidence is `REFERENCE_ONLY`: local SQLite lifecycle tests, synthetic SDK results and actual pinned SDK/Guzzle requests to a synthetic loopback server. These offline checks and the complete framework `composer check` are sufficient to verify and maintain the reference recipe. Real S3 and deployment verification are deferred until application adoption. A successful framework check does not grant S3 adoption.

## Generate and retain

Select up to 1,001 inventory rows in one constant SQL query, ordered by SKU. Reject more than 1,000. Parse each row once into a typed SKU/quantity value: SKU is 1–32 ASCII uppercase letters, digits, underscore or hyphen, starting with a letter or digit; quantity is an integer from 0 through 2,147,483,647. Emit fixed `sku,quantity` columns and LF newlines. Retain 1–65,536 bytes as `OPAQUE_BYTES`, not inspected or spreadsheet-certified content.

Generate one random 128-bit identity and the existing `private-documents/v1/{32-lowerhex}/content` key. Persist the trusted digest, size, exact bucket/account/region/KMS binding and 24-hour expiry while atomically reserving capacity. Only then issue one `PutObject` with a memory stream, exact length/checksum, fixed metadata/content type, STANDARD, conditional create and SSE-KMS. Require its exact nonempty/non-`null` VersionId and checksum, persist `stored`, then validate the exact version using Head before `accepted`. Never fabricate upload provenance or reuse an identity.

The retained-object check requires matching size, SHA-256, version, KMS key, `aws:kms`, `BucketKeyEnabled: false`, fixed content type and profile metadata. StorageClass, ArchiveStatus, Restore and Expiration must be absent. ContentEncoding, ContentRange and DeleteMarker are also rejected. STANDARD is requested on Put but is absent in a valid Head result; returning the string STANDARD is not equivalent.

## One synthetic media producer

The optional `generate-test-tone` command produces a fixed audio-path test artifact: exactly one second of mono 16 kHz signed 16-bit PCM WAV, 32,044 bytes. A 16-sample rounded 1 kHz sine cycle with peak magnitude 4,096 repeats 1,000 times. Its two-chunk representation fits the [accepted WAV profile](inspected-wav.md) and the existing 64 KiB S3 cap. The command accepts no frequency/duration parameter, source media, filename or path. It does not play audio or establish loudness, device calibration, hearing safety or player compatibility.

After validating writer configuration and the CA/credential lifetime, the sole console runs one fixed private PHP worker before opening SQLite or constructing the S3 client. The worker receives no application input or inherited credentials and writes only its generated bytes to stdout. The parent requires successful exit, clean EOF, empty diagnostics, exact length and the independently verified version-1 fixture digest before it creates the immutable operation value or reserves storage. These are known-output checks; the retained object remains `OPAQUE_BYTES` with the existing content type and metadata. No PHP upload is fabricated and no payload is staged on disk.

The worker uses the current absolute PHP binary, an array command, `-n`, a 16 MiB PHP allocation limit and two-second PHP execution limit. The parent independently enforces three seconds of wall time, drains both streams, and caps stdout at 32,044 bytes and stderr at 1,024 bytes, with one overflow-detection byte each. Cleanup allows TERM/250 ms then KILL/one second and requires confirmed stop before acceptance. Diagnostics, nonzero exit, timeout, partial, corrupt or excess output fail before reservation or S3 work. A later explicit command may try again after cleanup.

The fixed worker must be a regular non-symlink, non-hardlinked release file. Its code-owned working directory and release need immutable deployment ownership. The trusted worker has no descendant creation; this process boundary is not an OS sandbox or total RSS guarantee. The external supervisor owns the complete parent/child process scope, OS memory bound and existing 60-second command deadline, including parent death. See the reference's single application policy for the exact configuration and resource facts.

CSV and WAV reuse the same concrete private retention path, ledger, quotas, versions, bounded internal reads, 24-hour eligibility and ambiguity/deletion rules. No schema or retained-object migration is needed. Before reservation, an interrupted generation leaves no stored object; afterward, the recorded state owns reconciliation and an uncertain Put is never replayed. The internal reader returns integrity-checked opaque bytes and infers no producer/format from an identifier. A generator revision requires deliberate new evidence; already retained opaque objects keep their recorded eligibility. Consumer Contract 26, Strict Profile 4 and framework dependencies remain unchanged.

## Internal consumption and bounds

An internal reader needs its separately scoped workload authority and an accepted, unexpired authoritative row. Hold the shared application lock through reading and validation. Issue one exact-version Get with expected bucket owner and checksum mode. The pinned PSR-7 `DroppingStream` wraps `php://memory`, capped at the recorded size. Guzzle's explicit cURL handler rejects short sink writes. Disable retries, redirects and decompression. Verify complete byte length and actual SHA-256 before returning the immutable byte value; recheck expiry before handing it off. The console's `verify` command discards those bytes and emits only its finite outcome.

The reference caps control/error response bodies at 16 KiB, data at 64 KiB, PHP allocation at 64 MiB, connects at two seconds and each S3 operation at ten seconds. One command performs one operation: generate uses at most Put + Head; read uses one Get; reconciliation/deletion uses at most four calls. An external supervisor enforces a 60-second process deadline and a separately recorded OS memory bound. No polling, replay, default disk buffering or unclosed stream is part of the recipe.

Use single-host nonblocking exclusive locks for mutations and shared locks for reads. The application precreates private SQLite metadata and the lock, excludes unrelated writers and verifies storage durability. It reserves at most 32 live/ambiguous objects and 2 MiB, and retains at most 256 identities including tombstones. Reaching the history limit stops new generation; production history archival is a separate decision. The 24-hour deadline ends eligibility, while supervised physical deletion may remain unresolved during an outage.

## Failure and reconciliation

| Observation | Outcome |
| --- | --- |
| Proven local failure before send | Failed, reservation released |
| Definitive conditional-create 412 | Failed collision; never inspect, adopt or delete the conflicting object |
| Uncertain Put, contradictory result, interruption or metadata promotion failure | Non-serving pending/stored/reconciliation-required ownership; capacity retained; no repeated Put |
| Empty exact-key listing after uncertain Put | Unresolved; an earlier remote write can still complete |
| One exact current version with fully matching Head | Accepted; expiry still controls consumption |
| Marker, sibling, multiple versions, truncation, changed known version or lost metadata | Incident/restore path; no broad discovery or deletion |
| Expiry | Persist deletion-pending and attempt accounting before exact-version Delete |
| Verified post-delete absence | Persist deleted, then capacity is released; later deletion is a no-op |

Deletion permits one initial attempt and at most one reconciled attempt across process restarts. A reconciled pass observes the exact version, validates it, deletes it and verifies absence. A lost response retains the attempt; a later empty listing can resolve that deletion. Each process has only its named actions. The reconciler cannot perform deletion; the deletion process owns its bounded reconciliation. No transaction spans SQLite and S3.

## Reference verification

Run `composer test:generated-s3` for the recipe and `composer check` for the complete framework gate. No AWS account, credentials or cloud requests are required. Tests cover lifecycle, ownership, shared quotas, reconciliation, deletion, source/configuration and CLI behavior, plus SDK request/response handling and bounded transport failures. The WAV proof independently reproduces every sample with Python, exercises the real worker/console, confirms zero protected effects on generation failure, and sends its bytes through the SDK loopback transport with corrupt and excessive responses. Preserve their assertions and the `REFERENCE_ONLY` result.

Base synthetic responses on the documented S3 operations and the pinned SDK's request/result shapes. Keep documentation-derived expectations separate from actual service observations: a mock and its caller can share an incorrect assumption. Offline evidence verifies the application behavior and SDK loopback path; it cannot establish deployed IAM/KMS permissions, real S3 responses or production durability. Do not make the application-adoption command succeed merely because the reference checks pass.

## Application adoption and deferred AWS proof

Record the generated operation in the application's single `.ai/file-transfers.md`. Record CLI-only ingress, browser authentication, tenant and CSRF dimensions as inapplicable when that is actually true. The one configuration reader owns distinct process input names; the sole console owns the finite command map. An HTTP adopter must add the existing explicit authentication/authorization/CSRF sequence before protected work.

Keep source, offline behavior, actual selected-backend behavior and dated deployment facts separate. The original [verification template](amazon-s3-verification.md) covers its seven upload/redirect roles; it does not verify this extension. At adoption, the generated application owns the additional source and evidence under the same `file-transfers:s3:verify` alias. Missing real-service or deployment evidence fails that adoption gate, even when all offline tests pass. That expected failure does not prevent completion of the framework's reference recipe or issue #109.

When an application adopts the recipe, identify the non-production account, region, private versioned bucket, KMS key, four least-privilege short-lived identities and exact immutable runtime/CA facts before cloud work. Approve a frozen packet with at most eight generated objects / 512 KiB, 100 S3 calls including reserved cleanup, bounded KMS activity, exact owned keys/versions and a private cleanup ledger. Prove actual writes/reads, checksums, KMS and authority denials, version mismatch, ambiguous outcomes and exact-version cleanup. Do not provision resources, use an emulator as AWS evidence or discard ambiguous ownership. The executable AWS driver and resource-specific assertions are deferred to that application's packet; reference completion authorizes no cloud call.
