# File-transfer security

The accepted profiles narrow attack surface but are not complete upload-security systems. Apply the common controls plus the exact selected-profile controls.

- Enforce compatible limits before PHP and again at the application operation.
- Record dated effective proxy, web-server, and PHP web-SAPI controls, including `max_multipart_body_parts`; use it to bound total raw parts, never as proof that duplicate scalar names were rejected before normalization.
- Reject multiple, nested, text-field, chunked, malformed, and control-bearing input before storage.
- Ignore client path, filename, extension, and media type for executable decisions.
- Verify PHP upload provenance and actual bytes immediately before the selected storage operation. Treat the PHP temporary path as request-scoped input only; never persist, enqueue, log, trace, or reuse it after the request, and give durable work only an application-owned destination or reference established by that operation.
- Generate storage identities with sufficient randomness and keep fixed stored names outside the public tree.
- Use a dedicated effective web-SAPI `upload_tmp_dir` with exact owner/group, ACL or explicit none, modes, no-execute/non-public mount, capacity/inode monitoring, and stale cleanup. Under `LOCAL_ADR026`, deployment also pre-creates the separate durable root before HTTP handling; the non-root request identity cannot and need not create, chmod, chown, repair, or replace it. Keep local roots outside the release directory, and exclude unrelated durable-root writers. Under `AMAZON_S3_ADR053`, use its exact private bucket, key, KMS, versioning, lifecycle, and least-authority boundary instead of inventing a filesystem analogue.
- Return the fixed response posture of the selected profile with explicit cache policy and no reflected filename. `LOCAL_ADR026` requires `nosniff`; `AMAZON_S3_ADR053` accepts its absence only on the separate direct-S3 response.
- For protected upload, keep `authenticate -> resolve tenant when applicable -> authorize upload -> validate CSRF when applicable -> rate/concurrency admission -> atomic quota reservation -> storage` visible and fail before every later step. Authorize the named protected-download action before lookup when existence is confidential. `SameSite` and an opaque identifier are not permission.
- Bind retained metadata and every generated storage identity to the applicable tenant, owner or principal, and named authorization action through lookup, durable path resolution, lifecycle, and audit. Record each inapplicable dimension explicitly.
- Choose exactly one content posture. `OPAQUE_BYTES` uses fixed code-owned stored/download names and only an `application/octet-stream` attachment, explicit cache, and recorded authentication/authorization; `LOCAL_ADR026` also requires `nosniff`, while accepted `AMAZON_S3_ADR053` cannot guarantee it on S3's response. Neither posture is content-safety certification. `INSPECTED_CONTENT` uses byte-derived classification with a finite allowlist, pinned parser or scanner, process isolation, time, memory, nesting and decompression bounds, update ownership, quarantine and failure policy, and executable malicious and malformed fixtures.
- Treat a successful inspection as one bounded signal from the exact tool, version, configuration, signatures, timestamp, and byte identity tested. It does not prove that content is universally safe, free of unknown malware, harmless to every downstream parser, or unchanged after inspection.
- Version the complete inspection definition. Pending, scanner-error, rejected, and quarantined states remain non-serving until one recorded accepted promotion. A tool, configuration, signature set, accepted-format allowlist, or application-policy change does not retroactively upgrade retained content. Record whether that change triggers bounded reinspection, with explicit non-serving state, result transition, accepted promotion, completion and failure recovery, or leaves retained bytes under the named earlier definition with an explicit stale-inspection consequence.
- Enforce recorded per-operation and applicable principal, tenant, resource, byte, count, rate, and aggregate quotas with an explicit concurrent reservation and release policy. Fail closed when the selected quota owner is unavailable unless an accountable application decision says otherwise.
- If the application claims byte identity or integrity, compute, retain, and verify a digest using one exact algorithm and recorded computation, storage, mismatch, update, reinspection, retention, deletion, backup/restore, and algorithm-transition lifecycle. A byte count, an upload-time test hash, or `LocalFileBody` is not durable integrity evidence.
- Give retention start, expiry, deletion, orphan and partial-write recovery, backup, restore, legal hold, temporary cleanup, and incident response one named owner and path each. Cleanup failure remains visible and redacted; it never becomes hidden destructor behavior.
- Record fail-closed, redacted outcomes and recovery for every selected storage and response transition. `LOCAL_ADR026` covers move/response failure, ambiguous client retry after completion, process crash, disk full, inode exhaustion, permission failure, and partial cleanup. `AMAZON_S3_ADR053` follows its finite pre-send/write/validation/redirect/reconciliation/exact-version-deletion failure table without inventing local move or disk outcomes.
- Keep rejected metadata, paths, stored bytes, and identifiers out of public errors and terminal summaries.

Applications handling active content, archives, media, personal data, or regulated records must add explicit content inspection, parser isolation, decompression limits, quota, retention, deletion, audit, backup, legal, and incident-response policies. Image processing, antivirus scanning, and content-type inference are not PHPThis features, and PHPThis supplies no generic authentication, tenant, CSRF, quota, scanner, storage, or lifecycle API.

## Accepted direct-S3 exception

Accepted ADR 053's [Amazon S3 profile](amazon-s3.md) preserves the bounded multipart and protected request-policy requirements above but cannot preserve the local opaque-byte `nosniff` response header on direct S3 delivery. Fixed `application/octet-stream` and attachment disposition remain mandatory; S3's finite response overrides cannot add `X-Content-Type-Options`. A header on the application's redirect does not govern S3's later response.

Contract version 13 accepts that limitation as a narrow `AMAZON_S3_ADR053` exception. It is not a quiet relaxation of `LOCAL_ADR026`, and the profile still excludes a PHP proxy and CDN/offload workaround. An application needing such a response-header layer requires a separately accepted path and evidence.
