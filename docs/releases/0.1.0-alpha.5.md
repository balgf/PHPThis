# PHPThis 0.1.0-alpha.5

Release identity: `0.1.0-alpha.5`. Publication state is external; verify the approved tags and Packagist packages.

- Composer version: `0.1.0-alpha.5`
- Framework tag: `v0.1.0-alpha.5`
- Skeleton tag: `v0.1.0-alpha.5`

These notes describe the accepted bounded Alpha 5 source claim. Identity and candidate-preparation approval do not announce or authorize either tag, either package, the dedicated-skeleton update, a GitHub release, or the public installation path. Every external operation remains subject to the complete release proof and later accountable-human authorization in `RELEASING.md`.

## Purpose

Alpha 5 carries the complete Alpha 4 foundation forward and rolls up six bounded post-Alpha-4 changes: a maintainer-only PHPUnit runner, Composer-first consumer onboarding, one typed application configuration boundary with `PHT007`, a database setup scope gate, an application-owned database authority lifecycle, and recommended migration placement.

This prerelease remains experimental evaluation software. It is not production-ready and makes no backward-compatibility promise across prereleases.

## Maintainer testing and Composer-first setup

The framework repository now uses PHPUnit 13 to expose its duplicate-checked named behavior inventory as independently selectable data sets. CI emits machine-readable test reports and report-only coverage. This improves framework-maintainer diagnosis without changing application validity or runtime behavior.

PHPUnit is a root `require-dev` dependency, requires PHP 8.4.1 or newer for framework maintenance, and is excluded from the framework distribution. It is not a Consumer Contract requirement or skeleton test-runner choice. Applications continue to own their test library, organization, and `composer test` implementation while every observable behavior change still requires automated evidence.

Consumer onboarding now states one unambiguous path: create a new application with the published `phpthis/skeleton` Composer project. Cloning this repository is only for framework development or source evaluation. The tracked command remains subject to public-artifact proof and does not itself claim package availability.

## Typed application configuration and PHT007

ADR 036 advances the Consumer Contract from version 9 to version 10 and the Strict Profile from version 2 to version 3. Permanent diagnostic `PHT007` requires all direct process-environment reads in the application Composer project to occur in one application-owned PHP file as `\getenv('EXACT_LITERAL_KEY')`. Applications validate those values before application-controlled I/O into process-specific final readonly types and inject only the adopted process's required configuration through visible composition.

Runtime, worker, migration, and administrative configuration remain separate without credential fallback. A configuration-only database setup may record connection composition as deferred rather than inventing a connection. The framework adds no configuration service, string-keyed bag, global helper, facade, container, provider, automatic discovery, dotenv loader, secret-manager abstraction, or hidden reload.

`PHT007` checks exact structural access and one-file confinement. It does not detect hard-coded secrets, arbitrary secret-manager calls, dynamically obscured access, unsafe deployment permissions, incorrect parsing, overprivileged identities, or disclosure after parsing. Runtime tests, secret scanning, deployment review, and engine-specific authority evidence remain separate obligations.

`Connection::connect` marks its password parameter with PHP's native `#[\SensitiveParameter]` attribute. That reduces accidental stack-trace disclosure; it is not encryption, secret storage, log redaction, or proof that downstream code cannot expose the value.

## Database setup scope gate

ADR 037 separates two decisions before an ambiguous database-engine request can cause external I/O or mutation:

1. configuration structure only, connection to an existing server, or project-local server provisioning; and
2. deferred migrations or an application-owned migration foundation.

Local development is context, not authority to connect, install, provision, create identities, mutate schema, or prepare production operations. Explicit requests proceed without redundant questions. This is AI-authoring guidance with installed-consumer distribution evidence; it adds no database provisioning command and cannot guarantee that every model asks the question correctly or completes within a particular duration.

## Application-owned database authority lifecycle

ADR 038 distinguishes successful authentication and migration completion from usable runtime authority. An adopting application records its exact engine and version, supported namespace selection and qualification, namespace and object control-or-ownership model, each named operation's required and prohibited actions, applicable effective-authority sources, one activation and deactivation owner and path, exact-engine verification, and release ordering through traffic enablement and later authority removal.

PHPThis neither requires nor discourages an engine-default or application-specific namespace. Withholding all runtime object access is valid before a named operation exists. Before dependent code receives traffic, the runtime identity must execute that operation's intended statements and safely demonstrate selected prohibited actions against the recorded engine and version.

Authority activation may use visible engine-specific SQL in a forward migration, a separately authorized application console or deployment operation, or named external provisioning. PHPThis chooses none of those paths and adds no permission helper, grant API, role registry, framework-owned generic or request-time privilege introspection, schema builder, deployment hook, or HTTP authority transition. Application-owned deployment and test evidence may use safe engine-supported authority inspection.

The installed checker rejects one narrow contradiction: a direct canonical `Connection::connect` call cannot coexist with `.ai/data.md` declaring `NOT_APPLICABLE(DATABASE)`. It does not connect to a database, inspect grants, prove authorization, or certify runtime readiness.

## Recommended migration placement

ADR 039 defines migrations as specialized application-owned database evolution and recommends this source location for a newly adopting application:

```text
src/
  Database/
    Migrations/
```

The application records its actual path and namespace in `.ai/migrations.md`. Any coherent application-owned alternative remains valid, and established source is not moved without explicit accountable-human approval of the namespace, autoload, command, test, and deployment effects. The checker does not enforce, discover, order, or relocate migrations from their directory.

Multiple named connections may receive application-selected subdivisions only when they genuinely own independent migration histories. The recommendation creates no generic `Database/Queries` directory, repository layer, query-object layer, alternate SQL boundary, schema builder, migration runtime, portable DDL, or empty migration directory in the database-free skeleton.

## Upgrade from Alpha 4

Alpha 4 consumers move from Consumer Contract version 9 to version 10 and Strict Profile version 2 to version 3:

1. Add `.ai/configuration.md`, or retain the documented configuration-free state only when the application reads no process environment.
2. Inventory and centralize every process-environment read in one application-owned PHP file using exact direct `\getenv` calls.
3. Validate before application-controlled I/O into process-specific final readonly values. Keep runtime and elevated inputs separate without fallback, and record parsing, failure, redaction, rotation, and composition evidence.
4. If database access is adopted, record the engine-specific namespace, control-or-ownership, operation authority, activation, verification, and rollout facts required by ADR 038. Connectivity and migration completion are not readiness evidence.
5. If migrations are adopted, record their actual source path and namespace. Preserve a coherent existing layout; do not move it merely to match the new-application recommendation.
6. Keep the application's selected test library unless the application independently changes it; PHPUnit 13 is maintainer-only.
7. Update to the exact Alpha 5 prerelease only after reviewing these changes, then run the complete application gate on PHP 8.4.x.

## Carried-forward boundary

Alpha 5 retains zero third-party framework runtime dependencies, explicit manual composition, immutable HTTP values, finite route declarations, direct visible SQL through `Connection`, bound data, compile-time-constant SQL structure, query budgets and traces, and separately certified PDO transport for SQLite, MySQL 8.4, and PostgreSQL 17. The 2,600-line core ceiling remains unchanged; the current core occupies 2,593 lines and its seven-line margin authorizes no adjacent mechanism.

The release does not add or permit:

- an ORM, Active Record, lazy loading, model or repository layer, query builder, generated SQL, binding or placeholder helper, generic paginator, dialect abstraction, or generic database layer;
- implicit or global scopes, observer magic, automatic discovery, reflection-based wiring, service container, facade, global helper, macro system, dynamic proxy, or autowiring;
- a framework configuration runtime, provisioning API, schema builder, migration framework or DSL, permission helper, role registry, framework-owned generic or request-time grant inspection, portable DDL, or automatic deployment hook;
- generic or framework middleware, a hidden request pipeline, request-context bag, native WebSocket runtime, real-time gateway, channel, broadcaster, or pub/sub abstraction;
- hidden database calls, database work inside loops, hidden retries, automatic cache refill or invalidation, automatic job or migration discovery, inferred rollback, or exactly-once external-effect claims; or
- production readiness, a support or security-response SLA, complete CRUD, universal AI compliance, secret detection, grant validation, portable application SQL or DDL, deployment certification, or capacity certification.

Consumers remain responsible for product abstractions, identity, tenancy, authorization, schema, database plans and authority, concurrency, deployment, operational limits, observability destination, third-party runtimes, and complete behavior evidence.
