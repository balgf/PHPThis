## Breaking prerelease change: bounded response cookies

ADR 049 retains the existing `ResponseCookie` constructor and response-cookie emission path while rejecting values outside a finite interoperable profile:

- the cookie name remains an HTTP token and the value remains cookie-safe ASCII, with at most 4,096 combined bytes;
- `Path` is an absolute 1-through-1,024-byte value beginning with `/` and containing only bytes `0x21` through `0x7E` except `;`;
- `expiresAt`, when present, is from `1` through the smaller of `PHP_INT_MAX` and `253402300799`, inclusive, and must serialize with a four-digit UTC year;
- `maximumAgeSeconds`, when present, is from `0` through `34560000`, inclusive;
- one response contains at most 50 cookies, has no repeated case-sensitive cookie name even when paths differ, and has at most 8,192 aggregate bytes across its `ResponseCookie::headerValue()` results, excluding transport-owned `Set-Cookie: ` field-name and line-framing bytes; and
- ASCII-case-insensitive `__Secure-`, `__Host-`, `__Http-`, and `__Host-Http-` recognition enforces the accepted `Secure`, root-path, and `HttpOnly` combinations without changing the caller's name.

`Max-Age` is authoritative when both lifetime attributes are present, with `Expires` as the fallback rather than an inferred clock-relative equality. Every accepted cookie remains host-only. `Domain`, `Partitioned`/CHIPS, and `Priority` remain unsupported.

Native sessions keep their existing lifecycle and fixed cookie shape. A live session cookie has no `Expires` or `Max-Age`, but browser restoration can retain it; server-side idle and absolute expiry remain application policy. `HttpOnly` prevents ordinary script access to cookie bytes but does not prevent script-initiated authenticated requests or replace CSRF, XSS, CSP/output, endpoint, logging, authentication, authorization, logout, revocation, HTTPS, browser, or deployment policy.

This correction advances Consumer Contract version 11 to version 12. It changes no public constructor signature, adds no public method or class, and adds no runtime dependency, Strict Profile rule, or permanent diagnostic. The incompatibility is the smaller accepted value domain: an Alpha 6 construction outside these bounds fails under a future Alpha 7 candidate.

## Consumer Contract version 13 file-transfer profiles

ADR 053 carries Contract version 12 forward and splits the optional file-transfer path into common bounded multipart and application-policy requirements plus exactly one deliberately selected profile:

- `LOCAL_ADR026` preserves visible `move_uploaded_file`, local `LocalFileBody`, a complete local `200`, `X-Content-Type-Options: nosniff`, and deferred ranges unchanged; or
- `AMAZON_S3_ADR053` replaces only that durable local move and response portion with one exact application-owned direct-S3 profile and its application, isolated real-AWS, and dated deployment evidence.

The S3 opaque-byte response is a fixed `application/octet-stream` attachment served by an exact-version pre-signed `GetObject`. Direct S3 cannot guarantee the local profile's `nosniff` header. Contract version 13 accepts that absence only as this profile's narrow accountable exception; the application's initial `303` does not govern S3's separate response. The reusable URL is not claimed to be one-time, immediately revocable, range-free, received by the client, malware-safe, transactional with application metadata, or exactly once.

The framework, source skeleton, dedicated skeleton, and executable example add no AWS dependency, credential provider, configuration, client, presigner, retry policy, storage interface, route, lifecycle worker, network call, or S3 behavior. The health-only skeleton remains `NOT_APPLICABLE(FILE_TRANSFER)`, and the executable example remains the non-production `LOCAL_ADR026` reference.
