These notes describe the accepted bounded Alpha 6 source claim. Identity, scope, notes, planned date, announcement-draft, and source-preparation approval do not approve an exact candidate commit or authorize a commit, push, tag, package update, dedicated-skeleton change, GitHub prerelease, public installation claim, or announcement. Every external operation remains subject to the complete release proof and later accountable-human authorization in `RELEASING.md`.

## Purpose

Alpha 6 carries the complete Alpha 5 foundation forward and rolls up a feedback-driven hardening release focused on safer response and session boundaries, clearer application ownership, and navigable maintainer evidence. It advances the Consumer Contract from version 10 to version 11 while retaining Strict Profile version 3 and permanent diagnostics `PHT001` through `PHT007`.

This prerelease remains experimental evaluation software. It is not production-ready and makes no backward-compatibility promise across prereleases.

## Breaking prerelease changes

### PathParameters factory removal

The redundant public-prerelease convenience factory `PathParameters::onePositiveInteger()` is removed. Replace:

```php
$parameters = PathParameters::onePositiveInteger($name, $value);
```

with:

```php
$parameters = PathParameters::fromValues([$name => $value], []);
```

The replacement constructs the equivalent immutable value. Route declarations, accepted `positive-int` grammar, matching, and the `positiveInteger()` accessor are unchanged. An old call fails because the method no longer exists.

### Stricter ordinary response framing

`Response` now rejects:

- final informational `1xx` statuses;
- every ordinary `Transfer-Encoding` header;
- a non-canonical or body-mismatched ordinary `Content-Length`; and
- an ordinary body or `Content-Length` on `204`, `205`, or `304`.

An ordinary content-bearing response may omit `Content-Length`; when supplied, it must be the canonical decimal byte length of the supplied body. `HEAD` remains an explicit application-owned route with an empty body and no `Content-Length` under this safe subset. PHPThis does not infer `GET`, suppress a representation body, or calculate representation length.

## Deterministic native-session cleanup

When an operation has an original failure and native-session cleanup succeeds, PHPThis rethrows the exact original `Throwable` instance. When cleanup also fails, the narrow redacted `SessionCleanupFailed` retains both failures for framework-level diagnosis without exposing session identifiers, paths, state, or failure messages in its public text.

Cleanup is bounded, preserves or clears lifecycle state according to the operation's safe prerequisite order, and performs no hidden retry. `SessionCleanupFailed` is deliberately excluded from ordinary `ErrorResponseRegistry` mapping and remains on the generic redacted unknown-failure path. This is not transactionality with earlier database or external work and adds no logger, recovery service, or response conversion.

## Corrected eval guardrail

The existing forbidden-`eval` check now rejects the actual language construct without rejecting legal methods, properties, or other same-named identifiers. This is a false-positive correction, not a relaxation of the `eval(...)` prohibition and not a new diagnostic or Strict Profile version.

## Optional application-owned guidance

### Development Workbench

ADR 041 records PHPThis Workbench as an optional separate development-only package for inspecting one explicitly composed object through one fresh strict expression process at a time. Adoption is application-owned and does not add framework core, a service container, discovery, a generic dispatcher, batch or remote execution, a production shell, a sandbox claim, or a validity shortcut. Availability must be verified externally.

### Configuration evidence and probe semantics

Configuration guidance now includes a copyable application-owned child-process evidence pattern. A short-lived fixed-output child receives only an explicit bounded synthetic environment and exercises exact valid, missing, empty, malformed, maximum-plus-one, captured-output non-disclosure, and adopted-profile-separation behavior. Consumers adapt the names, grammar, bounds, fixture, and runner integration; PHPThis adds no process runner, test library, secret detector, parent-environment guarantee, or production configuration mechanism.

Startup and probe guidance now states that visible composition can perform synchronous work. `Connection::connect()` constructs PDO eagerly and may perform driver- and DSN-specific I/O during composition. The database-free starter `GET /health` composes no database, cache, queue, or network client, but its terminal coordinator still invokes the deployment-configured `error_log` sink synchronously; that destination can itself use network or remote-filesystem I/O. Each application records the exact liveness or readiness claim, composition root, synchronous dependencies and destinations, bounded work, failure behavior, owner, and evidence. PHPThis adds no probe API, lazy connection, hidden bypass, second HTTP path, or universal readiness definition.

### Structured request-body failure precedence

For application-owned structured request-body content, the recommended parser completes the entire shape and native-type phase before applying value rules. Malformed shape or native types return generic `400`; a completely shaped and typed payload with unacceptable values uses one exact application-owned generic `422`. Mixed structural and value failures remain `400` regardless of property order.

An application may retain another explicitly recorded and tested finite status contract. Query, header, route, multipart, and other transport representations retain their separately recorded boundaries. PHPThis adds no generic validator, error bag, validation exception, renderer, or framework-owned `422` behavior.

### Engine-specific migrations

ADR 043 separates universal application-owned migration invariants from the SQLite-only reference mechanisms. Each selected engine records its ledger-consistency boundary, coordination topology, non-atomic states, immutable forward recovery, authority handoff, and exact-engine evidence. Separately tracked histories may have explicit subdivisions; they are independent only when their objects, data, authority transitions, and coordination domains are proved disjoint.

PHPThis adds no migration API, schema builder, discovery, rollback inference, portable DDL, or cross-engine coordination abstraction.

### Task-routed AI context

ADR 044 routes ordinary work through one current concern guide and keeps universal entrypoints free of concern-specific duplication. A qualifying dependency-free simple endpoint has exactly four task-specific files after the universal entrypoints: one current guide, the existing named route-area manifest, the handler, and the nearest behavior test. Broader work follows its actual concerns rather than skipping context to preserve that count.

Application `AGENTS.md`, `.ai/` context, source layout, and decisions remain project-owned. Framework upgrades are reconciled deliberately and never overwrite or relocate those files.

### Canonical executable-example boundaries

ADR 046 consolidates four example-application choices:

- the composition-root registry solely owns its exact generic `400` response mapping;
- one application-owned semantic `UserId` carries the shared positive user identity while operation projections remain distinct;
- scheduled cadence is checked before database-path, Redis, PDO, token, SQL, or job dependency work; and
- authoritative document titles must be non-empty valid UTF-8, independently from the cache's narrower byte-admission limit.

These are executable application patterns, not framework identifier, error-renderer, scheduler, cache, or projection services.

### Identifier, UUID, CRUD, and evidence organization

Current guidance recommends one coherent application-owned semantic type per shared identifier invariant. The application records public representation, generation owner, supported UUID versions, storage and binding behavior, and narrower domain policy. UUID acceptance covers canonical versions 1 through 8 by default, while generation is explicitly versioned: version 7 is recommended for new database row identifiers when its embedded approximate-time disclosure is acceptable, version 4 remains the random-only alternative, and version 5 the recorded deterministic alternative. The framework mandates no generator library.

The optional feature-first CRUD reference profile now makes public and administrative access surfaces explicit when they have different route, policy, or representation contracts. Consumers may adopt that structure or record one coherent alternative. PHPThis does not enforce directories, generate a complete CRUD set, or add a repository, ORM, model binding, identifier base class, trait, interface, or generic service layer.

As application-owned test or validation evidence grows, one small deterministic entrypoint with cohesive concern modules is recommended. Applications continue to choose their test library, directory layout, and commands; there is no discovery rule or consumer-validity requirement.

## Maintainer evidence hardening

The framework behavior suite and repository guardrails are split into concern-owned modules while retaining their stable complete entrypoints, inventory checks, and diagnostic order. Repeated source and installed-distribution proof helpers are consolidated without treating one evidence source as the other. Installed-guide and vendor-root escape proof is repaired, PDO certification versions are executable, ADR successor relationships are explicit, and release preparation is version-neutral.

These are maintainer changes. They add no framework runtime dependency, consumer test-library requirement, checker discovery system, public API, Strict Profile rule, or new `PHT` diagnostic.

## Upgrade from Alpha 5

1. Review Consumer Contract version 10 to version 11. Strict Profile version 3 and diagnostics `PHT001` through `PHT007` remain unchanged.
2. Replace every `PathParameters::onePositiveInteger()` call with `PathParameters::fromValues([$name => $value], [])`.
3. Replace contradictory response construction with one supported explicit response and keep any `HEAD` route explicit.
4. If native sessions are adopted, prove primary-failure identity, dual-failure retention and redaction, terminal cleanup state, and exclusion of `SessionCleanupFailed` from registered response mapping.
5. Record and prove the application's structured-body failure precedence; the recommended default is complete shape/type `400` before unacceptable-value `422`.
6. Reconcile the installed guidance with project-owned context and structure without overwriting it. Keep Workbench adoption optional and separate.
7. Update to the exact Alpha 6 prerelease only after reviewing these changes, then run the complete application gate on PHP 8.4.x.

## Carried-forward boundary

Alpha 6 retains zero third-party framework runtime dependencies, explicit manual composition, immutable HTTP values, finite route declarations, direct visible engine-specific SQL through `Connection`, distinct named bindings, compile-time-constant SQL structure, query budgets and traces, and separately certified PDO transport. The 2,600-line core ceiling remains unchanged; the current source occupies 2,595 lines and its five-line margin authorizes no adjacent mechanism.

The release does not add or permit:

- an ORM, Active Record, lazy loading, model or repository layer, query builder, generated SQL, binding or placeholder helper, generic paginator, dialect abstraction, or generic database layer;
- implicit or global scopes, observer magic, automatic discovery, reflection-based wiring, service container, facade, global helper, macro system, dynamic proxy, or autowiring;
- a framework validation engine, identifier base class, UUID generator or library mandate, configuration runtime, provisioning API, schema builder, migration framework, permission helper, role registry, portable DDL, or automatic deployment hook;
- generic or framework middleware, a hidden request pipeline, request-context bag, native WebSocket runtime, generic cache, queue, scheduler, production shell, or automatic application-context rewrite;
- hidden database calls, database work inside loops, hidden retries, automatic cache refill or invalidation, automatic job or migration discovery, inferred rollback, or exactly-once external-effect claims; or
- production readiness, a support or security-response SLA, complete CRUD, universal AI compliance, secret detection, grant validation, portable application SQL or DDL, deployment certification, or capacity certification.

Consumers remain responsible for product abstractions, identity and generation policy, tenancy, authorization, schema, database plans and authority, concurrency, deployment, operational limits, observability destination, third-party runtimes, Workbench adoption, source and test organization, and complete behavior evidence.
